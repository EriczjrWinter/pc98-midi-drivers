# PC-98 私有 MIDI ドライバの発掘

[中文](README.md) | [English](README.en.md) | **日本語**

PC-98 のゲーム音楽の多くは「**データ + ドライバ**」という構造をしています。
データはただのイベントスクリプトで、本当のフォーマット仕様は
数百バイト〜数 KB の常駐ドライバの中にあります。

厄介なのは、**ドライバにドキュメントが無いこと**です。
**実行時の振る舞いだけが仕様**になります。

このリポジトリは、そうしたドライバを一つずつ掘り起こし、
動かして、音楽を取り出す試みです。

> 基本手法：**データを解析せず、ドライバ自身に走らせて出力を捕まえる。**
> フォーマットが既に文書化されている場合は静的解析で済ませます。
> どちらが楽かで選ぶのであって、原理主義にこだわりません。

## そのドライバ、解くべきか

**「PC-98 に MIDI がある」＝「ドライバを解析すべき」ではありません。**
逆に、Windows 移植版にだけ MIDI がある作品もあります。

| 分類 | PC-98 | Win | 対応 |
|---|---|---|---|
| **A** | あり | なし | ドライバを解くしかない |
| **B** | なし | あり | Windows 版を使う（通常は標準 MIDI） |
| **C** | あり | あり | 楽な方を選ぶ |
| **D** | なし | なし | CD-DA / WAV / FM、対象外 |

一覧は [catalog/](catalog/)、方針は [docs/CATALOG.md](docs/CATALOG.md)。

## 一般的な手順

会社が違っても、手順は同じです。

1. **ドライバを探す**：`.COM` / `.SYS` / `.BIN`、数百バイト〜数十 KB
2. **何をフックしたか見る**：常駐型はハードウェア割り込み + 機能呼び出し割り込み
3. **出力ポートを探す**
   - MIDI → インターフェースボードのデータポート（PC-98 では `0xE0D0` が多い）
   - FM → OPNA レジスタ（`0x188` / `0x388`）
4. **タイマをこちらで制御する** ← リアルタイムで待たなくて済む鍵
5. **バイトを集めて MIDI を組み立てる**

### 繰り返し踏んだ罠

| 罠 | 症状 | 対処 |
|---|---|---|
| Unicorn はリアルモードの IVT を辿らない | `UC_ERR_EXCEPTION` | `CD xx` のアドレスを個別にフックし `IP += 2` |
| `IN` のフックが値を返さない | `'NoneType' cannot be interpreted` | コールバックで `return value` |
| ドライバがタイマを書き換える | 速度が合わない、しかも**曲ごとに違う** | `out 0x77/0x71` を記録し tick 単位で換算 |
| クロック周波数の誤認 | 20〜30% 速い/遅い、エラーは出ない | PC-98 の 8253 は **2.4576 MHz** |
| ループ曲 | 何回も書き出される | バイト列の周期性検出で 1 回に切る |
| **同名で別ビルド** | 別のゲームで落ちる | **内容ハッシュで区別**、ファイル名は信用しない |

### 一言でいうと

**ファイルフォーマットは音楽の定義のすべてではない。**

`.MS` / `.FMD` / `.MMD` には「何拍待つ」とは書かれていません。
オペコードとオペランドだけです。本当の意味論（遅延 1 単位が何 tick か、
未知のコマンドが何をするか）は**ドライバの実行時の振る舞いにしか存在しません**。

だから静的解析で分かるのは**構造**だけで、**時間の意味論**は分かりません。
MMDR、MS.COM、MSDRV4 が最後に同じ答えに辿り着いたのはそのためです——
**本人に喋らせるしかない。**

## 著作権

ゲームデータ、ドライバ、音楽の著作権は各権利者に帰属します。
本リポジトリは**解析・変換コード**と、データから導出した**形式の文書**のみを含みます。
