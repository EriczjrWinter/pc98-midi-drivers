# MMDR —— LEAF 的 PC-98 MIDI 音源驱动

> 作者：**H.Ninomae**（驱动横幅写的就是这个署名）
> 出处：LEAF（リーフ）PC-98 作品
> 类型：常驻型（TSR）MIDI 驱动，通过 `INT 7Eh` 接收命令，把 `.MD` 曲数据翻译成 MIDI 字节流，
> 从 **MIDI 接口板的数据口 `0xE0D0`** 发出

---

## 0. 一句话

`.MD` 不是 MIDI 文件，是**给驱动解释的紧凑事件脚本**；MMDR 也不是播放器界面的那种东西，
它是一层翻译器——**输入 `.MD`，输出标准 MIDI 字节**。

所以想要 MIDI，不需要解析 `.MD`，**只要让驱动跑起来，把 `0xE0D0` 上的字节收下来就行**。

---

## 1. 已知的两个构建

| 作品 | 大小 | 入口 | `INT 08h` | `INT 7Eh` |
|---|---|---|---|---|
| 雫 -しずく-（1996） | 3218 B | `jmp 0x0BF2` | `0x0103` | `0x0479` |
| 痕 -きずあと-（1997） | 3954 B | `jmp 0x0E5A` | `0x0103` | `0x0555` |

**结构完全同源**，只是代码位置不同。差异集中在功能增加（痕的命令更多），
但对外接口、I/O 端口、`.MD` 头部布局都一样。

同一代还有更早的 **`MS.COM`**（`DR²ナイト雀鬼`、`Filsnown ～光と刻～` 的 MIDI 版），
数据也是 `.MD` 扩展名，推测是 MMDR 的前身——**未验证**。

## 2. 安装流程

执行 `MMDR.COM` 后（`.COM` 装在 `CS:0100`）：

```
1. 读 PIC 掩码（in al, 2）保存
2. 装 INT 08h  ← 0x0103（定时器，驱动音乐推进）
3. 装 INT 7Eh  ← 功能调用入口
4. 编程 8253 通道 0：out 0x77, 0x36；out 0x71, lo；out 0x71, hi
   计数 = 0x4E00（安装时的默认值，播放时会被改写）
5. 开中断（in al,2 / and al,0xFE / out 2,al）
6. AH=31h 常驻
```

如果在装之前检测到已经常驻（把 `0x103` 起 0x5F5 字节和当前 `INT 08h` 目标比对），
就只打印「常駐しました．」然后退出。

## 3. 功能调用（`INT 7Eh`）

`AL` = 功能号（0–9），跳转表在 `0x0BD3`（雫）/ 对应位置（痕）。

| AL | 作用 | 参数 |
|---|---|---|
| 0 | MIDI 接口初始化 / 探测 | — |
| 1 | 发 MIDI 复位（`0xFF`） | — |
| **2** | **装载并播放 `.MD`** | `DX` = 曲数据的**段地址** |
| 3 | 停止 | — |
| 4 | 读 tick 计数 | → `AX` |
| 5 | 读状态 | → `AX` |
| 6 | 其它控制 | `DL` |
| 7–9 | 其它控制 | `DL` |

`AL=2` 的关键几行（雫，`0x0541`）：

```asm
mov ds, dx              ; DS = 曲数据段
mov cs:[0xb61], dx      ; 记下数据段
lea di, [0x6f8]
mov cx, 0x469
rep stosb               ; 清空 0x469 字节的运行状态
xor si, si
mov bx, [si]            ; 头部 word0 = 8253 计数（tempo）
mov cs:[0x6fa], bx
add si, 2
mov ax, [si]            ; 头部 word1 = 备用计数（另一机型）
mov cs:[0x6fc], ax
...
out 0x77, 0x36 / out 0x71, lo / out 0x71, hi   ; 用计数编程定时器
lea di, [0x700]
mov cx, 0x12            ; 18 个通道
```

## 4. `.MD` 格式

### 4.1 文件头

```
偏移 0   u16   8253 计数值（tempo）        周期 = 值 / 2457.6 毫秒
偏移 2   u16   备用计数值（另一机型）
偏移 4   u16   chptr[18]                  18 个通道的数据起始偏移
```

**实测验证**（雫，头部 word0 与运行中 8253 的实际计数逐一吻合）：

| 文件 | word0 | 周期 | 实测计数 |
|---|---|---|---|
| `sz_gs07.md` | `0x6000` | 10.00 ms | `0x6000` ✓ |
| `sz_gs08.md` | `0x7362` | 12.02 ms | `0x7362` ✓ |
| `sz_gs16.md` | `0x7D00` | 13.02 ms | `0x7D00` ✓ |
| `sz_gs15/18.md` | `0x7A72` | 12.75 ms | `0x7A72` ✓ |

**PC-98 的 8253 时钟是 2.4576 MHz**，所以 `周期(ms) = count / 2457.6`。

### 4.2 通道运行状态（驱动内存 `0x700 + i*0x3E`，18 条）

| 偏移 | 含义 |
|---|---|
| `+0x00` | 活动标志（0 = 停止） |
| `+0x01` | **等待 tick 数**（到 0 才读下一条） |
| `+0x04` | 当前数据指针（文件内偏移） |
| `+0x06` | **MIDI 通道号** |
| `+0x07` | 同音处理计数 |
| `+0x08` | 内层计数 |
| `+0x0A` | 内层重装值 |
| `+0x3A` | 循环保存指针 |

### 4.3 数据流

每个 tick，18 个通道各执行一次：`[+1]` 减一，归零则读下一个字节。

```
字节 < 0x80   →  音符：音符号 + 2 字节
                     第 1 字节 → 内层计数
                     第 2 字节 → 外层等待（下一条命令前要等的 tick 数）

字节 >= 0x80  →  命令：命令号 = 字节 - 0x80
                     查跳转表 0x0B64（雫）
                     处理完的返回值 → 写回等待计数
                     ★ 返回 0 表示同一 tick 立刻继续执行下一条
```

### 4.4 已确认的命令

| 条目 | 字节 | 作用 |
|---|---|---|
| `0x00` | `80` | 设置本通道的 **MIDI 通道号**（读 1 字节） |
| `0x01` | `81` | 设置 **tempo**（读 2 个字，重新编程 8253） |
| `0x02` | `82` | 设置**音量**（CC7） |
| `0x22` | `A2` | **循环跳转**（用 `[+0x3A]` 保存的指针） |
| `0x23` | `A3` | **停止本通道**（`[+0]=0`，返回 0xFF） |
| `0x24` | `A4` | **停止**（返回 0xFF） |
| `0x07`/`0x08`/`0x0B`/`0x0F` | `87`/`88`/`8B`/`8F` | 都跳同一段（`0x328`），应为「发送一个 CC」 |

其余条目未逐一确认。

## 5. 为什么不该自己解析 `.MD`

如果按「读字节 → 翻译成 MIDI」写一个解析器，会踩这些：

1. **头部不是「文件头 + 数据区」**，而是 tempo + **18 个通道指针**。按「前 N 字节是头」猜必然错位。
2. **命令返回值是等待 tick 数，返回 0 表示当 tick 继续跑**。写成「一条命令一 tick」，
   整首会越走越偏——**而且听起来只是「节奏不对」，不会报错**。
3. **音符有同音分支**：和本通道正在响的音同高时走另一条路，字节消耗不同。线性解析遇到同音连打就失步。
4. **通道是 18 个**，不是 16。
5. **`A2` 会跳指针**，线性扫描会读到文件尾。

这些都属于「不报错、只是听起来不对」的坑。

**让它跑，比重新实现它省事。**

## 6. 运行器（本项目 `src/mmdr_emu.py`）

在 Unicorn 里用 16 位实模式把驱动跑起来，**自己敲 `INT 08h`**，所以不用实时。

### 6.1 内存布局

| 用途 | 段 |
|---|---|
| PSP + 程序体 | `0x1000`（`.COM` 装在 `CS:0100`） |
| 曲数据 | `0x2000`（`AL=2` 的 `DX` 指向这里） |
| 桩 / 魔术返回 | `0xE000` |
| 栈 | `0x1000:FF00` |

### 6.2 四个必须处理的坑

**① Unicorn 不走实模式 IVT**
设了 IVT 再执行 `INT 21h`，会直接抛 `UC_ERR_EXCEPTION`。
做法：扫整个镜像里的 `CD xx`，**按地址逐个挂 hook**，在 hook 里做 DOS 调用后 `IP += 2`。

**② `IN` 的 hook 必须返回值**
Unicorn 的 `UC_HOOK_INSN` + `UC_X86_INS_IN` 回调要 `return value`，
否则报 `'NoneType' object cannot be interpreted as an integer`。

**③ 定时器要自己敲，而且要跟着改**
驱动会用 `out 0x77, 0x36` + 两次 `out 0x71` 重编程 8253（这是它实现每首曲子 tempo 的方式）。
必须把这些写入记录下来，逐 tick 换算成毫秒——否则整首会快 20%–30%，
**而且每首曲子的偏差还不一样**（因为每首的计数不同）。

**④ 循环曲目**
找到字节流里第一处「512 字节重复 + 后续 4096 字节也完全一致」的位置，截断成一遍。
只比 512 会误判内部短重复（鼓点之类）。

### 6.3 用法

```bash
pip install unicorn

python src/mmdr_emu.py 7                      # 雫 第 7 首
python src/mmdr_emu.py --dir <痕的数据目录> --prefix KZ_GS --all --count 26
```

数据目录里需要有 `MMDR.COM` 和 `sz_gsNN.md` / `GSNN.MD`（两种命名都能自动识别）。

## 7. 验证

雫的 5 份参考 MIDI（在 HOOT 上录制的）逐音符对照：

| 参考 | 对应 | 音符差异 | 时间比值 |
|---|---|---|---|
| 世界が変わるとき（瑠璃子） | GS08 | 0 / 300 | 0.999 |
| MOON PHASE（トゥルーエンド） | GS16 | 0 / 300 | 0.999 |
| sunny-side up（沙織） | GS07 | 0 / 300 | 0.998 |
| 雫（オープニング） | **GS15** | 0 / 300 | 0.998 |
| 月蝕（バッドエンド） | **GS18** | 0 / 300 | 0.999 |

> **注意**：后两条与 HOOT 的曲名表正好对调。HOOT 说 GS15=バッドエンド、GS18=オープニング，
> 但实际数据内容相反。以录音为准。

## 8. 速度

约 40 分钟的音乐，**80 秒左右算完**（约 30 倍实时）。
瓶颈在 Python 的 hook 回调，不是模拟本身。
