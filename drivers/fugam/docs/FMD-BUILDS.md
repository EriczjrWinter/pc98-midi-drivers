## 0. 版本表（实测）

装法见第 7 节；`INT D3` / `INT 0E` / `[0x17]` 都是**安装完成后**从仿真内存里读出来的。

| 包 | FMD.EXE | md5 前 8 | 内部版本串 | INT D3 | INT 0E | `[0x17]` | 装后 `[0x1E]` | 导出 |
|---|---|---|---|---|---|---|---|---|
| reno / momoko / papa / tlove12 / yumecol / farce / hiragi | 4857 | `699a8a5e` | **Version 1.72** | `1010:003F` | `1010:06A1` | 16 KB | 0 | ❌ |
| ama4 / amakh | 4969 | `991dbe8d` | **Version 1.71** | `1010:003F` | `1010:06A1` | 16 KB | 0 | ✅（缺 program change，见 §5） |
| mug-r | 5365 | `de5bf6f7` | Version 1.61 | `1010:003C` | `1010:0610` | 16 KB | 0 | ❌ |
| venus | 4601 | `f06ac87f` | Version 1.51 | `1010:003B` | `1010:05CF` | 16 KB | **1** | ✅（15 首） |
| image2 | 5248 | `3dfd0981` | 无版本串 | **`1010:0056`** | `1010:05CB` | **8 KB** | 0 | ✅（14 首） |

**4857 与 4969 的 `INT D3` / `INT 0E` 完全一致**——这一条本身就否掉了「入口地址不同」。

## 1. 文件层：差的 112 字节全在 MZ 头

| | 4857（1.72） | 4969（1.71） |
|---|---|---|
| MZ 头 | 32 字节（最小头，`e_cparhdr=2`） | 144 字节（`e_cparhdr=9`） |
| 头里的招牌 | 无 | `FUGA MIDI Driver Version 1.71   1994/ 7/ 6 11:03 Copyright(C)1994 by FUGA System  All rights reserved.` |
| 代码 payload | **4825 字节** | **4825 字节** |
| 入口 | `010F:0000` | `010F:0000` |
| SS:SP | `01CB:02F0` | `01CB:02F0` |

- 两者 `e_crlc=0`（没有重定位项），所以**重定位表那一段是空的**；4969 的链接器正好把版本
  招牌填进了这段空位（头偏移 `0x1E` 起）。4857 用最小头，招牌被裁掉。
- **payload 一样大**，所以「4969 − 4857 = 112 字节」= 头差，不是代码变多/变少。
  （`e_cp=10` 两边相同，只有 `e_cblp` 249 → 361。）

### 打包壳

两版都是同一套 Zortech/SLR **LZSS 自解压壳**，stub 在 body `0x10F0`–`0x12D9`（489 字节），
**逐字节相同**：

```
010F:10F0  xchg ax,ax / jmp 10FF        ; 入口
           dx = ds+0x10                  ; 目的段
           复制 0xF5 个 word 到 ss:0      ; 把自己搬到内存顶部
           retf → 副本 +0x31（0x1121）    ; 再往下搬，腾出 unpack 空间
           ...                          ; 0x1150 起是 LZSS 解码器（0x1000 窗口、16 位标志字）
           最后 mov ss,cs:[9] / mov sp,cs:[7] / ljmp cs:[0xB]
```

- 打包层 4825 字节里 **3786 相同（78%）**，第一处差异在 body `0x483`。
- 差异集中在 body `0xCC4`–`0x10E2`，解压后对应**安装器 + 帮助文本**（见第 2 节）。

## 2. 解压后（常驻镜像）：引擎相同，只差安装器和文本

用 `build/_fmd_dumpdrv.py <pack>` 装一次、dump `1010:0000` 起的 `0x6000` 字节：

| 口径 | 4857 vs 4969 |
|---|---|
| 常驻镜像大小 | 24576 / 24576 |
| 相同字节 | **23597（96%）** |
| 差异 | **38 段 / 979 字节**，全部落在下面三处 |

| 位置 | 4857（1.72） | 4969（1.71） | 说明 |
|---|---|---|---|
| `0x1BA1` | 多 3 字节 `83 C3 0E`（`add bx, 0x0E`） | 无 | 安装器在 `INT 21/AH=48` 前把申请量**加 14 段（224 字节）** |
| `0x1C3D`–`0x1F88` | `Version 1.72`、`-?` 帮助日文措辞改动 | `Version 1.71`、旧措辞 | 因此 `0x574`/`0x5C1` 两条消息指针也差 3 |
| `0x20E8` / `0x2162` / `0x2164` | `0F` / `B8` / `DF` | `00` / `B9` / `E3` | 落在**运行时被改写的 stub 副本/栈区**（该区非零字节从 `0x20A0` 起就是搬移后的 loader），不是常驻代码；未解明，见 §6 |

**相同（逐字节）的部分包括**：AH 分派表（`0x73` 起 18 项）、`0x0100` 装载、18 轨建表、
事件解释、板命令序列、`INT 0E` 处理。所以「4857 与 4969 的引擎行为差异」在代码里不存在。

**唯一的功能差异**是那条 `add bx,0x0E`：1.72 在安装时比 1.71 多要 224 字节 DOS 内存
（`[0x17]` 两边都是 16 KB → `16×64 = 1024` 段，1.72 是 1038 段）。

## 3. 顺带确认的驱动语义（两版相同）

安装后 `INT D3` 入口：

```
003F  EB 02                  jmp 0043
0043  2E F6 06 1E 00 01      test byte cs:[0x1E], 1     ← 壳 FUGAM_98.COM 扫的就是这条
0049  75 27                  jne 0072                   → 0072 = iret（API 全静默）
004B  ... 60 8C CB 8E DB 8E C3
0054  2E C6 06 19 00 00      mov byte cs:[0x19], 0
005A  33 DB 8A DC            mov bl, ah                 ← 分派索引是 AH
005E  03 DB                  add bx, bx
0060  8D 9F 73 00            lea bx, [bx + 0x73]        ← 分派表在 0x73
0064  FF 17                  call word [bx]
0066  61                     popaw
0067  2E A0 19 00 / 2E 8A 26 1A 00  返回码取自 cs:[0x19]/cs:[0x1A]
0072  CF                     iret
```

- **分派索引是 AH，不是 AL**（`8A DC` = `mov bl,ah`）。表在 `0x73`，共 **18 项（AH=0x00–0x11）**，
  第 `0x12` 项起读到的是数据（`0xBA27`、`0xE0D2`…）。旧文档写的「AL 分派表 0–0x1A」应改成
  「**AH** 分派表 0x00–0x11」。
- 表（词偏移，两版相同）：`0095 00D4 03A6 02BE 0337 03F1 03FC 0422 042F 044C 0453 046A 04A6 04CB 0505 0537 0561 10B9`
  → 对应 `AX=0100`（装歌）、`AX=0201`（送音色）、`AX=0300`（播）、`AX=01FF`（停）等。
- 「已装过」判定：`INT 21/AH=35` 取 D3 向量后 `cmp word es:[3], 0x270B`——`0x270B` 就是
  `D3:0041` 那两个字节 `0B 27`。命中则跳到 `0x0569`（「已常驻」分支，不再挂一次）。

### 3.1 A 代 / B 代的实际分界（`INT D3` 入口形态）

| build | INT D3 | 入口测 `[0x1E]` | 分派表 | 返回码变量 |
|---|---|---|---|---|
| FMD9 4774（ama2s） | `0056` | 无 | —（未查） | — |
| FMD13 5301（ama2m） | `0056` | 无 | —（未查） | — |
| FMD7 4998（marple） | `0054` | 无 | —（未查） | — |
| image2 5248 | `0056` | **无** | `0x88` | `[0x18]` |
| venus 4601（1.51） | `003B` | **无** | `0x69` | `[0x19]` |
| mug-r 5365（1.61） | `003C` | 有（`0x40`） | —（未查） | — |
| ama4/amakh 4969（1.71） | `003F` | 有（`0x43`） | `0x73` | `[0x19]` |
| reno 等 4857（1.72） | `003F` | 有（`0x43`） | `0x73` | `[0x19]` |

- **`0056` 是 A 代的入口形态**（FMD9 / FMD13 / image2 都是它），B 代是 `003B`–`003F`。
  所以旧文「4969 build 是 `1010:0056`」不仅数值错，连代次都张冠李戴了。
- `[0x1E]` 门只出现在 **003C / 003F** 这几个 build 上（mug-r、1.71、1.72）；
  venus（1.51）和 image2 的入口根本**不测**它——所以壳的 patch 对这两版是空操作。
  实测 venus 装完 `[0x1E]=1` 仍能导出，正好对上。
- `build/_fmd_export.py: shell_patch()` 只扫入口后 96 字节，因此不会误伤 venus 里
  `0x4FE` 那个**巧合命中**的同字节序列（那里不是门）。

### 命令行参数解析（`0x1A12`–`0x1B66`，两版逐字节相同）

前缀 `-` 或 `/` 等价，逐字符：

| 参数 | 效果 |
|---|---|
| `-?` | 打印帮助后 `exit(2)` |
| `-I n` / `-i n` | 取参数（`sub '0'`，必须 ≤2），从 `0x2B` 的**3 字节记录表**（`n*3`）取三项 → `cs:[0x28]/[0x29]/[0x2A]`；原字符另存 `cs:[0x1E62]` |
| `-O` / `-o` | `cs:[0x20] = 1` |
| `-G` / `-g` | `cs:[0x1F] = 1` |
| `-#` | **`cs:[0x1E] = 1`**（`/#` 同一个分支；这就是「D3 直接 iret」的开关） |
| `-R` / `-r` | `cs:[0x0B] = 1`，并**立刻跳到安装/常驻**（不继续解析后面的参数） |
| `-<1~3 位十进制>` | 十进制 → `cs:[0x17]`＝**申请内存 KB**（安装时 `bx = [0x17]<<6` 段） |

`cs:[0x29]` 在 `0x057A`–`0x0583` 被 OR 进端口 `0x02` 的读值再写回（板子设置），
`[0x28]/[0x2A]` 的具体用途还没定。**结论：`-<n>` 和 `-In` 不只是「让 D3 挂不挂」，
它们改的是内存大小与板子配置**——排查「装上了没声」时先看命令行。

## 4. 更正 HANDOFF / FMD.md 的两条

1. **「4969 build 是 `1010:0056`」是记串了。** 实测 4969（ama4/amakh）＝`1010:003F`，
   与 4857 相同；`0056` 属于 `image2_98` 的 5248 字节 build（无版本串、`[0x17]=8 KB`）。
   （项目交接文档（不随库发布） 里 FMD9 安装小节的「`INT D3=1010:0056`、`INT 0E=1010:05BF`」是**A 代**的数，
   实测 ama2s_98 就是这个值——所以更可能是这两组数被抄混了。）
2. **「解决 4857 与 4969 的 API 差异可一次解锁 7 个包」不成立**：引擎逐字节相同，
   1.71 能跑的曲子 1.72 没理由跑不了（反之亦然）。剩下的差异在**数据 / 命令行参数 / 安装环境**。

## 9. 2026-11-23 晚补测

### 9.1 交叉实验（决定性）

把驱动和数据交叉，各跑 300 tick：

| 数据 × 驱动 | 轨道表 | 300 tick 输出 | 0x90 音符 | 结论 |
|---|---|---|---|---|
| reno `RENO_000.GS` × **1.71**（4969） | 18 | 246 字节 | **82** | 正常 |
| ama4 `AMA4_000.GMD` × **1.72**（4857） | 18 | 431 字节 | **0** | 坏 |

**同一份 reno 数据换 1.71 就响；同一份 ama4 数据换 1.72 就不响。**
→ 失败与**数据无关**，是 1.72 这个 build 在本环境下跑不起来。
（复现：`python build/_lead_fmd_cross.py`）

### 9.2 AH=48 内存分配：不是根因

1.72 安装时 `AH=48` 请求 **1038 段**（1.71 是 1024 段，正是那 +14 段）。
给 `Board._dos` 补上 bump 分配器（heap 从 0x2000 起，`para+0x10`）后重跑：

```
heap 用完: 0x241e
bytes=68409  0x90=0  0xC0=0
```

**和没补一样**。所以“多要 14 段内存”不是失败原因。
（复现：`python build/_lead_fmd_alloc_fix.py`）

### 9.3 常驻镜像差异：两处可疑的“自改写”字节

979 字节差异里大多数是版本串偏移引起的跳转位移，剩下两处仍在运行时 loader 副本区：

```
0x20E8: 1.71 = 0f 85 00 00      1.72 = 00 85 00 00
0x2162: 1.71 = b8 14 df 10      1.72 = b9 14 e3 10
```

形态像**安装时自我改写的常量**（段地址 / 近跳转目标）。1.72 装得上、轨道表也建得出，
但播放不出音符，最可能就是这份运行时副本没被打对补丁。

**下一步**：hook 写入 `0x121E8` / `0x12262`（段 0x1010 + 上述偏移），对比两个 build
的写入序列与写入值；再顺藤找到补丁代码的输入（是否依赖 `AH=48` 返回段 / PSP 字段）。

（复现：`python build/_lead_fmd_imgdiff.py`）

## 10. AMA4/AMAKH 缺 program：先做 30 秒判定

**现象**：`ama4_98` / `amakh_98` 已导出 41 首，但**没有 program change**。直接盯驱动
（1.71），`AMA4_000.GMD` 前 400 tick 的数据口只有 `B0 79 00` / `B0 07 7F` 这类 CC
和 3 个 note_on，**一个 `0xC0` 都没有**。

两种可能：

1. **我们的 harness 少了初始化**（例如 0x0201 送音色、或某个 GS 初始化块）——
   驱动“能发但没被触发”；
2. **驱动本来就不发**（音色来自 GS 默认表或游戏自己的设置）——那缺 program 是“原样”。

**判定实验（30 秒）**：

1. 把 `hoot.ini` 的 `output_midi_device` 指到 loopMIDI；
2. 用 `py -3.12 build/_lead_midicap.py --seconds 30` 抓 HOOT 播一首 AMA4 的输出；
3. 在抓到的流里数 `0xC0–0xCF`：

| 结果 | 含义 | 下一步 |
|---|---|---|
| 有 `0xC0` | 我们漏了初始化 | 找 HOOT 里触发它的那一步（0x0201 / SysEx / 模式），修好可救 41 首 |
| 没有 `0xC0` | 驱动本来不发 | 不修，文档标注“音色由 GS 默认/游戏设置”，收口 |

**顺带**：这个 30 秒捕获同时验证了 HOOT 录制管线——它也是 7 个“装得上但不出声”包
（reno/momoko/papa/tlove12/yumecol/farce/hiragi）的兜底方案：HOOT 能播，就录它的输出，
不必把 1.72 仿真对。

### 三条纠正

1. **papa / farce / hiragi 不是死包**：`PAPA_00.GS` / `FARCE_00.GS` / `HIRAGI_00.GS` 是
   **4 字节的 `"STOP"` 哨兵**，真实曲目从 `01` 号往后（12–20 KB）。取错文件导致上一轮误判。
   **哨兵陷阱值得写进 checklist。**
2. **`AMA4_000.GMD` 与 `AMKH_000.GMD` 是同一份文件**（md5 `97363ddf0080`，3759 字节，逐字节相同）。
   之前的“时长/音符/tempo 完全相同、疑似串包”不是导出 bug——两个游戏共用一套数据。
3. **reno 的洪泛是短循环重放**：它的轨道是「`FE` 开头 + 短循环」的另一代格式：

```
轨0: FE FE FE FE ...                    ← 立刻停
轨1: EB 00 01 00 | EB 00 07 64 | EB 00 0A 40 | FE   ← 三条 CC 就循环
轨4: EB … | EC 00 0A 00 | 5B 08 08 64 …             ← 有 EC（乐器）
```

FMD9 把这种短循环当正常循环，每几 tick 重发一遍 CC（300 tick 就 7209 个 CC → 36 KB）；
1.71 把它当“停”，所以干净，但 1.71 丢 EC/EB → 乐器没了。

### 落地方式

- **FMD9 重导**：ama4、amakh、tlove12、momoko、yumecol、mug-r、hiragi、papa；
- **reno**：引擎用 1.71，再按数据里的 `EC`/`EB` 记录补 `program_change`/CC
  （`EC 00 <prog>` → ch=轨号、prog=p1；A 代发出的值已严格对上）；
- **farce**：FMD9 能读出 3331 个音符记录但 0 个 C0（EC 只有 43 个，其它包 175–421）。
  先抓一首 HOOT 对 `0xC0`：有 → 补；没有 → 按“本来就少切换乐器”结档。

**引擎选择不写死在导出器里**：做成探针表（包 → 引擎 → 采样结果），校验条件是
**load 成功 + 音符 > 0 + 最忙 tick 字节数合理**（第一轮误选 STOP 文件就是缺了这条）。

脚本：`build/_lead_fmd_engine.py`（矩阵生成）、`_lead_fmd_trio.py`（同数据/洪泛/头检查）。

### EC/EB 补事件（`synth_events`）

按 4 字节记录走表，`EC 00 <prog>` → `program_change(ch=轨号, prog=p1)`，
`EB 00 <cc> <val>` → CC；tick 用记录里的 `dur` 累加。
**时机很关键**：必须「预装载（0x0100）之后、0x0300 之前」取轨道表——播放后 `cur` 已经前进，
那时走表拿到的是半路数据（第一次实现就踩了这个，补了 0 个事件）。

**实测（`AMA4_000.GMD`）**：

| 导出方式 | program change |
|---|---|
| 1.71（旧产物） | 0 |
| 1.71 + 补事件 | **12 个**：`(0,ch0) (39,ch1) (39,ch2) (29,ch3–5) (56,ch6–8) (60,ch3–5)` |

数值与 FMD9 发出的 `C9 00 / C1 27 / …` 一致，所以补出来的事件是对的。

> **已撤回（2026-11-24，见 §31/§32）**：这条纠正的参照物是**坏掉的 1.71**（分派表在仿真里
> 从来不匹配，见 §31）。FMD9 实际能在 8000 tick 下跑完整曲，且**前 706 个音与 HOOT 逐个相同**；
> 所谓「FMD9 结构错位」「只到 16.2 s」都是假象。**ama4/amakh 应当换回 FMD9**，见 §32。

|---|---|---|

### 已知坑（新增）

- `.GS` 里 `00` 号常常是 4 字节 `"STOP"` 哨兵（papa/farce/hiragi），按文件名字典序取第一首会踩空；
  导出器的 `main()` 已经跳过，但自己写探针时别忘了。
- `max_ticks` 调大后，尾段会重放 16 声道 CC（`AMA4_000` 在 24000 tick 时出现 2.7 万个 CC），
  所以**必须保留原来的循环截断逻辑**，不能靠“跑够长”来省事。

### 更稳的落地：直接给已有 SMF 补事件（`_lead_fmd_patch.py`）

重跑仿真会连时长一起改（见上一条），而旧产物的时长是核对过的。所以对 **ama4 / amakh**
采用「不重跑仿真、只补事件」：

```

→ build/hootcap/fmd_synth/<HOOT 标题>/<曲>.mid
```

做法：用 1.71 预装载取**初始**轨道表 → `synth_events` 算出 (tick, 消息) →

**实测（23 + 18 首全部跑过）**：

- 时长**逐首不变**（174.7 s 还是 174.7 s）；
- 每首补 25–310 条事件，program 6–16 个；
- 一个坑：`synth_events` 走到轨道循环点之后会产生超出曲尾的 tick，直接插进去会把文件拉长

## 14. FMD5 的启动差异（为什么只有风雅セレクション受影响）

**只有 `fgsel1c` / `fgsel1m` 用 FMD5（`/e` 参数）**；其余已导出的包全部是
FMD9 / FMD13 / FMD.EXE。所以这个启动差异只落在风雅这两包。

在 harness 里跑 `MAZE00`（FMD5）：

```
0x0300 播放调用内只吐 6 字节
tick 0：  82 字节（全是 SysEx / program change / CC，**没有音符**）
tick 24： 第一个音（64+8 字节）
tick 47： 62+8
tick 72： 16+8
```

而 HOOT 的抓取里 **t=0 就是 10 个音**（36/42/40/64/57/76×4/40）。

结论：**FMD5 在播放调用里不吐音乐，要等第一个 tick 之后才开始**；HOOT 里（游戏真实运行时）
它是立刻开始的。对比 FMD9 的包（AMA2_000、CHAOS）与 HOOT 抓取斜率都是 **1.000**，没有这个偏移。

**修复方向**：

1. 查 FMD5 的播放初始化——`0x0300` 之后是否需要额外一次 `INT 0E` 或先读一次状态口；
2. 若确认是“前 24 tick 空转”，导出时把起点挪到第一个音符/第一个事件；
3. 验证：去掉偏移后与 HOOT 对齐，斜率应回到 1.000。

脚本：`build/_lead_maze_playstart.py`（逐 tick 字节数）、`_lead_maze_pkl.py`（抓取对齐）、
`_lead_maze_index.py`（按序号对齐）。

## 16. 长抓取的截断：自相似检测（给重导用）

**背景**：重跑 `ama4_000` 得到 298.5 s（旧冻结产物 174.7 s），音符数一致、时长不对——
说明循环截断没触发，跑满预算后全是重放尾巴。旧的 offset 回跳判据对多轨循环不灵
（OPENING 已经证明：多轨独立循环没有统一点）。

**判据（可照抄实现）**：

1. **只在 capture 跑满预算（capped）时才尝试截断**；idle 自然停下的不截；
2. 构建每 tick 的 token：把该 tick 的所有消息字节拼成字符串，再做整数哈希；
3. 候选周期 T：`12` 的倍数，范围 `[96, min(n//2, 16384)]`；
4. 对每个 T，比较 `tok[t] == tok[t+T]`（t ∈ [0, T)）；
   要求 **匹配率 ≥ 0.95** 且 **匹配 tick 数 ≥ max(600, T*0.5)**；
5. 取满足条件的**最小 T**；若全部不满足 → 不截，标记 `no-loop`；
6. 截断点 = 第一个满足条件的 `t0`（从 0 找起，允许 2% 不匹配）。

**性能**：token 先转成整数哈希数组，n=32000、候选约 1300 → 约 4×10⁷ 次整数比较，
几秒内可完成。

**验证**：截完抽 1 首与 HOOT 60 秒抓取对齐（斜率应 1.000）；至少确认时长落在
“首尾事件时间差”的合理范围，而不是预算上限。

参考实现：`build/_fmd_export.py` 的 `_tokens` / `find_loop`（已弃用的 O(n²) 版本，
思路可复用，性能要换成哈希）。

## 17. 引擎探针必须包含结构校验（2026-11-23）

现有探针只看**数量**：`load 成功 + 音符 ≥ 20 + 最忙 tick ≤ 400 字节`。
**反例**：FMD9 读 `AMA4_000.GMD` 不只是截断（静态 1740 tick → 16.2 s），
**轨道与事件也是错位的**——而音符数、program 数看起来都正常。
这种“数量对、结构错”的产物比没导出更糟，因为它看起来是对的。

**新增判据（每包先导 1 首）**：

1. 与 HOOT 抓取的前 60 秒对齐（loopMIDI 录制）；
2. **音高序列匹配率 ≥ 80%**；
3. **斜率 1.000 ± 0.02**；
4. **残差中位 < 20 ms**。

三条全过才允许批量；不过就换引擎（用包自带驱动）或改走 HOOT 录制。

**结论修订**：§15 的“FMD9 是参考引擎”应限缩为
**“FMD9 是事件最全的引擎，仅对通过结构校验的包成立”**。
FMD9 不能被当作通用读取器——ama4/amakh 已证明它会错位。

## 18. §16/§17 的实现与实测（2026-11-23 深夜）

**实现**：`build/_lead_fmd_engine.py`

- `selfsim_cut()` 按 §16 的判据实现：只在没有旧式「确认循环」时启用；token = 每 tick 全部
  消息字节的 blake2b 哈希；T 为 12 的倍数、`[96, min(n//2, 16384)]`；匹配率 ≥ 0.95 且
  匹配数 ≥ `max(600, T*0.5)`；取最小 T；`t0` 用前缀和滑窗找第一个允许 2% 不匹配的位置。
- **截断点取 `t0 + T`**（前奏 + 一遍）——§16 写的是「第一个 t0」，但 t0 只是周期段的起点，
  直接当截点会把前奏连同整段都砍掉；这与旧 `find_loop` 的语义（jump 点 = 一遍结束）一致。
- `structure()`：从事件流算 音符数 / 用到几个通道 / 音高种类 / C0 / CC / 音符密度 /
  峰谷比，并按「通道 <3、音高 <8、密度 <0.3 或 >80/s、峰/中位 >4 倍」出 flags。
- `agreement()`：两个引擎在**同一份数据**上的条数比 + 音高直方图余弦；
  只有两边都 ≥20 音时才比较（一边不出声时无法交叉校验，不能当证据）。

**实测探针（600 tick，两引擎）**：

```
        两引擎一致度：条数比 0.21 / 音高余弦 0.86  ⚠ 结构不一致 → 别用 FMD9
```

## 20. AMA4_015 逐项对照 + FUGAM_98.COM 反汇编（2026-11-23）

拿到 HOOT 抓取（`D:\music\AMA4_015_HOOT.mid`）后，和导出逐项比：

| 项 | HOOT | 导出 |
|---|---|---|
| 拍数 | 146.8（73.4 s） | **666.6（333.3 s）**，4.54× |
| 音符 | 2696 | 14733 |
| 音高序列相似度 | — | **0.008** |
| 导出 [0,A) 与 [A,2A) 相似度 | — | 0.022（**不是循环重复**） |
| ch1/ch2/ch3/ch4/ch5 | 374/299/163/336/162 | 144/457/43/72/**0** |
| ch9 鼓 | 718 音、9 种音高 | **141 音、只有 36/41/45** |
| program | (9,16)(1,33)(2,30)… | (0,16)(1,33)(2,30)…（值同，第一个落在 ch0） |

结论：**不是“缺乐器”，也不是循环没截**——事件流本身就是另一套东西。
鼓轨只出 3 个音高、ch5 整条轨消失，说明轨道/通道和记录解码都错了。

**FUGAM_98.COM（228 字节）完整反汇编**：

```
0101 out 0x7E8,0x80         ; 音源板模式口（读的是 0x7E0）
010E AH=4A 缩小内存
011B call 0x1A5             ; 扫 2E F6 06 xx xx 01 75 → 把驱动 [0x1E] 清 0
011E AH=48 BX=0x1000        ; 申请 64 KB（不是 16 KB）
0133 AH=3F BX=5 读 stdin    ; 音色数据 → AX=0201 送音色（DS:DX = 缓冲区，不是文件名！）
0152 AH=25 AL=07F          ; 挂 INT 7F = 键盘回调
0161 AX=9801 int 18         ; 等键
0168 回调: in al,0x7E0      ; 0 → 读 stdin 歌 → AX=0100 → AX=0300；2 → AX=01FF
```

**关键结论**：壳**没有任何“轨道→通道分配”的初始化**，就是 0201/0100/0300/01FF 四次调用
＋清 `[0x1E]`。所以 §19 的「游戏启动时做了我们没复刻的初始化」**不成立**——HOOT 跑的调用链
和我们一样。

差别只可能在两处：

1. **喂数据的方式**：壳先 `AH=4A`、再 `AH=48 BX=0x1000`（64 KB），用 `AH=3F` 从 stdin 读进
   这块内存，然后 `DS:DX = 缓冲段`（DX=段、SI=0）。我们则是把歌写到固定的 `0x5000`、
   再把 `cs:[7]` 强行改成 `0x4000`——驱动看到的“自己那块内存”与 HOOT 不同。
2. **板子模型**：我们 `in 0xE0D0` 永远返回 `0xFD`、`in 0xE0D2` 只按 ack/tick 给位，
   没有 FIFO/状态语义。驱动如果按状态位决定“这一拍推进几条记录”，模型不对就会错位。

**下一步（按优先级）**：

1. 在 harness 里**照抄壳的流程**：`AH=4A`→`AH=48 0x1000`→把歌写进那块内存→`DS:DX=buf, SI=0`
   →不要手改 `cs:[7]`；0201 也改成「DS:DX=数据」而不是文件名；
2. 用已经拿到的 `AMA4_015_HOOT.mid` 当回归标尺（音高序列相似度、拍数、ch9 音高集合）；
3. 若还不对，再动板子模型（0xE0D0 状态/FIFO 语义）。

## 21. 内存流程修复无效 → AMA4/AMAKH 与 6 包记 blocked（2026-11-23 收尾）

## 22. 结案（2026-11-23）

**决定**：B 代（`FMD.EXE` 1.5x–1.72 / `FMD5` / `FMD7`）**停止逆向，结案归档**。
理由不是"没时间再试一下"，而是三个独立证据链都指向同一结论：**我们不知道 HOOT 到底做了什么，
而每追一个假设都要一轮 HOOT 录制 + 逐事件对齐 + 反汇编**——代价与收益完全不成比例。

**证据摘要**（细节见 §9–§21）：

| 假设 | 实验结果 | 判定 |
|---|---|---|
| 数据不对 | 同一份 `.GMD/.GS` 换 FMD9 能出完整事件（program/CC/弯音/SysEx） | 数据没问题 |
| build 有 API 差异 | 4857 与 4969 引擎逐字节相同（1.72/1.71） | 排除 |
| 内存流程不对 | 三版 harness（旧 / 修 `AH=48` / 壳式 64 KB + 不 poke `[7]`）输出逐字节相同 | 排除 |
| 壳里有轨道分配 | `FUGAM_98.COM` 全反汇编：只有 0201/0100/0300/01FF + 清 `[0x1E]` | 排除 |
| 只是循环没截 | 导出 [0,A) 与 [A,2A) 相似度 0.022，不是重复 | 排除 |
| 只是缺乐器 | 补了 program 后仍是另一场演奏（AMA4_015 相似度 0.008） | 排除 |
| 板子状态/FIFO 语义 | 只能到此为止：我们 1 次读 = 1 条记录，HOOT 事件密度是我们的 2.3 倍 | **未验证的剩余假设** |

**定性**：这个驱动的难度**远高于本工程其它驱动**——它把「时间轴、事件流、轨道分配」都放在
板子固件行为里，而我们只仿了协议表面（`0xE0D0`/`0xE0D2` 的握手），没有仿它的缓冲/状态机。
在没有公开规格的前提下，继续逆向**不现实**。

**结案后的口径**：

- 交付：A 代 70 个文件（Amaranth II GS 36 + MT-32 34，斜率 1.000）；
- unverified：`build/hootcap/fmd/` 其余 99 个文件 + `fmd_synth/` 41 首，**不要当成果引用**；
- 回归标尺保留：`D:\music\AMA4_015_HOOT.mid`（音高相似度 / 拍数 / ch9 音高集合 / 每 1/48 拍事件数）；
- 若要重启：先做板子 FIFO/状态模型，再跑 §17 的三项判据；否则改走 HOOT 录制兜底。

**归档脚本**（`build/_lead_fmd_*.py`，都不进仓库）：引擎表/探针 `_lead_fmd_engine.py`、
SMF 补事件 `_lead_fmd_patch.py`、壳式流程 `_lead_fmd_shell.py`、自相似截断
`selfsim_cut()`、以及 §19 的对照脚本 `_lead_fmd_ama15c.py`。

## 23. 参考实现：MAME / DOSBox-X 里的 PC-98 MPU-401（2026-11-24 查证）

问的是「真机板子到底怎么工作」。三家源码的结论（NP2 系列源码在 GitHub，本机取不到；NP21W 的
发布包只走 Google Drive，见文末）：

### MAME：板子 = 通用 `mpu401_device` + 真固件

- `src/devices/bus/pc98_cbus/mpu_pc98.cpp`：C-Bus 卡只是把 `0xe0d0-0xe0d3` 映射到
  `mpu401_device`（`umask16(0x00ff)`），DIP-SW 决定 base（默认 `0xe0d0`）与 IRQ。
- 核心 `src/devices/machine/mpu401.cpp` **不是行为模型，而是跑 Roland 6801 固件**
  （ROM `roland__6801v0b55p__15179222.bin`）＋ 门阵列寄存器：
  - `mpu_r(0)`=数据、`mpu_r(1)`=状态；读数据口会清 IRQ 并置 `STAT_RX_EMPTY(0x80)`；
  - 6801 写来一个字节 → 清 `0x80` 并拉 IRQ；
  - `STAT_TX_FULL(0x40)`：主机写了字节、6801 还没取走；
  - `STAT_CMD_PORT(0x01)`：上一字节写的是命令口。
  ⇒ **bit7=0 表示「有字节可取」，bit6=1 表示「忙」**——和 FMD 驱动 `0x713`/`0x690` 两个
  轮询循环（等 bit7=0 读、等 bit6=0 写）完全一致。

### DOSBox-X：intelligent mode 的完整行为模型（这份最好用）

`src/hardware/mpu401.cpp`（Debian 源 `dosbox-x 2026.10.01`）：

```c
#define MPU401_QUEUE 32
MSG_MPU_CLOCK 0xfd        /* 发给主机的时钟字节就是 0xFD */
uint8_t ret=0x3f;         /* bit6、bit7 清 */
if (mpu.state.cmd_pending) ret|=0x40;
if (!mpu.queue_used)       ret|=0x80;   /* 队列空才置 bit7 */
```

- **PC-98 端口**：`base=0xE0D0`（数据）、`base+2=0xE0D2`（状态/命令），与我们的假设一致；
  默认 IRQ **6**（注释：「This is said to be the MIDI card's factory default on PC-98」）。
- **寄存器**：32 字节队列；`0xE0D2` 写入 = 命令；`0xE0D0` 写入 = 数据/命令参数。
- **命令集**（与 FMD 的 init 逐条对得上）：`$FF` reset、`$3F` UART、`$C2-$C8` timebase
  (48/72/96/120/144/168/192)、`$E0` tempo（clamp 4..250）、`$E1` relative tempo（`$40`=1.0）、
  `$E7` → `cth_rate = val>>2`、`$94` clock-to-host off、`$95` on、`$B8/$B9` clear counters、
  `$AC/$AD` 版本/修订。
- **时钟（关键）**：intelligent 模式下板子自己跑一个 timer：

  ```
  period_ms = 60000 / (tempo × timebase × tempo_rel/0x40)
  134 BPM × $C2(48) × 1.0  →  60000/(134×48) = 9.33 ms  →  107.2 次/秒
  ```

  每次事件里 `cth_counter++`，到 `cth_rate` 就 `req_mask |= 1<<13`，EOI 时
  `QueueByte(0xf0+13)` = **0xFD**。`$E7 04` → `cth_rate=1` → **每个事件一个 0xFD**。
  107 次/秒 = 134×48/60 —— 正好等于「每拍 48 tick、134 BPM」的 tick 速率。

### 我们的板子模型（`build/_fmd_play3.py`）缺什么

| 真机（DOSBox-X/MAME） | 我们 |
|---|---|
| timer 按 tempo×timebase 自己出 0xFD | 我们手动调 `INT 0E`，**节奏由我们定** |
| 32 字节队列 + bit7/bit6 状态 | 一次 `in` 一个字节，状态只在 ack/tick 之间切 |
| IRQ（PC-98 默认 IRQ 6）拉/清 | 没有 IRQ，直接 `emu_start` 进 ISR |
| `$E7` → cth_rate 分频 | 未实现 |

**这条大概就是「事件密度只有 HOOT 的 1/2.3、时长 4.5×」的来源**：驱动 ISR 里对中断做了
计数分频（`cs:[0x13]=6` 之类），而我们是「一次 `INT 0E` = 一个音乐 tick」，喂的时钟频率
和板子给的不是一个量级。**可测**：把 harness 的 `INT 0E` 调用频率改成
`tempo×timebase/60`（134/48 → 107 Hz），看 `AMA4_015` 的时长是否从 333 s 掉到 ~73 s、
鼓轨音高是否补齐。这一条不需要改驱动，只改 harness 的喂法。

### NP21W：源码到手（rev106，`cbus/mpu98ii.c`）

板子是 **MPU-PC98II**，源码在 `cbus/mpu98ii.c`（CP932，已转 UTF-8 到
`build/_fmd_tmp/np2_mpu98ii.c`）：

```c
MIDIIN_AVAIL = 0x80,  MIDIOUT_BUSY = 0x40,  MPUMSG_HCLK = 0xFD,  MPUMSG_ACK = 0xFE;
mpu98.port = 0xc0d0 | ((opt & 0xf0) << 6);   /* DIP-SW 选 base，0x80 → 0xE0D0 */
mpuirqnum[4] = {3, 5, 6, 12};                /* IRQ 由配置位选 */
```

- **状态口 0xE0D2**（`mpu98ii_i2`）：`ret = status`；**收队列空时才置 `0x80`**
  （所以 bit7=0 才是「有字节可取」）；写缓冲超阈值时置 `0x40`（BUSY）。
  数据口 0xE0D0 读走一个字节后，若还有数据就保持 IRQ，否则 `pic_resetirq()`。
- **时钟**（`midiint` / `makeintclock`）：

  ```c
  l = tempo * 2 * reltempo / 0x40;
  if (!FSKRESO) l *= inttimebase;           /* inttimebase = ($C2..$C8) & 0x0F */
  stepclock = pccore.realclock * 5 / l;     /* 每个内部时钟的间隔 */
  ```

  每个 `stepclock` 到期：若 `CLKTOHOST` 置位，按 `hclk_step[]` 分频，减到 0 就
  `setrecvdata(0xFD)` 并拉 IRQ。`$E7 n` → `quarter = n>>2`（0 视作 64），
  `hclk_step[i] = quarter + hclk_step1[n&3][i]`；**`$E7 04` → 每个内部时钟一个 0xFD**。
  速率 = `l / 5`，134 BPM + `$C2` → **107.2 次/秒**（= 134×48/60）。
- **写侧节流**：`xferclock = realclock / 3125`（3125 B/s，MIDI 31250bps ÷ 10bit）；
  `MPU98_WRITEBUFFER = 2048`，写得比这快就置 BUSY，排空后清；
  命令之后还有 `midicmdwait(realclock/10000)` 的强制 BUSY。

**和我们模型的差异**（`build/_fmd_play3.py` 是桩）：

| 真机 | 我们 |
|---|---|
| timer 按 `stepclock` 自己出 0xFD（`$E7` 分频） | 手动调 `INT 0E`，节奏由我们定 |
| 收队列；读空后返回**上一个字节** | 每次读都返回 0xFD |
| IRQ 拉/清（3/5/6/12 可选） | 无 IRQ 线，直接进 ISR |
| 写节流 3125 B/s → BUSY | 永远接受 |

### 重要更正：那份 HOOT 抓取是**片段**，不是完整曲子

`D:\music\AMA4_015_HOOT.mid` 最后几条消息是还在响的 `note_on`，紧接着 `end_of_track`，
**没有 all-notes-off** —— 它是「录 N 秒后截断」的样本。
所以 §19 / §21 里「333 s vs 73.4 s = 4.5 倍」**不能当证据**：我们的导出是整曲，
抓取只是开头 73 秒。结构对比必须在**同一时间窗**里做（按秒对齐 + 偏移搜索），
不能再拿总时长比。

## 26. HOOT 的板子模型（读侧，IDA 实测）（2026-11-24）

从 HOOT.exe 的 I/O 分发器 `sub_5A8590` 与设备函数 `sub_73E0D0` 反编译得到：

```
设备对象：this+56 (0x38)
FIFO    ：128 字节 @ +1520 (0x5F0)
FIFO 计数：+1512 (0x5E8)
FIFO 头  ：+1516 (0x5EC)    （0..0x7F 循环）
pending ：+1477 (0x5C5)     （单字节，优先于 FIFO）
状态字节：+1485 (0x5CD)
最后读出：+1448 (0x5A8)
```

| 操作 | 行为 |
|---|---|
| 读 `0xE0D0` | 先取 pending（取后清零）；否则从 FIFO 弹出（头+1 & 0x7F、计数-1）；都空时调回调（`+3828`）并返回上次读出的值 |
| 读 `0xE0D2` | bit `0x40` = FIFO 非空（有数据可读）；bit `0x80` = 空；`0x40` 每次读后被清（边沿语义） |

`0xE0D0`/`0xE0D2` 的 IN 分发在 `sub_5A8590`：
`0xE0D0 → sub_73E0D0(obj, 0)`、`0xE0D2 → sub_73E0D0(obj, 1)`。
OUT 方向没有直接的 `cmp 0xE0D0` 命中，推测走端口页表——但**导出不需要 HOOT 的写队列**，
我们抓的就是驱动写出的字节。

**推论**：HOOT 的驱动在一次中断里可以**连续读多个 tick**（FIFO 里积了几个就处理几个），
而我们的 harness 是“一次中断一个 `0xFD`”——这正是事件密度 1.64 vs 3.85 的来源。
下一步：在 harness 里实现上述 FIFO/状态，按 tick 率塞 `0xFD`，让驱动连续读空后再对比 AMA4_015。

> **2026-11-25 已实现**：`build/mpu401.py` 收队列/状态位/FIFO 已落地；A 代逐字节回归通过，
> B 代 `[bx+4]` 已过 0x104、鼓 6 种/密度比 0.42。结论与证据见
> `BOARD-SPEC.md` §五、§十一。

**参考实现**：MAME 有 `src/devices/sound/mpu_pc98.cpp`（Roland MPU-PC98）与 `mpu401.cpp`，
实现的就是这块板（timebase/tempo/clock-to-host/FIFO/状态位）。**读它对照行为可以，
但不要整段抄**——MAME 是 GPL，抄进仓库会带来许可问题；按行为重写即可。

### 28.4 DE/DD/DF 的真实语义：GS SysEx 参数块，不是鼓音符

> **更正（2026-11-24）**：下面引的字节行（`0CA8 mov cl,0x10 / call 0xD14` … `0D58 'A'`）
> 是 **+0x100** 之后的地址，实际是 `0x0DA8` 那段例程。真正的 `0x0CA8` 是：
> `E8 C7 FD`（`call 0x0A72`：板命令 `$DF` → 命令口 `0xE0D2`，再 `F0` → 数据口 `0xE0D0`）
> → `B0 41`（'A'）→ `8A 47 2E`（dev）→ `8A 47 2F`（model）→ `B0 12` → GS 地址 `[bx+0x2C]`
> → 数据 → `F7`。**语义结论不变**，只是地址要按 §30.3 读。

`DE → 0x0CA8` 展开（★ 更正后的地址，原稿这一整段是 `0x0DA8` 那段例程）：

```
0CA8  call 0x0A72       ; $DF → 命令口 0xE0D2（长消息），F0 → 数据口 0xE0D0
0CAB  B0 41            ; 'A'（Roland）
      mov al,[bx+0x2E] ; dev      ← DF 存的
      mov al,[bx+0x2F] ; model    ← DF 存的
      B0 12            ; GS
      B2 00
      8B 47 2C         ; GS 地址字 ← DD 存的
      8A C4            ; 取高字节
      ...              ; p1/p2 作数据，最后 F7 (EOX)
```

原稿那份（`0CA8 mov cl,0x10 / call 0xD14 / 0D58 'A' 10 41 16 12`）是 `0x0DA8` 处的另一个例程，
**不用于 DE**；但「发 `$DF` 长消息 + `F0`」这个动作两处都有，语义判断不受影响。

- **`DF`**：把两个字节存进轨道项 `[bx+0x2E]`/`[bx+0x2F]`（设备/型号）；
- **`DD`**：把一个字存进 `[bx+0x2C]`（GS 地址）；
- **`DE`**：用上面三者 + 自己的 p1/p2，发一条 GS 参数写 SysEx。

**结论：DD/DE/DF 是「GS 参数块」三件套（音色/鼓组/部件配置），不产生 note。**
§25 里「DE 的唯一副作用是 cur+4 + 清 entry+0x28」应撤回：`+0x28` 是记录时长字节。

> 通道表和 loader 副本区，**没有一字节落在 `0x0D49` 的循环体或 `0x0CA8` 的处理器上**。详见 §30.2。

同一份内存（0x10000–0x16000）在 **0100 之后**和 **播放 40 tick 之后**相比，**51 字节不同**，
包括轨道表区（0x0FE3 起，活镜像偏移 = CS `0x0EE3`）和 0x202C 的一整块。更要命的是：

- **播放中**活镜像里「`cmp al,[si]` + `je`」的查表循环在 **0x0E49**；
- 但跟踪里实际命中的是 **0x0D49** 那个版本，且 0x0D44 附近的活字节和我们 dump 的文件**完全不同**。

也就是说：驱动有**两份/多份代码副本**（装载期 vs 运行期），我们手里的 `drv_ama4_98.bin`
不是驱动真正执行的那份。**所有基于它的静态反汇编结论都不可靠。**

> **上面这句已撤回（2026-11-24）**：只有一个查表循环在 `CS:0x0D49`；`0x0E49` 只是活镜像
> 基址低 0x100 造成的记法。`drv_ama4_98.bin` 的**代码区**与活镜像逐字节相同
> （循环体、命令表、DE 处理器、INT 0E 入口全部吻合）；两批 dump 的其余差异落在
> **18 条轨道表**（装载时由 `0x0100` 建出来）、通道表和 loader 副本区。§30.3 有分组。

### 29.4 DE 为什么静默（当前证据）

逐次打断点（`si/al/[DS:SI]`）（★ 地址口径不明，仅存档，别当证据）：

```
si=0EA2 al=DE [si]=EE → si=0EA5 (EC) → 0EA8 (EB) → 0EAB (E2)
si=0EAE al=DE [si]=DE   ← 本该命中
si=0EB1 … 0EB7 (FF) → si=0EB8 → 跳到 FF 处理器（空动作）
```

在 `0x0D4B` 的 `je` 上 AL 与 `[SI]` 都是 0xDE，条件跳转却没跳；但随后抓现场字节发现
**0x0D4B 当时根本不在指令边界上**（那里是 `cmp es:[bp+2],0x6f` 的半条指令）。
所以「跳转没生效」是**反汇编错位**造成的假象，不是真的。

**结论：查表循环的位置在运行期会变，必须先抓活镜像再反汇编。** 这一轮没能收敛。

> **已否（2026-11-24）**：位置没变，变的是 dump 基址。本节那次跟踪的 hook 地址低了 0x100，
> 所以「走完整张表、停到 FF」这个观察不能当证据。按 §30.3 的字节，`AL=0xDE` 到 `0x0D49`
> **必然**命中 `0x0EAE` 的 DE 表项；`0x0CA8` 一进去就会写命令口 `$DF` 和数据口 `F0`。
> 所以现在的矛盾是「代码要求至少吐两个字节，实测零字节」，而不是「表漏了 DE」。

## 30. 地址基准更正：§28/§29 的 0x100 是从哪来的（2026-11-24 复核）

   被当成同一口径。§29.1 / §29.3 / §29.4 的结论全靠这个，所以一起崩。
2. **清单整体低 0x100**——§28.2 那张地址表、§28.4 引的字节行，是另一处 origin 问题

### 30.2 由此作废的四条

1. **「同一个查表循环在 `0x0D49` 与 `0x0E49` 各有一份副本」（§29.3、§29.7）**：假。
   只有一个循环在 `CS:0x0D49`；`0x0E49` 是同一地址的活镜像记法。
2. **§28.2 那张清单整体低 0x100**。正确：`0x083E` 起 `mov es,[bx] / mov bp,[bx+4] / mov ax,es:[bp]
   / mov [bx+0x28],ah`；`0x08C5` 是 `cmp al,0xF0`；`0x08E9` 是 `mov si,0x0EA2`；
   `0x08EC` 是 `call 0x0D49`（**不是** `0xC49`）。
3. **「驱动在运行中改写自己的代码区、文件镜像 ≠ 执行镜像」（§29.3）**：假。
   文件镜像 vs 活镜像（对齐后）共 538 字节不同，分组如下，**没有一字节落在本轮关心的
   循环体与 DE 处理器上**：

   | 范围（CS） | 字节 | 是什么 |
   |---|---|---|
   | `0x0008`–`0x0026` | 5 | 入口区之前的 loader 状态（未解释） |
   | `0x0EBC`–`0x121C` | 189 | **18 条轨道表**（步长 `0x30`，`0x0100` 装载时建出来） |
   | `0x178D`–`0x18C1` | 298 | 通道表（`0x177C` 起）及邻接数据（未解释） |
   | `0x1F32`–`0x1F5F` | 46 | loader 副本/栈区 |

   合计 5+189+298+46 = **538**，无其它散点。
   对照：循环体 `0x0D49`–`0x0D58` 差异 **0** 字节；DE 处理器 `0x0CA8`–`0x0CD0` 差异 **0** 字节。
4. **「§29.4 查表循环的位置在运行期会变」**：假。变的是 dump 基址，不是代码。
   另外两份 live 快照之间的 51 字节差异也全是状态与标志：`[bx+0x28]` 时长（`01`→`09/0A/0B…`）、
   `[bx+4]` 记录指针（`2C`→`3C`）、轨 0 的 `[0x27]`（`FF 01`→`00 00`）、`0x0024`、`0x0336`、
   `0x179E/0x17A1`、`0x1F2C`–`0x1F55`。

### 30.3 正确的 DE 分派链（CS 偏移）

记录读取器是 `0x083E`，由每 tick 的轨道循环在 `0x07E9` 调 `call 0x083E`
（那时 `[bx+0x28]` 时长字节刚减到 0）：

```
08DB  F6 47 27 01   test byte [bx+0x27],1      ; 轨启用位
08DF  74 D7         je  08B8                   ; ← 闸门 A：吞掉记录，表都不查
08E1  8A 67 29      mov ah,[bx+0x29]           ; 通道字节（0x90|n）
08E4  80 FC 8F      cmp ah,0x8F
08E7  74 CF         je  08B8                   ; ← 闸门 B：通道未分配
08E9  BE A2 0E      mov si,0x0EA2
08EC  E8 5A 04      call 0x0D49                ; 全驱动唯一的调用点

0D49  3A 04         cmp al,[si]
0D4B  74 08         je  0D55
0D4D  83 C6 03      add si,3
0D50  80 3C FF      cmp byte [si],0xFF
0D53  75 F4         jne 0D49
0D55  46            inc si
0D56  FF 24         jmp word [si]

0EA2  EE | 76 0C   → 0x0C76
0EA5  EC | DA 0B   → 0x0BDA
0EA8  EB | 38 0C   → 0x0C38
0EAB  E2 | F4 0B   → 0x0BF4
0EAE  DE | A8 0C   → 0x0CA8   ← DE 走这里
0EB1  DD | A0 0C   → 0x0CA0
0EB4  DF | 95 0C   → 0x0C95
0EB7  FF | BA 0E   → 0x0EBA   （C3 90 = ret，「空动作」）

0CA8  E8 C7 FD      call 0x0A72   ; → 板命令 $DF（命令口 0xE0D2）+ F0（数据口 0xE0D0）
0CAB  B0 41 E8 ..   mov al,'A'  ; dev  ; model ; 12 ; GS 地址 [bx+0x2C] ; 数据 ; F7
```

- `DD` → `0x0CA0`：`mov ax,es:[bp+2]; mov [bx+0x2C],ax; ret`（GS 地址字）
- `DF` → `0x0C95`：`mov ax,es:[bp+2]; mov [bx+0x2E],al; mov [bx+0x2F],ah; ret`（设备/型号）
- `DE` → `0x0CA8`：用上面三者发 GS 参数写 SysEx

**关键推论：表本身不可能漏掉 DE。** `AL=0xDE` 走到 `0x0D49`，`0x0EAE` 的 DE 表项必然被 `je` 命中
→ `jmp [0x0EAF]` → `0x0CA8`；而 `0x0CA8` 第一条就是 `call 0x0A72`，里面先写命令口（`$DF`）
再写数据口（`F0`）。**一旦进入处理器，端口字节数必变。** 实测 159→159，所以只能是
「没进去」或「进去后吐不出」。

### 30.4 所以只剩两条路

> **已解（2026-11-24，见 §31）**：两条都不是。真正的原因在**表里的那条 `cmp`**——
> 它在仿真里根本不置 ZF，于是 DE 从没进过表项。本节保留作过程记录。

| 候选 | 机制 | 判据 |
|---|---|---|
| **表之前被闸门吞掉** | `0x08DB`/`0x08DF`（轨启用位）或 `0x08E4`/`0x08E7`（`[bx+0x29]==0x8F`）；命中就 `bp+=4` 吃掉记录，表根本不查 | `0x08EC` 不命中 |
| **进了处理器但吐不出** | `$DF` 是板命令（long message），而 `_lead_fmd_board.py` 里 `$DF`/`F0` 一族 **0 处命中**；`0x0684`–`0x0689` 死等 ACK `0xFE` | `0x0CA8` 命中但零字节 |

顺带否掉一个旧怀疑：**`DS ≠ CS` 不成立**。INT 0E 入口 `0x06B3` 就是 `push cs / pop ds`，
查表时 DS=CS（§28.5 的「下一步」可以划掉）。

已确认的这个 hook 地址是对的：`0x0CA8`（DE 表项确实指它）。所以「DE 处理器一次都没命中」
比其它几条证据干净——但它和上面的静态推理正面冲突，这是现在唯一要解的矛盾。

### 30.5 下一轮的 hook 清单（别再用 §28.5 的旧地址）

在 `de.zip` 夹具上挂四处，**每处都用 CS:IP 和线性 `0x10100+off` 各挂一次**，
先分清「挂错地址空间」和「根本没跑到」：

| 地址（CS） | 意义 | 打印 |
|---|---|---|
| `0x083E` | 进记录读取器 | `bx, es, bp, es:[bp]` |
| `0x08EC` | 进表前一刻（闸门已过） | `al, bx, [bx+0x27..0x2A]` |
| `0x0D49` | 循环头 | `al, si, ds, [si]` |
| `0x0CA8` | DE 处理器入口 | `al, bx, [bx+0x2C..0x2F]` |

## 31. 结案：DE 静默 = 查表 `cmp` 在仿真里不置 ZF（2026-11-24）

按 §30.5 的四点 hook 跑了 `ama4_171` + `AMA4_015`（`build/_lead_fmd_dehook.py`），结论是
**一条指令的仿真异常**，不是驱动行为，也不是 §30.4 那两条候选。

### 31.1 证据

在 `CS:0x0D4B`（`je 0D55`）上打断点，`AL == [DS:SI]` 的那一次现场是：

```
EAX=000099DE  ESI=00000EAE  DS=1010  [DS:0EAE]=DE
CS:IP=1010:0D4B   指令字节 3A 04 74 08   ZF=0   ← 相等却没置 ZF
```

统计（9000 tick 的短跑同样成立）：`al=DE` 在 `si=0EAE` 命中 24 次，**ZF=1 一次都没有**；
所有命令（`EB/EC/DD/DE/DF`）的循环都走到 `si=0EB7`（FF 终止项）才停，**一个表项都没匹配上**。
所以每条 ≥0x80 的记录都落到 `FF → 0x0EBA`（`C3 90` = ret，空动作）→ 静默。

**对照实验**：在 `0x0D4B` 上把「`AL == [DS:SI]` 却没置 ZF」补成 `ZF=1`（等价于 `cmp` 本来的语义），
同一份数据立刻正常：

| | 不补 | 补 ZF |
|---|---|---|
| DE 处理器 `0x0CA8` 命中 | **0** | 24（30 tick）/ 493（全曲） |
| 数据口字节 | 139 | 457 |
| 发出的 GS SysEx | 无 | `F0 41 10 16 12 7F 00 00 00 01 F7`（GS Reset） |

最小复现（`build/_tmp_cmp_repro*.py` 已删）表明纯 unicorn 16 位跑 `3A 04 / 74 08` 是**对的**
（DS 非零段基址也对），所以这是本项目仿真环境里的特定异常，成因未定位；
**但补丁的语义与指令本意一致**，可以当仿真修复用。

### 31.2 这条解释了一大片旧结论

- **「1.71 把 `EC`/`EB`/`EE` 全丢」**（§22、§13）——不是驱动丢，是仿真丢；补丁后 `EC` 出 program change 335 个、`EB` 出 CC、`EE` 出驱动命令。
- **ama4/amakh 导出「没有 program change」**（§22、§10）——同一个原因；不是音源初始化问题。
- **DE 静默**——同一个原因。
- `DD`/`DF` 之前也全被丢，所以 GS 地址/设备/型号从来没设过。

## 33. `.MD` 音色上传（AX=0201）是死路（2026-11-24）

**动机**：壳的流程里 `0x0100` 之前有一步 `AX=0201` 送音色，每首歌配一个 `.MD`
（`AMA4_015.MD` 1082 字节）。我们的 harness **一直跳过**（`_lead_fmd_shell.py` 注释写着
「GS 包跳过」）。怀疑 42 就丢在这一步。

**驱动侧的 0201**（`0x03D0` 起）：

```
03D0  8E 1E 07 00   mov ds,cs:[7]        ; 用驱动自己的缓冲段
03D4  B4 3F / CD 21 int 21 AH=3F         ; 把 .MD 读进缓冲
03D9  9C / B4 3E / CD 15 / 9D / 72 0C    ; pushf / mov ah,3E / int 15 / popf / jc
```

`INT 15h/AH=3Eh` 是个**能力探测**：成功 → `call 0x0D58` 处理音色；失败 → `AL=0xFF; STC`。

**我们原来直接崩在这里**（UcError @ `1010:03DE`）。本轮在 `_lead_fmd_tone.py` 里加了
`hook_int15()`：拦 `CD 15`，按 PC-98 惯例把 CF 写回压在栈上的 FLAGS。

结果：

| | 之前 | 加了 hook |
|---|---|---|
| `0201` 返回 | UcError | **`0x0`** |
| 多发事件 | — | 一条 SysEx `F0 41 10 16 12 10 00 00 04 00` |
| 音符流 | 987 音 | **逐字节相同**，鼓还是 36/41/45 |

**结论：`.MD` 这条路不通。** 送了也不改变音符/鼓的映射。

**旁证**：`INT 15h AH=3Eh` 在两家模拟器里都**不存在**——NP21W 的
`np21w-src-rev106/bios/` 下没有 `bios15.c`，`bios.c` 里也没有 INT 15 分派；
DOSBox-X 的 `src/ints/bios.cpp`（555 KB）`INT15_Handler` 只有
`0x00–0x06 / 0x24 / 0x4F / 0x83–0x8A / 0x90 / 0x91 / 0xC0 / 0xC2–0xC4 / E801 / E820 / APM`，
`pc98_lio.cpp` 里也搜不到。所以它多半是**探测常驻扩展**（某个 TSR），真机上大概率返回 CF=1、
驱动走失败分支——`.MD` 在 HOOT 里很可能也没被真正消费。

## 34. 42 的真正位置：鼓轨的播放指针不前进（2026-11-24）

### 34.1 记录 → 发声 的对照表

|---|---|---|
| 0（鼓） | **60** | 36×20, 41×20, 45×20 |

| 2 | 273 | 40×172, 49×52, 50×40, 52×9 |
| 4 | 40 | 64×40 |

- **首字节 `2A`（鼓 42）的记录，进 `0x0A8C` 的次数 = 0**。不是音高被改写，是整条没走到。
- 鼓轨 40 秒只发 60 个音（HOOT 同期约 400），反复 36/41/45。

### 34.2 鼓轨卡在开头三段

轨 0 数据（`0x4000:0xE0` 起）：

```
0E0  24 00 01 6A | 29 00 01 6A | 2D 0C 01 6A      ← 36/41/45
0EC  24 00 01 6A | 29 00 01 6A | 2D 0C 01 6A      ← 再来一遍
0F8  3C 18 00 00 | 3C 90 00 00                     ← 非音符（p1/p2 = 0，被跳过）
100  F8 03 00 00                                   ← 循环结束，次数 3
104  FD 00 00 00                                   ← 回跳
108  …
128  30 08 01 6A …                                 ← 48 从这里才开始
660  2A 08 01 6A …                                 ← 42 在很后面
```

发声时间戳 `t=2228 / 2240 / 2420 / 2432 …`，每 ~192 tick 重放一遍那三个音。

### 34.3 循环机件是好的，坏的是指针交接

`F8/F9/FD` 的实现（反汇编）：

```
F9 → 0x0B3F  压栈：深度 [bx+0x2B]（最多 5 层）；栈项在 bx+6+6n：
              [si]=计数, [si+2]=bp, [si+4]=[bx+2]
F8 → 0x0B6A  dh=ah（次数）；计数 +1，达到次数就弹层并回跳
FD/FC → 0x0CE7：si=[bx+2] → 扫描 → [bx+4]=bp、[bx+2]=si；失败则停轨
```

探针（`_lead_fmd_loopprobe.py`，4000 tick，轨 0）：

```
命中： F9=4  F8=9  FD=45  send=60
运行后： [bx+2]=0220   [bx+4]=00FC   depth=2   [bx+6]=1   [bx+0xC]=2
```

- **三个都在跑**，循环栈确实建在轨道项里（深度 2，两层计数 1 和 2）
- **但取记录用的 `[bx+4]` 全程钉在 `0x00D4`**，只有 `[bx+2]` 在往前扫
  （`002C→0030→0034…`，每 72 tick +4）

**即：扫描指针在走，播放指针不动。** 这是鼓轨只发 36/41/45 的机制。

### 34.4 下一步（很具体，别再另找方向）

把 hook 从 F8/F9/FD 换到**记录读取器 `0x083E` 入口**，每条记录打
`[bx+2] / [bx+4] / es:[bp]` 四字节，看**哪一条之后 `[bx+4]` 不再前进**。
重点核对 `0x0CE7` 里这两句的先后与条件：

```
0CEE  89 6F 04   mov [bx+4],bp     ; 把扫描结果交回播放指针
0CF1  89 77 02   mov [bx+2],si
```

怀疑点：`FD/FC` 扫描完没有把结果交回 `[bx+4]`，或 `mov [bx+4],bp` 走的分支被跳过。

**已知的坑（本轮踩过两次）**：hook 地址必须落在指令边界上——`0x0B6D` 看起来像 F8 入口，
实际 `E9 5F 02` 从 `0x0908` 算出来是 **`0x0B6A`**；挂错 3 字节就永远是 0 命中。

### 34.5 `0x0CE7` 实测：它其实写了 `[bx+4]`，是别处又改回去（2026-11-24 收尾）

`build/_lead_fmd_fdprobe.py`，钩 `0x0CE7`（进）与 `0x0CF4`（`mov [bx+4],bp` / `mov [bx+2],si`
两句都执行完之后）：

```
 tag tick  al  [2]    [4]    bp
 in    72  FD  0030   00D4   00D4
 out   72  DE  0034   0030   0030      ← 交回： [bx+4] := 旧 [bx+2]
 in   144  FD  0034   00D4   00D4      ← 又变回 00D4
 out  144  DE  0038   0034   0034
```

**结论修正**：`FD` 处理里 `mov [bx+4],bp` 是**执行了的**，指针确实被交回一次；
但到下一次 `FD` 时 `[bx+4]` 又变回 **`0xD4`** —— 所以问题不在 `0x0CE7`，而在**两次 FD 之间**
有代码把当前偏移重置成 `0xD4`。`0xD4` 正是轨 0 进入循环前的位置（`EC 24 10 00` 之后）。
下一步该钩 **写 `[bx+4]` 的所有点**（`0x08C1 mov [bx+4],bp`、`0x0CEE mov [bx+4],bp`，
以及 F8 的 `mov [bx+2],ax` 之后若有交接），看谁最后写的 `0xD4`。

### 34.7 谁写 `0xD4`：查清了，是正常播放，不是神秘重置（2026-11-24）

`build/_lead_fmd_whowrites.py`：对 `CS:0x0EC0`（轨 0 的 `[bx+4]`）挂内存写钩子，300 tick：

```
写 [bx+4] 共 23 次
  1010:08C1  +EC0 sz2  17 次  值 0038×3, 0050×5, 00C4×5, 00D4×4
  1010:0CEE  +EC0 sz2   5 次  值 002C/0030/0034/0038/003C 各 1
  1010:0226  +EC0 sz2   1 次  值 002C（装载期）
```

时间线（每轮一样）：

```
t=156  08C1 = 0050      ← 正常播放推进
t=164  08C1 = 00C4
t=180  08C1 = 00D4      ← 走完 0x38..0xD4 这一区间
t=216  0CEE = 0038      ← FD 跳回 0x38
t=216  08C1 = 0050      ← 同一 tick 里又推进到 0x50
```

**结论**：`0xD4` 是 `0x08C1`（取记录后的 `mov [bx+4],bp`）写的，属于**正常播放推进**，
不是什么东西在“重置”。真正的现象是：**轨 0 在 `0x38`–`0xD4` 之间无限循环**，
每轮末尾由 `FD`（`0x0CEE`）跳回 `0x38`。

也就是说：`F8 03` 的计数**没有终止这个循环**（或者 `FD` 根本不看循环栈）。
下一步只查一件事：`F8`（`0x0B6A`）弹层之后，`FD`（`0x0CEE`）跳的还是不是 `0x38`——
若不是，说明弹层后 `[bx+2]` 没被更新，`FD` 用的是旧目标。

### 34.8 裸跑复核 + 三个字段的写点（2026-11-24 收尾二）

**§31 的裸跑复核**（`build/_lead_fmd_bare.py`，同样 4000 tick）：

| | SysEx | CC | program | pitch | 音符 |
|---|---|---|---|---|---|
| 裸跑（零 hook） | **1** | 32 | **0** | 0 | 1972 |
| 挂 ZF 补丁 | 494 | 447 | 120 | 111 | 1972 |

- 「命令类记录不发」这个**现象**不依赖 hook（裸跑只有 1 条 SysEx），§31 的**结论**成立；
- 但「ZF 没置位」这个**机制解释**仍来自带 hook 的观测——按 REVIEW-CHECKLIST 记为
  **待裸验**（要证伪它，得用非 hook 手段，例如直接改驱动镜像里的 `74 08`）；
- 音符数在两种情况下**完全相同**（1972），补丁不扰动音符路径。

**三个字段的写点**（`build/_lead_fmd_writers3.py`，只用内存写钩子，2600 tick）：

```
[bx+0x2B] 深度   IP=0B49（F9 压栈）  仅 2 次：值 1、2
[bx+4] 当前偏移  IP=08C1（正常播放） 100 次；IP=0CEE（FD 跳转）43 次
[bx+2] 循环起点  IP=0CF1（FD 扫描）  43 次；IP=0B95（F8 恢复）**仅 1 次**
```

**判读**：深度**只被写过两次（1、2），从来没有被减过**；`F8` 的恢复路径（`0x0B95 mov [bx+2],ax`）
**全程只跑了 1 次**。也就是说 —— `F8` 每次都走了「计数已完成 / dh=0」而跳过恢复，
`[bx+2]` 于是被 `FD` 的扫描结果一路推着走（43 次），播放偏移跟着它，永远回不到 0x100 之后的段落。

**下一步**：在 `0x0B8F`（dh=0 分支入口）与 `0x0B86`（计数读取）各打一次
**只读**观测是没用的（会切 TB）；改成在 `0x0B82` 之前用内存写钩子读不到寄存器。
可行的干净做法：**把 `0x0B82` 的 `0A F6`（or dh,dh）改成 `90 90`**，让 F8 无条件走计数分支，
看鼓轨是否立刻走出循环、42 是否出现——这是在驱动镜像上打补丁，不是观测，不污染语义。

### 34.9 结案：鼓轨锁死是 `FD` 回跳造成的（2026-11-24 收尾三）

用**镜像补丁**（不挂 hook）做两个可证伪实验，4000 tick：

| 实验 | 鼓音高 | 命中 |
|---|---|---|
| 基线 | 36/41/45 | 27 |
| `0x0B82` NOP（F8 的 `or dh,dh`） | 36/41/45 | 27 → **假设证伪** |
| **`0x08F7`：`je 0x091C` → `jmp 0x08B8`**（FD/FC 变空操作） | **36/38/41/42/45/46/48/49/51 = 9 种** | **388** |

- **`FD` 是唯一开关。** 跳过 FD/FC 分支后鼓轨立刻完整：9 种音高、388 次（HOOT 73 s 是 718 次，
  我们 4000 tick ≈ 41 s，量级对得上），**42 出现了**。
- 去掉音符路径两道「p1/p2 == 0 就跳过」（`0x0895`/`0x089A` NOP）**结果完全相同**，
  说明 42 不是被那两道门滤掉的——就是被 FD 的回跳挡在循环外。
- 轨 0 的 `[bx+4]` 在 FD 空操作版里最大值 `0x07A4`，早已越过 `0x660`（42 所在），
  证明「不是到不了，是被跳回去了」。

**结论**：`FD` 在 `FMD.md:202` 的定义是「板子节拍标记」——它是**同步用**的，
不该用来改播放指针；我们的 `0x0CE7` 却把它当跳转执行，于是每轮把鼓轨拉回开头。

**对导出的直接做法**：导出 1.71 时把 `0x08F7` 的 `74 23` 改成 `EB BF`（FD/FC → 空操作）。
这是镜像补丁，不依赖 hook，也不改数据；`0x0B82` 那条可以彻底忘掉。

**注意**：这条只解决「鼓轨循环」。§32 记的**轨道→通道映射**（ch5 整条 0、ch3 翻倍、
ch8/ch10 各 584）**仍未解决**，是另一件事。

### 34.10 「混了其他轨 / 音高不对」= 导出里含重放（2026-11-24 收尾四）

§34.9 之后导出的成品里，ch9 除了鼓还混进了 28–35 这些旋律音高，而且计数与 ch1 的低音部分
**逐项相同**。查了时间关系：

```
ch9 低音起点 47.88 s：28 28 28 28 28 33 35 33 …
                      Δ = 47.13 s —— 整条流被重放，落到鼓通道上
```

混轨）分别对应三条修复**：

| 修复 | 位置 | 作用 |
|---|---|---|
| ZF 补丁 | `0x0D4B` | ≥0x80 的记录能进分派表（program/CC/SysEx） |
| FD 补丁 | `0x08F7` `74 23→EB BF` | 鼓轨不被回跳锁死（9 种音高，含 42） |
| **循环截断** | **~4700 tick ≈ 47.13 s** | 不把重放那一遍算进产物（ch9 归零污染） |

`_lead_fmd_fixexport.py` 已加 `--cut`（默认 4700）。

**评分要按同一时间窗**：HOOT 那 73.4 s 抓取本身跨了 1.5 遍，拿我们的 47.9 s 整段去对它
会得到偏低的 0.357；按 47.1 s 对齐窗口是 **0.406**。**以后对比必须先把窗口截到同一长度。**

参考值（2026-11-24 末）：截到 47.9 s → 1690 音；同上窗口对齐后音高相似度 0.41，
9 条通道齐全、鼓 9 种。离 0.8 还差一档，剩下的是每通道的条数配比（ch1/ch4 偏少、ch7 偏多）。

### 34.11 残余「混轨」的真身：轨 0 跑过头（2026-11-24 收尾五）

「混入其他轨」在 47.9 s 窗口里还剩这些：

| 通道 | 我们 | HOOT | 差 | 多出的音高 |
|---|---|---|---|---|
| ch3 | 136 | 74 | +62 | 55:2, 59:2, 52:1 |
| ch5 | 135 | 73 | +62 | 55:2, 59:2, 52:1（**与 ch3 逐项相同**） |
| ch7 | 105 | 44 | +61 | **40:37** |
| ch8 | 181 | 246 | −65 | — |

看起来像「一条流被发到三个通道」，但**逐轨采样后不成立**：
`build/_lead_fmd_pertrack.py` 逐 tick 读 18 条轨的 `[bx+4]`，5000 tick 内**回跳 0 次**，
所有轨单调前进——说明 FD 补丁把循环机制整个拆掉了。

真正的原因是**轨 0 跑过头**。轨 0 自己的数据直方图（§34 那次扫的）：

```
轨0 音符记录：28:54  29:5  30:7  31:6  33:5  34:4  35:6  36:165 …
ch9 里的低音：28:54  29:5  30:7  31:6  33:5  34:4  35:6            ← 逐项相同
```

这些记录在轨 0 数据 `0x400` 之后的区段，**真实驱动走不到**（会在那之前绕回）；
`0x08F7` 一 NOP，轨 0 就一路播到终点，把它们全发了出来。所以 47.13 s 的
「重放」也不是第二遍，是**轨 0 走出了自己的周期**。

**收口两方案**：

- **A（先用）**：FD 补丁 + 在轨 0 跑过头之前截断（`--cut 4700`）。前 47 s 的 ch9 是干净的
  9 种鼓音高，可以直接交付；代价是曲子只有一遍。
- **B（更正确）**：把 `0x08F7` 从「FD 完全空操作」改成「**只跳一次**」——在 `0x0CE7`
  成功跳转后把该轨标记完成，下次 FD 直接走 `0x08B8`。语义接近 `FMD.md:230–233` 的
  「多段独立循环，截到最长轨的第一周期」，但需要重验判据，留作下一轮。

**方法论备注**：这一条之所以能定性，靠的是「逐 tick 读内存、不挂 hook」+「拿轨 0 自己的
数据直方图对账」。挂 code hook 那几轮全是噪声（见 内部审查清单（不随库发布））。

### 34.12 待做：B 方案「FD 只跳一次」（本轮未落地）

**目标**：每条轨的 `FD` 只跳一次，之后按数据自然跑到 `0xFE` 收尾——这样就不需要
`--cut` 硬截，A 方案里「轨 0 跑过头」的多余内容也不会出现。

**现成机制**：`0x0CE7` 的 `CF=1` 在调用点 `0x091F jc 0x0924` 处表示「停这条轨」
（`mov byte [bx+0x27],0`），正好是需要的“结束”语义：

```
第一次 FD  → 0x0CE7 返回 CF=0 → 正常回跳一次
之后的 FD  → 让它返回 CF=1 → 0x0924 停轨
```

**状态位**：`[bx+0x26]`（现存只用 bit7，bit0–6 闲置）取 bit6 记「已跳过」。

**卡点**：`0x0CE7` 前后（`0x0CE0`–`0x0D30`）没有空位插这 6–8 字节，得先找 code cave
（候选：镜像尾部 `0x1F00` 之后的 0x00 区；`0x0EBC` 不行，那是轨道表起点），
把 `0x0CE7` 头两字节改成 `JMP cave`，cave 里放「测 bit6 → 置/清 CF」+ 原逻辑。

**验收**：鼓仍 9 种（含 42）、ch8 从 181 回补到 ~246（HOOT 同窗）、总时长自然收敛到
最长轨第一周期。**止损：两轮不成，停在 A 方案交付，B 记为「已知未采用」。**

**当前交付物**：`build/_fmd_tmp/fix_patched_AMA4_015.mid`（A 方案，47.9 s / 1690 音）。

### 34.6 老文档里的现成参考（省了我半轮）

同一份格式在库里早就写过，`FMD.md` 第四节：

- **轨道项布局**（`FMD.md:199`）：`+0 数据段 / +2 循环起点 / +4 当前偏移 / +0x27 启用位 /

**`0xFD` 的口径（2026-11-24 最终）**：

- **FMD 的 `0xFD` 语义上是「节拍同步标记」**（`FMD.md:202` 的原定义是对的）；
- 但它的**实现**（`0x0CE7`）会写播放指针 `[bx+4]`，所以行为上像跳转；
- **导出时按空操作处理**（同步由板子模型提供）——§34.9 的实测：跳过 FD/FC 分支后
  鼓轨才完整、9 种音高全出、42 出现；
- **MMD 的 `0xFD` 才是「定位/跳转」**（`MMD/docs/BUILDS.md:49`、`MMD.md:212`），
  两边不要互套（`MMD.md:216` 已有反向提醒）。

一句话：**FMD 的 FD 是同步语义、跳转实现；MMD 的 FD 是跳转语义。**

## 37. 根因：播放期 code hook 让 `cmp` 丢 CF（2026-11-25 收口）

### 37.1 `0x0CFC` 读出来的东西

`0x0CE7` 是 FD/FC 的处理入口：

```
si = [bx+2]              ; 旧循环锚点
call 0x0CFC
[bx+4] = bp              ; 新 cur = FC 链解析后的跳转目标
[bx+2] = si              ; 新锚点 = 向后扫描到的控制字节
```

`0x0CFC`：

```
call 0x0D09              ; 从 [bx+2] 起跟 $FC 链（最多 10 层）→ bp
cmp al, $FE
je  结束（CF=1）
call 0x0D28              ; 从 si 起按 4 字节记录向后扫
clc / ret
```

`0x0D28` 的扫描规则：

| 记录首字节 | 动作 |
|---|---|
| `< $FC`（普通记录） | `si += 4`，继续 |
| `$FD` | `si += 4`，越过它 |
| `$FC` | 停在它（新锚点） |
| `$FE` / `$FF` | 停在它（`$FE` 由 `0x0CFC` 判为终止） |

所以新锚点 = 旧锚点到下一个控制字节的距离。HOOT 长录实测正步长
`+0x14 ~ +0xC4`（5–50 条记录），我们原来固定 `+4`。

### 37.2 为什么旧仿真只 +4

`0xD28` 里的 `cmp al,0xFC` 后面是 `jae 0xD45` / `jb 0xD33`。在我们的驱动 `Uc` 里，
`cmp` 之后 `FLAGS` 一直是 `0x16`（CF=0），没有物化：
`0xD31` 的 `jae` 于是把每个普通记录都当成控制字节，`si += 4` 直接返回。

**不是驱动、不是数据、不是板子**——是 `_fmd_export.install_pack` 在播放期持续挂着：

- `L.hook_all_ints()` 的 10 个 `CD xx` 精确 code hook；
- 覆盖 `0x10100–0x16000` 的**范围** code hook。

Unicorn 2 在这种持续 code hook 下会让 `cmp` 的 CF 不更新；同一段 `3C FC` 在干净 Uc 里
`flags=0x87`，在驱动 Uc 里 `cmp` 前后都是 `0x16`。这是 内部审查清单（不随库发布）
「范围 hook 污染相邻指令语义」的最强实证：被污染的是整条 `cmp` 分支链。

### 37.3 修法与结果

修法（`build/_fmd_export.py`、`build/_fmd_play3.py`）：

1. 安装阶段保留 INT21 范围 hook 过 DOS；`emu_start` 返回后立刻 `u.hook_del(h_cd)`；
2. 播放阶段不再调用 `L.hook_all_ints()`；
3. 播放期只保留 `LOOP_END` 一个精确 hook（`on_loop`）。

结果：


## 38. 导出 tempo：`$E0` + `$E1` → timed map（2026-11-25）

### 38.1 现象

`TLOVE_01` 导出只有 `120 BPM @0s`；WIN 版是 `120 @0s, 112 @0.771s`，
前 400 音斜率 0.9333（我们快 6.7%）。引擎日志里：

```
tick 0   $E0 0x78   (120 BPM)
tick 30  $E2 0x00
tick 30  $E1 0x3C   (120 × 60/64 = 112 BPM)
```

旧 `to_smf` 只认 `$E0`，把 `$E1` 相对速度漏掉了——所以整首按 120 走。

### 38.2 修法

`build/_fmd_export.py` 新增 `tempo_map(seq, default)`：

- `$E0 <bpm>`：基准 BPM，并把 rel 重置为 `$40`；
- `$E1 <rel>`：有效 BPM = `base × rel / $40`，按 NP2 的 `curtempo` 取整；
- 每次变化按 tick 落一个 `set_tempo`，不是只在开头写一个；
- `to_smf` 不再使用单一的 `cap['bpm']`，改用完整 timed map。

### 38.3 验收

| 曲 | 修复前 | 修复后 | 基准 |
|---|---|---|---|
| `TLOVE_01` 前 400 音斜率 | 0.9333 | **1.00000** | WIN 版 M001.MID |
| `AMA4_015` 音高相似度 | 0.999 | **0.999** | HOOT |

全批 237 首中 **189 首有效 BPM ≠120**（含 `TLOVE` 这类 `$E1` 变速）；
本轮已全部用新 tempo map 重导到 `build/hootcap/fmd_b/`。
`$E2`（graduation）仍未建模，遇到再单独立项。

> `AMA4_000` 的「700 s / 111.9 s」是 `max_ticks=12000` 造成的空转；它实际是
> **13.86 s / 337 音**的短曲（HOOT 也只有十几秒）。改用 1600 tick 后 8 s 导完。


## 39. 导出结束判定：fe / loop / cap（2026-11-25）

按优先级，每首必须给出明确 `end`：

1. **`fe`**：所有非空轨的 `[bx+4]` 都指向 `$FE` 记录 → 立即停，不管 tick 跑到哪；
2. **`loop`**：所有活跃轨的 `(seg, loop, cur, en)` 同时回到同型状态 → 取一轮；
3. **`cap`**：跑到 `max_ticks` → 打 `WARNING: ... end=cap`，**不算 ok**，报表标
   `status=truncated`。

短曲（`dur<30s`）若走到 `cap`，额外标 `SHORT_CAP`——说明出口没生效，不能靠加 timeout。
批处理结果：237 ok（fe 18 / loop 219）、11 cap、7 曲目 skipped；
`AMA4_000` 是 `fe` 的 13.77 s 短曲，不再是 timeout。
