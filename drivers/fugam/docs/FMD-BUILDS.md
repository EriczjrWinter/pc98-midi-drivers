# FMD.EXE 各 build 的实际差异（2026-11-23 复查）

> **结论先行**：`4857` 与 `4969` 是**同一个驱动的相邻版本**（FMD **1.72** / **1.71**），
> **音乐引擎、AH 分派表、`0x0100` 装载路径逐字节相同**。
> 所以「入口地址不同 → API 不同 → 解决它可解锁 7 个包」这条推论不成立；
> `1010:0056` 属于另一个 build（`image2_98` 的 5248 字节，`[0x17]=8 KB`），不是 4969。
>
> 本文替代 [`docs/HANDOFF.md`](../../../docs/HANDOFF.md) 与 [`FMD.md`](FMD.md) 里同名那一节
> （两份都写着「4969 build 是 1010:0056」，是记串了）。

## 0. 版本表（实测）

装法见第 7 节；`INT D3` / `INT 0E` / `[0x17]` 都是**安装完成后**从仿真内存里读出来的。

| 包 | FMD.EXE | md5 前 8 | 内部版本串 | INT D3 | INT 0E | `[0x17]` | 装后 `[0x1E]` | 导出 |
|---|---|---|---|---|---|---|---|---|
| reno / momoko / papa / tlove12 / yumecol / farce / hiragi | 4857 | `699a8a5e` | **Version 1.72** | `1010:003F` | `1010:06A1` | 16 KB | 0 | ❌ |
| ama4 / amakh | 4969 | `991dbe8d` | **Version 1.71** | `1010:003F` | `1010:06A1` | 16 KB | 0 | ✅（缺 program change，见 §5） |
| mug-r | 5365 | `de5bf6f7` | Version 1.61 | `1010:003C` | `1010:0610` | 16 KB | 0 | ❌ |
| venus | 4601 | `f06ac87f` | Version 1.51 | `1010:003B` | `1010:05CF` | 16 KB | **1** | ✅（15 首） |
| image2 | 5248 | `3dfd0981` | 无版本串 | **`1010:0056`** | `1010:05CB` | **8 KB** | 0 | ✅（14 首） |

**4857 与 4969 的 `INT D3` / `INT 0E` 完全一致**——这一条本身就否掉了「入口地址不同」。

## 1. 文件层：差的 112 字节全在 MZ 头

| | 4857（1.72） | 4969（1.71） |
|---|---|---|
| MZ 头 | 32 字节（最小头，`e_cparhdr=2`） | 144 字节（`e_cparhdr=9`） |
| 头里的招牌 | 无 | `FUGA MIDI Driver Version 1.71   1994/ 7/ 6 11:03 Copyright(C)1994 by FUGA System  All rights reserved.` |
| 代码 payload | **4825 字节** | **4825 字节** |
| 入口 | `010F:0000` | `010F:0000` |
| SS:SP | `01CB:02F0` | `01CB:02F0` |

- 两者 `e_crlc=0`（没有重定位项），所以**重定位表那一段是空的**；4969 的链接器正好把版本
  招牌填进了这段空位（头偏移 `0x1E` 起）。4857 用最小头，招牌被裁掉。
- **payload 一样大**，所以「4969 − 4857 = 112 字节」= 头差，不是代码变多/变少。
  （`e_cp=10` 两边相同，只有 `e_cblp` 249 → 361。）

### 打包壳

两版都是同一套 Zortech/SLR **LZSS 自解压壳**，stub 在 body `0x10F0`–`0x12D9`（489 字节），
**逐字节相同**：

```
010F:10F0  xchg ax,ax / jmp 10FF        ; 入口
           dx = ds+0x10                  ; 目的段
           复制 0xF5 个 word 到 ss:0      ; 把自己搬到内存顶部
           retf → 副本 +0x31（0x1121）    ; 再往下搬，腾出 unpack 空间
           ...                          ; 0x1150 起是 LZSS 解码器（0x1000 窗口、16 位标志字）
           最后 mov ss,cs:[9] / mov sp,cs:[7] / ljmp cs:[0xB]
```

- 打包层 4825 字节里 **3786 相同（78%）**，第一处差异在 body `0x483`。
- 差异集中在 body `0xCC4`–`0x10E2`，解压后对应**安装器 + 帮助文本**（见第 2 节）。

## 2. 解压后（常驻镜像）：引擎相同，只差安装器和文本

用 `build/_fmd_dumpdrv.py <pack>` 装一次、dump `1010:0000` 起的 `0x6000` 字节：

| 口径 | 4857 vs 4969 |
|---|---|
| 常驻镜像大小 | 24576 / 24576 |
| 相同字节 | **23597（96%）** |
| 差异 | **38 段 / 979 字节**，全部落在下面三处 |

| 位置 | 4857（1.72） | 4969（1.71） | 说明 |
|---|---|---|---|
| `0x1BA1` | 多 3 字节 `83 C3 0E`（`add bx, 0x0E`） | 无 | 安装器在 `INT 21/AH=48` 前把申请量**加 14 段（224 字节）** |
| `0x1C3D`–`0x1F88` | `Version 1.72`、`-?` 帮助日文措辞改动 | `Version 1.71`、旧措辞 | 因此 `0x574`/`0x5C1` 两条消息指针也差 3 |
| `0x20E8` / `0x2162` / `0x2164` | `0F` / `B8` / `DF` | `00` / `B9` / `E3` | 落在**运行时被改写的 stub 副本/栈区**（该区非零字节从 `0x20A0` 起就是搬移后的 loader），不是常驻代码；未解明，见 §6 |

**相同（逐字节）的部分包括**：AH 分派表（`0x73` 起 18 项）、`0x0100` 装载、18 轨建表、
事件解释、板命令序列、`INT 0E` 处理。所以「4857 与 4969 的引擎行为差异」在代码里不存在。

**唯一的功能差异**是那条 `add bx,0x0E`：1.72 在安装时比 1.71 多要 224 字节 DOS 内存
（`[0x17]` 两边都是 16 KB → `16×64 = 1024` 段，1.72 是 1038 段）。

## 3. 顺带确认的驱动语义（两版相同）

安装后 `INT D3` 入口：

```
003F  EB 02                  jmp 0043
0043  2E F6 06 1E 00 01      test byte cs:[0x1E], 1     ← 壳 FUGAM_98.COM 扫的就是这条
0049  75 27                  jne 0072                   → 0072 = iret（API 全静默）
004B  ... 60 8C CB 8E DB 8E C3
0054  2E C6 06 19 00 00      mov byte cs:[0x19], 0
005A  33 DB 8A DC            mov bl, ah                 ← 分派索引是 AH
005E  03 DB                  add bx, bx
0060  8D 9F 73 00            lea bx, [bx + 0x73]        ← 分派表在 0x73
0064  FF 17                  call word [bx]
0066  61                     popaw
0067  2E A0 19 00 / 2E 8A 26 1A 00  返回码取自 cs:[0x19]/cs:[0x1A]
0072  CF                     iret
```

- **分派索引是 AH，不是 AL**（`8A DC` = `mov bl,ah`）。表在 `0x73`，共 **18 项（AH=0x00–0x11）**，
  第 `0x12` 项起读到的是数据（`0xBA27`、`0xE0D2`…）。旧文档写的「AL 分派表 0–0x1A」应改成
  「**AH** 分派表 0x00–0x11」。
- 表（词偏移，两版相同）：`0095 00D4 03A6 02BE 0337 03F1 03FC 0422 042F 044C 0453 046A 04A6 04CB 0505 0537 0561 10B9`
  → 对应 `AX=0100`（装歌）、`AX=0201`（送音色）、`AX=0300`（播）、`AX=01FF`（停）等。
- 「已装过」判定：`INT 21/AH=35` 取 D3 向量后 `cmp word es:[3], 0x270B`——`0x270B` 就是
  `D3:0041` 那两个字节 `0B 27`。命中则跳到 `0x0569`（「已常驻」分支，不再挂一次）。

### 3.1 A 代 / B 代的实际分界（`INT D3` 入口形态）

| build | INT D3 | 入口测 `[0x1E]` | 分派表 | 返回码变量 |
|---|---|---|---|---|
| FMD9 4774（ama2s） | `0056` | 无 | —（未查） | — |
| FMD13 5301（ama2m） | `0056` | 无 | —（未查） | — |
| FMD7 4998（marple） | `0054` | 无 | —（未查） | — |
| image2 5248 | `0056` | **无** | `0x88` | `[0x18]` |
| venus 4601（1.51） | `003B` | **无** | `0x69` | `[0x19]` |
| mug-r 5365（1.61） | `003C` | 有（`0x40`） | —（未查） | — |
| ama4/amakh 4969（1.71） | `003F` | 有（`0x43`） | `0x73` | `[0x19]` |
| reno 等 4857（1.72） | `003F` | 有（`0x43`） | `0x73` | `[0x19]` |

- **`0056` 是 A 代的入口形态**（FMD9 / FMD13 / image2 都是它），B 代是 `003B`–`003F`。
  所以旧文「4969 build 是 `1010:0056`」不仅数值错，连代次都张冠李戴了。
- `[0x1E]` 门只出现在 **003C / 003F** 这几个 build 上（mug-r、1.71、1.72）；
  venus（1.51）和 image2 的入口根本**不测**它——所以壳的 patch 对这两版是空操作。
  实测 venus 装完 `[0x1E]=1` 仍能导出，正好对上。
- `build/_fmd_export.py: shell_patch()` 只扫入口后 96 字节，因此不会误伤 venus 里
  `0x4FE` 那个**巧合命中**的同字节序列（那里不是门）。

### 命令行参数解析（`0x1A12`–`0x1B66`，两版逐字节相同）

前缀 `-` 或 `/` 等价，逐字符：

| 参数 | 效果 |
|---|---|
| `-?` | 打印帮助后 `exit(2)` |
| `-I n` / `-i n` | 取参数（`sub '0'`，必须 ≤2），从 `0x2B` 的**3 字节记录表**（`n*3`）取三项 → `cs:[0x28]/[0x29]/[0x2A]`；原字符另存 `cs:[0x1E62]` |
| `-O` / `-o` | `cs:[0x20] = 1` |
| `-G` / `-g` | `cs:[0x1F] = 1` |
| `-#` | **`cs:[0x1E] = 1`**（`/#` 同一个分支；这就是「D3 直接 iret」的开关） |
| `-R` / `-r` | `cs:[0x0B] = 1`，并**立刻跳到安装/常驻**（不继续解析后面的参数） |
| `-<1~3 位十进制>` | 十进制 → `cs:[0x17]`＝**申请内存 KB**（安装时 `bx = [0x17]<<6` 段） |

`cs:[0x29]` 在 `0x057A`–`0x0583` 被 OR 进端口 `0x02` 的读值再写回（板子设置），
`[0x28]/[0x2A]` 的具体用途还没定。**结论：`-<n>` 和 `-In` 不只是「让 D3 挂不挂」，
它们改的是内存大小与板子配置**——排查「装上了没声」时先看命令行。

## 4. 更正 HANDOFF / FMD.md 的两条

1. **「4969 build 是 `1010:0056`」是记串了。** 实测 4969（ama4/amakh）＝`1010:003F`，
   与 4857 相同；`0056` 属于 `image2_98` 的 5248 字节 build（无版本串、`[0x17]=8 KB`）。
   （`HANDOFF.md` 里 FMD9 安装小节的「`INT D3=1010:0056`、`INT 0E=1010:05BF`」是**A 代**的数，
   实测 ama2s_98 就是这个值——所以更可能是这两组数被抄混了。）
2. **「解决 4857 与 4969 的 API 差异可一次解锁 7 个包」不成立**：引擎逐字节相同，
   1.71 能跑的曲子 1.72 没理由跑不了（反之亦然）。剩下的差异在**数据 / 命令行参数 / 安装环境**。

## 5. 新线索：失败组的共同点可能是数据集，不是驱动

| 组 | 数据文件 | 驱动 |
|---|---|---|
| ❌ reno / momoko / papa / tlove12 / yumecol / farce / hiragi | **`.GS` + `.FM`**（16/16、11/10、12/12…） | 4857（1.72） |
| ❌ mug-r | `.GS` + `.FM`（9/9） | 5365（1.61） |
| ✅ ama4 / amakh | `.GMD` + `.MD` | 4969（1.71） |
| ✅ venus | **`.GS` + `.FM`**（19/19） | 4601（1.51） |
| ✅ image2 | `.GS` + `.FM`（14/14） | 5248 |

- 失败组清一色 `.GS`，但 **`.GS` 不是必然失败**（venus 1.51、image2 都能导）。
- 另有一处已记录的疑点：ama4/amakh 导出**没有 program change**（不是导出器丢的，驱动没发），
  说明「B 代」这条线上还有 **音色/音源初始化** 的问题，和 build 早晚不是同一件事。
- 数据头的粗查也有信号：`AMA2_000.GMD` 在 `+0x0E` 是轨道名 `"DRUMS"`，而
  `AMA4_000.GMD` / `RENO_000.GS` 同位置是空格——**头布局可能不止一种**，
  「`+0x02` 起 16 条 4 字节记录」这句描述未必对所有包成立（详见 `FMD.md` 第四节，待复核）。

## 8. 下一步（把「为什么失败」从驱动身上挪开）

1. **决定性交叉实验**：reno 的数据 + 1.71 驱动、ama4 的数据 + 1.72 驱动，各跑 300–1000 tick，
   看「轨道表建出几轨 / `0x90` 类字节数 / `0xC0` 类字节数」。

2. 若确认是数据：拿 `RENO_000.GS` 与 `VENUS_000.GS`（都是 `.GS`）逐字段比头，

3. 记录调参矩阵：对失败包试 `-8`/`-16`/`-32`（内存 KB）与 `-I0/1/2`（板子配置），

## 9. 2026-11-23 晚补测

### 9.1 交叉实验（决定性）

把驱动和数据交叉，各跑 300 tick：

| 数据 × 驱动 | 轨道表 | 300 tick 输出 | 0x90 音符 | 结论 |
|---|---|---|---|---|
| reno `RENO_000.GS` × **1.71**（4969） | 18 | 246 字节 | **82** | 正常 |
| ama4 `AMA4_000.GMD` × **1.72**（4857） | 18 | 431 字节 | **0** | 坏 |

**同一份 reno 数据换 1.71 就响；同一份 ama4 数据换 1.72 就不响。**
→ 失败与**数据无关**，是 1.72 这个 build 在本环境下跑不起来。
（复现：`python build/_lead_fmd_cross.py`）

### 9.2 AH=48 内存分配：不是根因

1.72 安装时 `AH=48` 请求 **1038 段**（1.71 是 1024 段，正是那 +14 段）。
给 `Board._dos` 补上 bump 分配器（heap 从 0x2000 起，`para+0x10`）后重跑：

```
heap 用完: 0x241e
bytes=68409  0x90=0  0xC0=0
```

**和没补一样**。所以“多要 14 段内存”不是失败原因。
（复现：`python build/_lead_fmd_alloc_fix.py`）

### 9.3 常驻镜像差异：两处可疑的“自改写”字节

979 字节差异里大多数是版本串偏移引起的跳转位移，剩下两处仍在运行时 loader 副本区：

```
0x20E8: 1.71 = 0f 85 00 00      1.72 = 00 85 00 00
0x2162: 1.71 = b8 14 df 10      1.72 = b9 14 e3 10
```

形态像**安装时自我改写的常量**（段地址 / 近跳转目标）。1.72 装得上、轨道表也建得出，
但播放不出音符，最可能就是这份运行时副本没被打对补丁。

**下一步**：hook 写入 `0x121E8` / `0x12262`（段 0x1010 + 上述偏移），对比两个 build
的写入序列与写入值；再顺藤找到补丁代码的输入（是否依赖 `AH=48` 返回段 / PSP 字段）。

（复现：`python build/_lead_fmd_imgdiff.py`）

## 10. AMA4/AMAKH 缺 program：先做 30 秒判定

**现象**：`ama4_98` / `amakh_98` 已导出 41 首，但**没有 program change**。直接盯驱动
（1.71），`AMA4_000.GMD` 前 400 tick 的数据口只有 `B0 79 00` / `B0 07 7F` 这类 CC
和 3 个 note_on，**一个 `0xC0` 都没有**。

两种可能：

1. **我们的 harness 少了初始化**（例如 0x0201 送音色、或某个 GS 初始化块）——
   驱动“能发但没被触发”；
2. **驱动本来就不发**（音色来自 GS 默认表或游戏自己的设置）——那缺 program 是“原样”。

**判定实验（30 秒）**：

1. 把 `hoot.ini` 的 `output_midi_device` 指到 loopMIDI；
2. 用 `py -3.12 build/_lead_midicap.py --seconds 30` 抓 HOOT 播一首 AMA4 的输出；
3. 在抓到的流里数 `0xC0–0xCF`：

| 结果 | 含义 | 下一步 |
|---|---|---|
| 有 `0xC0` | 我们漏了初始化 | 找 HOOT 里触发它的那一步（0x0201 / SysEx / 模式），修好可救 41 首 |
| 没有 `0xC0` | 驱动本来不发 | 不修，文档标注“音色由 GS 默认/游戏设置”，收口 |

**顺带**：这个 30 秒捕获同时验证了 HOOT 录制管线——它也是 7 个“装得上但不出声”包
（reno/momoko/papa/tlove12/yumecol/farce/hiragi）的兜底方案：HOOT 能播，就录它的输出，
不必把 1.72 仿真对。

## 11. FMD9 作为通用读取引擎

**背景**：1.71 会把数据里的非音符记录（`EC` program、`EB` CC、`EE` 驱动命令）全部丢掉，
1.72 干脆不播。同一份 `.GMD`/`.GS` 数据换 **FMD9（A 代）** 就完整吐出 program/CC/弯音/SysEx。

**测试**：把各包的 `.GS`（或首个数据文件）注入 FMD9.EXE，`/ #` 安装、`0x0100` 装载、
`0x0300` 播放、600 tick：

| 包 | 输出 | 0x90 音符 | 0xC0 program | 结论 |
|---|---|---|---|---|

### 三条纠正

1. **papa / farce / hiragi 不是死包**：`PAPA_00.GS` / `FARCE_00.GS` / `HIRAGI_00.GS` 是
   **4 字节的 `"STOP"` 哨兵**，真实曲目从 `01` 号往后（12–20 KB）。取错文件导致上一轮误判。
   **哨兵陷阱值得写进 checklist。**
2. **`AMA4_000.GMD` 与 `AMKH_000.GMD` 是同一份文件**（md5 `97363ddf0080`，3759 字节，逐字节相同）。
   之前的“时长/音符/tempo 完全相同、疑似串包”不是导出 bug——两个游戏共用一套数据。
3. **reno 的洪泛是短循环重放**：它的轨道是「`FE` 开头 + 短循环」的另一代格式：

```
轨0: FE FE FE FE ...                    ← 立刻停
轨1: EB 00 01 00 | EB 00 07 64 | EB 00 0A 40 | FE   ← 三条 CC 就循环
轨4: EB … | EC 00 0A 00 | 5B 08 08 64 …             ← 有 EC（乐器）
```

FMD9 把这种短循环当正常循环，每几 tick 重发一遍 CC（300 tick 就 7209 个 CC → 36 KB）；
1.71 把它当“停”，所以干净，但 1.71 丢 EC/EB → 乐器没了。

### 落地方式

- **FMD9 重导**：ama4、amakh、tlove12、momoko、yumecol、mug-r、hiragi、papa；
- **reno**：引擎用 1.71，再按数据里的 `EC`/`EB` 记录补 `program_change`/CC
  （`EC 00 <prog>` → ch=轨号、prog=p1；A 代发出的值已严格对上）；
- **farce**：FMD9 能读出 3331 个音符记录但 0 个 C0（EC 只有 43 个，其它包 175–421）。
  先抓一首 HOOT 对 `0xC0`：有 → 补；没有 → 按“本来就少切换乐器”结档。

**引擎选择不写死在导出器里**：做成探针表（包 → 引擎 → 采样结果），校验条件是
**load 成功 + 音符 > 0 + 最忙 tick 字节数合理**（第一轮误选 STOP 文件就是缺了这条）。

脚本：`build/_lead_fmd_engine.py`（矩阵生成）、`_lead_fmd_trio.py`（同数据/洪泛/头检查）。

## 13. 按包选引擎的落地实现（2026-11-23 深夜）

### EC/EB 补事件（`synth_events`）

按 4 字节记录走表，`EC 00 <prog>` → `program_change(ch=轨号, prog=p1)`，
`EB 00 <cc> <val>` → CC；tick 用记录里的 `dur` 累加。
**时机很关键**：必须「预装载（0x0100）之后、0x0300 之前」取轨道表——播放后 `cur` 已经前进，
那时走表拿到的是半路数据（第一次实现就踩了这个，补了 0 个事件）。

**实测（`AMA4_000.GMD`）**：

| 导出方式 | program change |
|---|---|
| 1.71（旧产物） | 0 |
| 1.71 + 补事件 | **12 个**：`(0,ch0) (39,ch1) (39,ch2) (29,ch3–5) (56,ch6–8) (60,ch3–5)` |

数值与 FMD9 发出的 `C9 00 / C1 27 / …` 一致，所以补出来的事件是对的。

### 纠正 §12 的一处：ama4/amakh **不要**整体换 FMD9

FMD9 读 `AMA4_000.GMD` 只切到 **16.2 s**（`static` 1740 tick，且确认不到整曲循环），
同一首用 1.71 是 **174.7 s**——两个引擎对「歌曲长度」差 10 倍。
**如果按 §12 那样把 41 首整体换 FMD9 重导，会被截短一个数量级。**

### 最终引擎表

| 包 | 引擎 | 理由 |
|---|---|---|
| ama4 / amakh | **1.71 + synth** | 时长与旧产物一致，只补回 12 个 program |
| reno | **1.71 + synth** | FMD9 把短循环当循环 → 36 KB CC 洪泛 |
| tlove12 / momoko / yumecol / mug-r / hiragi / papa | FMD9 | 自带驱动崩/空/洪泛；换引擎后**必须核对时长** |
| farce | FMD9（待定） | 能读（124–414 音）但 0 program |

**换引擎的包不能直接覆盖旧产物**：FMD9 常常确认不到整曲循环，会走 `static` 截断，
时长可能和 HOOT 或旧产物差很多。批量前先抽 1–2 首对时长（HOOT 实听/旧产物），
一致再整包替换。

### 已知坑（新增）

- `.GS` 里 `00` 号常常是 4 字节 `"STOP"` 哨兵（papa/farce/hiragi），按文件名字典序取第一首会踩空；
  导出器的 `main()` 已经跳过，但自己写探针时别忘了。
- `max_ticks` 调大后，尾段会重放 16 声道 CC（`AMA4_000` 在 24000 tick 时出现 2.7 万个 CC），
  所以**必须保留原来的循环截断逻辑**，不能靠“跑够长”来省事。

### 更稳的落地：直接给已有 SMF 补事件（`_lead_fmd_patch.py`）

重跑仿真会连时长一起改（见上一条），而旧产物的时长是核对过的。所以对 **ama4 / amakh**
采用「不重跑仿真、只补事件」：

```
python build/_lead_fmd_patch.py ama4_98 amakh_98
→ build/hootcap/fmd_synth/<HOOT 标题>/<曲>.mid
```

做法：用 1.71 预装载取**初始**轨道表 → `synth_events` 算出 (tick, 消息) →
用 mido 把 `program_change`/`control_change` 按绝对 tick 插进已有 SMF。

**实测（23 + 18 首全部跑过）**：

- 时长**逐首不变**（174.7 s 还是 174.7 s）；
- 每首补 25–310 条事件，program 6–16 个；
- 一个坑：`synth_events` 走到轨道循环点之后会产生超出曲尾的 tick，直接插进去会把文件拉长
  （`AMKH_010` 61.0→65.6 s、`AMKH_016` 87.1→122.3 s）。**必须把 tick 钳到原文件总长**，
  钳完 18 首全部时长不变。

确认后整目录替换即可。

## 14. FMD5 的启动差异（为什么只有风雅セレクション受影响）

**只有 `fgsel1c` / `fgsel1m` 用 FMD5（`/e` 参数）**；其余已导出的包全部是
FMD9 / FMD13 / FMD.EXE。所以这个启动差异只落在风雅这两包。

在 harness 里跑 `MAZE00`（FMD5）：

```
0x0300 播放调用内只吐 6 字节
tick 0：  82 字节（全是 SysEx / program change / CC，**没有音符**）
tick 24： 第一个音（64+8 字节）
tick 47： 62+8
tick 72： 16+8
```

而 HOOT 的抓取里 **t=0 就是 10 个音**（36/42/40/64/57/76×4/40）。

结论：**FMD5 在播放调用里不吐音乐，要等第一个 tick 之后才开始**；HOOT 里（游戏真实运行时）
它是立刻开始的。对比 FMD9 的包（AMA2_000、CHAOS）与 HOOT 抓取斜率都是 **1.000**，没有这个偏移。

**修复方向**：

1. 查 FMD5 的播放初始化——`0x0300` 之后是否需要额外一次 `INT 0E` 或先读一次状态口；
2. 若确认是“前 24 tick 空转”，导出时把起点挪到第一个音符/第一个事件；
3. 验证：去掉偏移后与 HOOT 对齐，斜率应回到 1.000。

脚本：`build/_lead_maze_playstart.py`（逐 tick 字节数）、`_lead_maze_pkl.py`（抓取对齐）、
`_lead_maze_index.py`（按序号对齐）。

## 16. 长抓取的截断：自相似检测（给重导用）

**背景**：重跑 `ama4_000` 得到 298.5 s（旧冻结产物 174.7 s），音符数一致、时长不对——
说明循环截断没触发，跑满预算后全是重放尾巴。旧的 offset 回跳判据对多轨循环不灵
（OPENING 已经证明：多轨独立循环没有统一点）。

**判据（可照抄实现）**：

1. **只在 capture 跑满预算（capped）时才尝试截断**；idle 自然停下的不截；
2. 构建每 tick 的 token：把该 tick 的所有消息字节拼成字符串，再做整数哈希；
3. 候选周期 T：`12` 的倍数，范围 `[96, min(n//2, 16384)]`；
4. 对每个 T，比较 `tok[t] == tok[t+T]`（t ∈ [0, T)）；
   要求 **匹配率 ≥ 0.95** 且 **匹配 tick 数 ≥ max(600, T*0.5)**；
5. 取满足条件的**最小 T**；若全部不满足 → 不截，标记 `no-loop`；
6. 截断点 = 第一个满足条件的 `t0`（从 0 找起，允许 2% 不匹配）。

**性能**：token 先转成整数哈希数组，n=32000、候选约 1300 → 约 4×10⁷ 次整数比较，
几秒内可完成。

**验证**：截完抽 1 首与 HOOT 60 秒抓取对齐（斜率应 1.000）；至少确认时长落在
“首尾事件时间差”的合理范围，而不是预算上限。

参考实现：`build/_fmd_export.py` 的 `_tokens` / `find_loop`（已弃用的 O(n²) 版本，
思路可复用，性能要换成哈希）。

## 17. 引擎探针必须包含结构校验（2026-11-23）

现有探针只看**数量**：`load 成功 + 音符 ≥ 20 + 最忙 tick ≤ 400 字节`。
**反例**：FMD9 读 `AMA4_000.GMD` 不只是截断（静态 1740 tick → 16.2 s），
**轨道与事件也是错位的**——而音符数、program 数看起来都正常。
这种“数量对、结构错”的产物比没导出更糟，因为它看起来是对的。

**新增判据（每包先导 1 首）**：

1. 与 HOOT 抓取的前 60 秒对齐（loopMIDI 录制）；
2. **音高序列匹配率 ≥ 80%**；
3. **斜率 1.000 ± 0.02**；
4. **残差中位 < 20 ms**。

三条全过才允许批量；不过就换引擎（用包自带驱动）或改走 HOOT 录制。

**结论修订**：§15 的“FMD9 是参考引擎”应限缩为
**“FMD9 是事件最全的引擎，仅对通过结构校验的包成立”**。
FMD9 不能被当作通用读取器——ama4/amakh 已证明它会错位。

## 18. §16/§17 的实现与实测（2026-11-23 深夜）

**实现**：`build/_lead_fmd_engine.py`

- `selfsim_cut()` 按 §16 的判据实现：只在没有旧式「确认循环」时启用；token = 每 tick 全部
  消息字节的 blake2b 哈希；T 为 12 的倍数、`[96, min(n//2, 16384)]`；匹配率 ≥ 0.95 且
  匹配数 ≥ `max(600, T*0.5)`；取最小 T；`t0` 用前缀和滑窗找第一个允许 2% 不匹配的位置。
- **截断点取 `t0 + T`**（前奏 + 一遍）——§16 写的是「第一个 t0」，但 t0 只是周期段的起点，
  直接当截点会把前奏连同整段都砍掉；这与旧 `find_loop` 的语义（jump 点 = 一遍结束）一致。
- `structure()`：从事件流算 音符数 / 用到几个通道 / 音高种类 / C0 / CC / 音符密度 /
  峰谷比，并按「通道 <3、音高 <8、密度 <0.3 或 >80/s、峰/中位 >4 倍」出 flags。
- `agreement()`：两个引擎在**同一份数据**上的条数比 + 音高直方图余弦；
  只有两边都 ≥20 音时才比较（一边不出声时无法交叉校验，不能当证据）。

**实测探针（600 tick，两引擎）**：


**自相似截断的实测**：`AMA4_000`（1.71，32000 tick）→ **`no-loop`**（找不到 0.95 匹配的

## 19. 结构校验失败：AMA4_015 的轨道→通道映射不对（2026-11-23）

```
HOOT: 36 41 45 28 40 64 64 40 40 36 ...
导出: 40 40 40 64 40 52 64 52 40 64 ...
```

**通道分布（更关键）**：

| 通道 | HOOT | 导出（前 60 s） |
|---|---|---|
| ch1 | 374 | 64 |

就是错的。

**假设**：游戏启动时会做一步我们没复刻的初始化——很可能是**轨道→通道分配**
（藏在 `EE` 记录或 `0x0201` 送音色流程里）；驱动拿不到就退回“按轨道号分配”。

**下一步**：

1. 从 HOOT 抓取的通道分布反推映射（ch9=鼓、ch1/ch4 为主旋律等）；
2. 对照 `.GMD` 轨道表 / `EE` 记录，找“目标通道”字段；
3. 导出时按字段重映射，而不是让驱动按轨道号分配；
4. 重跑 AMA4_015，§17 三项指标全过再批量。

**在此之前，ama4/amakh 的 41 首不能算交付**——音符数对得上，但结构不对。

## 20. AMA4_015 逐项对照 + FUGAM_98.COM 反汇编（2026-11-23）

拿到 HOOT 抓取（`D:\music\AMA4_015_HOOT.mid`）后，和导出逐项比：

| 项 | HOOT | 导出 |
|---|---|---|
| 拍数 | 146.8（73.4 s） | **666.6（333.3 s）**，4.54× |
| 音符 | 2696 | 14733 |
| 音高序列相似度 | — | **0.008** |
| 导出 [0,A) 与 [A,2A) 相似度 | — | 0.022（**不是循环重复**） |
| ch1/ch2/ch3/ch4/ch5 | 374/299/163/336/162 | 144/457/43/72/**0** |
| ch9 鼓 | 718 音、9 种音高 | **141 音、只有 36/41/45** |
| program | (9,16)(1,33)(2,30)… | (0,16)(1,33)(2,30)…（值同，第一个落在 ch0） |

结论：**不是“缺乐器”，也不是循环没截**——事件流本身就是另一套东西。
鼓轨只出 3 个音高、ch5 整条轨消失，说明轨道/通道和记录解码都错了。

**FUGAM_98.COM（228 字节）完整反汇编**：

```
0101 out 0x7E8,0x80         ; 音源板模式口（读的是 0x7E0）
010E AH=4A 缩小内存
011B call 0x1A5             ; 扫 2E F6 06 xx xx 01 75 → 把驱动 [0x1E] 清 0
011E AH=48 BX=0x1000        ; 申请 64 KB（不是 16 KB）
0133 AH=3F BX=5 读 stdin    ; 音色数据 → AX=0201 送音色（DS:DX = 缓冲区，不是文件名！）
0152 AH=25 AL=07F          ; 挂 INT 7F = 键盘回调
0161 AX=9801 int 18         ; 等键
0168 回调: in al,0x7E0      ; 0 → 读 stdin 歌 → AX=0100 → AX=0300；2 → AX=01FF
```

**关键结论**：壳**没有任何“轨道→通道分配”的初始化**，就是 0201/0100/0300/01FF 四次调用
＋清 `[0x1E]`。所以 §19 的「游戏启动时做了我们没复刻的初始化」**不成立**——HOOT 跑的调用链
和我们一样。

差别只可能在两处：

1. **喂数据的方式**：壳先 `AH=4A`、再 `AH=48 BX=0x1000`（64 KB），用 `AH=3F` 从 stdin 读进
   这块内存，然后 `DS:DX = 缓冲段`（DX=段、SI=0）。我们则是把歌写到固定的 `0x5000`、
   再把 `cs:[7]` 强行改成 `0x4000`——驱动看到的“自己那块内存”与 HOOT 不同。
2. **板子模型**：我们 `in 0xE0D0` 永远返回 `0xFD`、`in 0xE0D2` 只按 ack/tick 给位，
   没有 FIFO/状态语义。驱动如果按状态位决定“这一拍推进几条记录”，模型不对就会错位。

**下一步（按优先级）**：

1. 在 harness 里**照抄壳的流程**：`AH=4A`→`AH=48 0x1000`→把歌写进那块内存→`DS:DX=buf, SI=0`
   →不要手改 `cs:[7]`；0201 也改成「DS:DX=数据」而不是文件名；
2. 用已经拿到的 `AMA4_015_HOOT.mid` 当回归标尺（音高序列相似度、拍数、ch9 音高集合）；
3. 若还不对，再动板子模型（0xE0D0 状态/FIFO 语义）。

## 21. 内存流程修复无效 → AMA4/AMAKH 与 6 包记 blocked（2026-11-23 收尾）

按 §20 的第 1 条改了三版 harness，都在 `AMA4_015` 上跑 9000 tick：

| 变体 | 改了什么 | 结果 |
|---|---|---|
| A | 旧流程（poke `cs:[7]=0x4000`、AH=48 段放 BX） | 2470 音，音高相似度 0.008 |
| B | 只修 AH=48（段放 AX，DOS 语义） | **与 A 逐字节相同** |
| C | 壳流程：AH=48 + 64KB 块放歌 + **不 poke `[7]`** | **与 A 逐字节相同** |

三版输出完全一致 ⇒ **内存流程（buf 段、64KB、`cs:[7]`）不是分歧点**。

**三项验收（对 `AMA4_015_HOOT.mid`）**：

| 指标 | 通过线 | 实测 |
|---|---|---|
| 音高序列相似度 | ≥ 0.8 | **0.008** ✗ |
| 拍数/时长 | 差 < 5% | 不适用（导出不是自相似重复，见 §20） ✗ |
| ch9 鼓音高集合 | 9 种一致 | **6 种**（36/38/41/45/48/49） ✗ |

**退路第 1 条的量测（每 tick 事件数）**：以 1/48 拍为格统计

```
HOOT : 5645 事件 / 1467 格 = 3.85 件/格，最多一格 48 件，78% 的格 ≥2 件
导出 : 4966 事件 / 3020 格 = 1.64 件/格，最多一格 32 件，51% 的格 ≥2 件
```

HOOT 的**事件密度是我们 2.3 倍**，而我们是「一次 `in 0xE0D0` 给一个 `0xFD`、一次推进一条记录」。
这与 §17 的假设一致：**板子状态语义（`0xE0D0`/`0xE0D2` 的 FIFO / 状态位）才是下一个坑**，
而不是内存布局。

**按预算停手**（不再动板子模型，避免变成第二个三天）：

- **已验证可交付**：Amaranth II GS（36 首）+ MT-32（34 首）——FMD9/FMD13，HOOT 逐事件对齐
  斜率 1.000，产物在 `build/hootcap/fmd/[PC-9801] Amaranth II(GS|MT-32)/`；
- **blocked**（同一个根因：记录解码/板子语义不对，不是“缺乐器”）：
  ama4 / amakh（含 `fmd_synth` 那 41 首——底子错，**不可交付**）、
  tlove12 / momoko / yumecol / mug-r / hiragi / papa（FMD9 能读但未过结构校验）、
  reno（1.71 干净但丢 EC/EB）、farce（0 program）；
- **解锁条件**（任一）：
  1. 实现板子模型的 FIFO/状态语义（`0xE0D0` 每次读给多少字节、`0xE0D2` 的位含义），
     用 `AMA4_015_HOOT.mid` 的三项指标当回归；
  2. 或对 blocked 的包直接录 HOOT 的 MIDI 输出（`_lead_midicap.py`，时间轴可信）。

## 22. 结案（2026-11-23）

**决定**：B 代（`FMD.EXE` 1.5x–1.72 / `FMD5` / `FMD7`）**停止逆向，结案归档**。
理由不是"没时间再试一下"，而是三个独立证据链都指向同一结论：**我们不知道 HOOT 到底做了什么，
而每追一个假设都要一轮 HOOT 录制 + 逐事件对齐 + 反汇编**——代价与收益完全不成比例。

**证据摘要**（细节见 §9–§21）：

| 假设 | 实验结果 | 判定 |
|---|---|---|
| 数据不对 | 同一份 `.GMD/.GS` 换 FMD9 能出完整事件（program/CC/弯音/SysEx） | 数据没问题 |
| build 有 API 差异 | 4857 与 4969 引擎逐字节相同（1.72/1.71） | 排除 |
| 内存流程不对 | 三版 harness（旧 / 修 `AH=48` / 壳式 64 KB + 不 poke `[7]`）输出逐字节相同 | 排除 |
| 壳里有轨道分配 | `FUGAM_98.COM` 全反汇编：只有 0201/0100/0300/01FF + 清 `[0x1E]` | 排除 |
| 只是循环没截 | 导出 [0,A) 与 [A,2A) 相似度 0.022，不是重复 | 排除 |
| 只是缺乐器 | 补了 program 后仍是另一场演奏（AMA4_015 相似度 0.008） | 排除 |
| 板子状态/FIFO 语义 | 只能到此为止：我们 1 次读 = 1 条记录，HOOT 事件密度是我们的 2.3 倍 | **未验证的剩余假设** |

**定性**：这个驱动的难度**远高于本工程其它驱动**——它把「时间轴、事件流、轨道分配」都放在
板子固件行为里，而我们只仿了协议表面（`0xE0D0`/`0xE0D2` 的握手），没有仿它的缓冲/状态机。
在没有公开规格的前提下，继续逆向**不现实**。

**结案后的口径**：

- 交付：A 代 70 个文件（Amaranth II GS 36 + MT-32 34，斜率 1.000）；
- unverified：`build/hootcap/fmd/` 其余 99 个文件 + `fmd_synth/` 41 首，**不要当成果引用**；
- 回归标尺保留：`D:\music\AMA4_015_HOOT.mid`（音高相似度 / 拍数 / ch9 音高集合 / 每 1/48 拍事件数）；
- 若要重启：先做板子 FIFO/状态模型，再跑 §17 的三项判据；否则改走 HOOT 录制兜底。

**归档脚本**（`build/_lead_fmd_*.py`，都不进仓库）：引擎表/探针 `_lead_fmd_engine.py`、
SMF 补事件 `_lead_fmd_patch.py`、壳式流程 `_lead_fmd_shell.py`、自相似截断
