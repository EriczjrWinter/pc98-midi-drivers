# FMD 期望的硬件环境：PC-98 MIDI 板的公共交集（MPU-401 intelligent mode）

> **为什么写这份**：FMD 是写给一整代 PC-98 MIDI 卡的（MPU-PC98 / PC-9801-26K / -86 /
> MPU-98II），它只能使用这些卡的**公共子集**——MPU-401 的 intelligent mode。
> 所以「HOOT 实现了什么」不是正确的问题，**「这些卡共同保证什么」才是**。
>

> NP21W `cbus/mpu98ii.c` + DOSBox-X `src/hardware/mpu401.cpp`（本地已在 `FMD-BUILDS.md` §23 摘录）。

## 一、端口与状态

| 地址 | 方向 | 语义 |
|---|---|---|
| `0xE0D0`（基址可由 DIP 改） | R/W | 数据口 |
| `0xE0D2`（= base+2） | R/W | 状态（读）/ 命令（写） |

状态位（读 `0xE0D2`）：

| 位 | 含义 |
|---|---|
| bit7 = 0 | **有字节可取**（收队列非空） |
| bit7 = 1 | 空闲 |
| bit6 = 1 | 写忙（TX 未排空） |
| bit0 | 上一字节写的是命令口（MAME 的 `STAT_CMD_PORT`） |

## 二、命令表（FMD 实际用到的 + 手册定义）

| 命令 | 语义 | FMD 用法 |
|---|---|---|
| `$FF` | RESET | 装载/停止 |
| `$3F` | UART 模式 | 不用 |
| `$C2–$C8` | **SET TIMEBASE**：48/72/96/120/144/168/192 tick/拍 | 发 `$C2` = 48 |
| `$E0` | **SET TEMPO**（BPM，4–250） | 曲头 BPM |
| `$E1` | **SET RELATIVE TEMPO**（`$40` = 1/1） | 变速 |
| `$E2` | GRADUATION（速度渐变） | 渐变时 |
| `$E4` | MIDI THRU on/off | 未用 |
| `$E7 <n>` | **内部时钟分频**：`n>>2`（0 当 64） | 发 `$E7 04` → 不分频 |
| `$94` / `$95` | CLOCK TO HOST **off / on** | 发 `$95` |
| `$B8` / `$B9` | 清计数器（播放 / 录音） | 见第五节 |
| `$AC` / `$AD` | 版本 / 修订 | 可能用于探测 |
| `$AF` | 读 tempo | 可能用于探测 |
| `$D0` | **送一条短 MIDI 消息**（随后写 status + 数据字节；不是只送一个字节） | 所有普通 MIDI 输出 |
| `$DF` | **长消息 / 发数据块**（数据口后续字节到 `$F7` 为止） | GS SysEx（`DD/DE/DF` 记录） |

**时钟公式**：

```
每拍 tick 数 = timebase × 4 / ($E7 >> 2)
FMD：48 × 4 / 4 = 48
板子出 0xFD 的速率 = tempo × timebase / 60   （134 BPM × 48 → 107.2 次/秒）
```

## 三、~~★ Conductor（小节）协议~~——**已证伪，作废（2026-11-25）**

> **结论先行：FMD 驱动从未发 `$8D`（也没有 `$8C` / `$F8` / `$F9`）。**
> 手册确实定义过这套 MEASURE END / conductor 协议，但 FMD 不用它。
> 因此 `$F9` 发送、`$F8` 装载 240、`$8C/$8D` 使能**一律没有实现**——
> 按 §9.5 与任务书的要求，不在模型里留死代码。
>
> 证据（`build/mpu_log.py`，JSONL 全事务流）：
>
> | 运行 | 命令数 | `$8C/$8D/$F8/$F9` | A/B 代实际命令集 |
> |---|---|---|---|
> | A 代 `ama2s_98 / AMA2_000` | 9,066 | **0** | `$FF $32 $E0 $C2 $E7 $95 $D0×9060` |
> | A 代 `ama2s_98 / CHAOS` | 3,203 | **0** | 同上，`$D0×3197` |
> | B 代 `ama4_98 / AMA4_015`（1.71） | 4,973 | **0** | `$FF×2 $32 $E0 $C2 $E7 $95 $D0×4966` |
>
> 复现：`python build/_fmd_export.py ama2s_98 AMA2_000.MMD --board-log <path>.jsonl`
> → `python build/mpu_log.py <path>.jsonl --conductor`。
>
> 下面这段保留为**手册事实与错误假设的记录**，不要再据此改模型。

**（已作废的假设）这块板不只是发 0xFD 时钟，它还有一个小节/节拍计数器，并且在每个小节边界向主机索要数据。**

| 报文 | 方向 | 语义 |
|---|---|---|
| **`$F9`** | 板 → 主机 | **MEASURE END / CONDUCTOR DATA REQUEST**：小节结束，向主机请求下一段 conductor 数据 |
| **`$F8`** | 主机 → 板 | **TIMING OVERFLOW / NO OPERATION**：主机表示「再给点时间」，**把播放计数器装载 240**。手册要求**单独发送** |
| **`$8D` / `$8C`** | 主机 → 板 | 打开 / 关闭 `$F9` 的发送（MEASURE END 使能） |

**主机应答 `$F9` 的格式**（手册 p.44 起）：在数据口上依次送

```
$00–$EF   timing 字节（本小节剩余时序）
随后     conductor 命令（如 $E1 修改相对速度）
```

手册例子：**「如果在 CONDUCTOR REQUEST（`$F9`）之后发了 `$78 $E1 $80`，
MPU-401 的内部 tempo 会在一个四分音符之后变成两倍」**——即 timing 字节 + conductor 命令的组合。

录音侧对称：录音计数器累计到 240（`$F0`）时，用 `$F8` 表示溢出。

## 四、~~这条协议为什么解释了我们所有的困惑~~（已撤回）

FUGA 的数据流里有 `F8` / `F9` 记录，我们一直按「循环开始/结束」解释：

```
F9 → 压栈（6 字节一项，深度 [bx+0x2B]，最多 5 层）
F8 → dh=ah（次数），计数 +1，达到就弹层并回跳
```

但按手册，这两个字节在 intelligent mode 里是 **conductor 协议报文**：

- **`$F9` = 小节结束请求**，不是「循环开始」；
- **`$F8` = 装载 240 / 时序溢出**，不是「循环结束」；
- 那个「次数」（`AH`）很可能**不是重复遍数**，而是与板子的小节计数器绑定的量；
- 「`0 = 无限`」可能实际是「**不干预，让板子的小节计数器自己跑**」。

> **2026-11-25 撤回**：以上解释**作废**。驱动没有发 `$8D`，板子也就不会发 `$F9`；
> FMD 数据流里的 `F8/F9` 仍按**驱动自己的循环计数**解释（§四开头那套压栈/回跳），
> 不是 conductor。原来「我们测不到 F8 是因为板子没有小节计数器」的推论是错的——
> 真正的原因是**根本不存在这条协议的使用**。

## 九、板卡 + 日志：零扰动观测面（2026-11-24 谋士方案）

### 9.1 为什么是「日志」而不是「hook」

三轮会话的全部误判都来自同一个根：**用 code hook 观测 CPU**——它会切 TB、改变 lazy flags
的物化时机、改变时序，于是「测到的」和「真实跑的」不是一回事。

板卡是**我们自己写的代码**，在里面 `append()` 一条记录不改任何语义。观测点从「CPU 指令流」
挪到「软硬件接口」，天然干净：

| | code hook | 板卡日志 |
|---|---|---|
| 观测位置 | CPU 指令 | 端口事务 |
| 扰动被测对象 | **是** | **否** |
| 可重放 / 可断言 | 难 | **是**（日志即完整事务流） |

### 9.2 日志四层

**① 原始事务**

```
{tick, phase, dir, port, value}          dir = in/out
```

**② 解码层**（板卡自己知道语义，不靠事后猜）

```
cmd $C2 timebase=48 | cmd $E0 tempo=179 | param 0xB3 → tempo
cmd $95 clock_to_host=on | clock $FD #1234
（以下两行是**已作废**的 conductor 假设，模型里不存在）
cmd $8D measure_end=on
conductor $F9 #17 → host reply: timing=0x78, cmd $E1 rel=0x80
$D0 → MIDI C1 45（program change ch1=69）
```

**③ 派生指标**（离线分析，不实时）

- `0xFD` 间隔分布 → **实际时钟速率**（应 = tempo × timebase / 60）
- 每 tick 发出的 MIDI 字节数 → **事件密度**（1:2.3 的来源）
- 队列深度曲线 → 驱动是「一读一字节」还是「一次读空」
- ACK 等待时长 → 驱动对时序的敏感程度

**④ 每 tick 附上轨道表状态**（**只读内存，不算观测**）

18 条轨道项的 `[bx+2] / [bx+4] / [bx+0x2B]`，拼进同一行日志。

### 9.3 它能一次证伪的悬案

> **`$F9` conductor 假设**：
> 若日志显示驱动**从未发 `$8D`** → `F8/$F9` 就不是 conductor 协议，假设当场作废；
> 若发了 `$8D` 却收不到 `$F9`（我们的板子不发）→ **是我们的错**。

这是本工程一直缺的能力：**把猜想变成一次运行即可判定**。

### 9.4 产物形态

```
build/mpu401.py      板卡模型（含 self.log）
build/mpu_log.py     日志分析：clock_stats / cmd_trace / queue_stats / conductor
build/test_board.py  规范断言（手册条款 → 测试）
```

日志用 **JSONL**（一行一条），方便 `jq` / pandas，也方便直接贴进文档。

### 9.5 纪律

1. **日志不许改行为**：加日志前后，A 代回归必须逐字节一致（硬门槛）；
2. **不做通用 tracing 框架**，只记这一层接口；
3. 若日志证明某功能驱动根本不用（如 conductor），**立刻回滚那段实现**，不留死代码。

### 11.6 根因：播放期 code hook 让 `cmp` 丢 CF，FD 扫描只走 +4

**0x0CFC 读出来的语义**（`drv_ama4_98.bin`，与 HOOT 1.71 同 build）：

```
0x0CE7  push si
        si = [bx+2]            ; 旧锚点
        call 0x0CFC
        [bx+4] = bp            ; 新 cur = FC 链解析后的跳转目标
        [bx+2] = si            ; 新锚点 = 向后扫描到的控制字节
        ...

0x0CFC  call 0x0D09            ; 从 [bx+2] 起跟 $FC 链（最多 10 层）→ bp
        cmp al, 0xFE
        stc / je  结束          ; 轨道终止
        call 0x0D28            ; 从 si 起按 4 字节记录向后扫
        clc

0x0D28  从 si 起：
        记录字节 < $FC        → si += 4，继续
        记录字节 = $FD        → si += 4，越过它
        记录字节 = $FC        → 停在它（新锚点）
        记录字节 = $FE/$FF    → 停在它（其中 $FE 由 0x0CFC 判为终止）
```

所以**新锚点 = 旧锚点到下一个控制字节的距离**；HOOT 实测这个正步长是
`+0x14 ~ +0xC4`（5–50 条记录）。我们的仿真原来每次只 `+4`，因为 `0xD28` 里的
`cmp al,0xFC` 后面的条件跳转（`jae 0xD45` / `jb 0xD33`）把每个普通记录都当成了
控制字节——**CF 一直是旧值 0**。

**为什么 CF 不更新**：`_fmd_export.install_pack` 原来在播放期持续挂着
`hook_all_ints` 的 10 个 code hook + 覆盖 `0x10100–0x16000` 的范围 hook。
Unicorn 2 在这种持续 code hook 下，`cmp` 的 CF 不再物化（`uc.reg_read(FLAGS)`
在 `cmp` 前后都是 `0x16`，CF=0；同样指令在干净 Uc 里是 `0x87`）。
这是 内部审查清单（不随库发布） 里「范围 hook 污染相邻指令语义」的最强一次实证：
**被污染的不是一条指令，而是整条 `cmp` 分支链。**

**修法**：

1. 安装阶段保留范围 hook 过 DOS，`emu_start` 返回后立即 `u.hook_del(h_cd)`；
2. 播放阶段不再调用 `L.hook_all_ints()`（它装的 10 个点即使不在 `cmp` 附近也会让 CF 失效）；
3. 播放期只留 `LOOP_END` 一个精确 hook（`on_loop`，用于旧实验统计）。

**验证**：

| 指标 | 修复前 | 修复后 | HOOT |
|---|---|---|---|
| 轨 0 loop 正步长 | 固定 +4 | +0x14 ~ +0xC4（集合与 HOOT 同型） | +0x14 ~ +0xC4 |
| 轨 0 loop 地址序列 | 0x30,0x34,0x38… | 0x108,0x14C,0x1CC,0x258… | 0x108,0x14C,0x1CC,0x258… |
| 轨 0 `[bx+4]` 范围 | 0x2C–0x148 | 0x2C–0x7DC | 0xEC–0x7F0（长录） |
| 鼓音高 | 6 种 | **9 种（含 42）** | 9 种 |
| 事件密度比 | 0.42 | **0.88** | 1.00 |
| A 代 AMA2_000 哈希 | `A5AB…` | **`A5AB…`（不变）** | — |
| A 代 CHAOS 哈希 | `99ED…` | **`99ED…`（不变）** | — |

**纪律**：以后播放阶段不许有覆盖指令流的 code hook；安装期 hook 用完就拆。
这不是「驱动难」，是观测工具第二次把答案藏起来了——上一次是 lazy flags 的半条指令，
这一次是整整一层 `cmp`。
