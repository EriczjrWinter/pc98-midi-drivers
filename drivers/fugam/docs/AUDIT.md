## 一、台账（唯一事实来源）

脚本扫描全库，产出 `build/audit/fuga_ledger.csv`，每首歌一行：

| 字段 | 说明 |
|---|---|
| `pack` | 包名（如 `ama2_98`） |
| `song` | 曲目文件名 |
| `gen` | `A` / `B` / `FMD5` |
| `has_export` | 是否有导出文件 |
| `dur` | MIDI 实际时长（秒，mido 读回） |
| `notes` | 音符数 |
| `nps` | 音符/秒 |
| `tempo_n` | tempo 事件个数 |
| `drums` | 鼓音高集合（ch9） |
| `end` | `fe` / `loop` / `pass` / `cap` / `none` |
| `ref` | HOOT 参照文件路径（可为空） |
| `ref_indep` | 参照是否独立（sha1 不等于我们的产物） |
| `d_notes` | 与参照的音符数差（%） |
| `d_dur` | 与参照的时长差（%） |
| `verdict` | `ok` / `re-tempo` / `re-pass` / `re-density` / `no-ref` / `empty` |

**要求**：脚本必须可重复运行，输出稳定排序，方便 `diff` 两个版本。

## 二、审计步骤

### 步骤 0：甄别假参照（必做，否则后续全白做）

```
对每个参照文件，算 sha1
若与 build/ 下任一导出产物相同 → ref_indep=0，标记 "参考即产物"，不得用于验证
```

已知案例：`OPENING.mid`（Amaranth II GS）与我们的产物完全相同；`うきうきアイランド` 整目录。

### 步骤 1：静态体检（不需要参照）

对每个已导出文件查：

| 检查 | 阈值 | verdict |
|---|---|---|
| `notes == 0` | — | `empty`（必查原因，不允许静默跳过） |
| `dur < 30` 且 `end=cap` | — | `SHORT_CAP`（出口没生效） |
| `end == cap` | — | `re-pass` |
| `tempo_n > 5` | — | `re-tempo`（疑似误读，OPENING 那种） |
| `nps` 偏离同包中位数 ±3σ | — | `re-density`（太稀=漏音，太密=重放） |

### 步骤 2：对照 HOOT（仅 `ref_indep=1`）

四条判据，任一不过即打标：

```
① |d_notes| < 5%        ← 主判据（漏音就是靠这条抓到的）
② |d_dur|   < 2%
③ tempo_n 一致
④ end != cap
```

> **注意**：旧的「斜率 1.000」判据有盲区——只比时间轴、不比密度，
> 漏一半音也能拿满分。**不要再用它作主判据。**

### 步骤 3：分类处置

| 类 | 条件 | 处置 |
|---|---|---|
| A | 四判据全过 | 不动 |
| B | 只差 tempo | 用新 tempo 逻辑重导 |
| C | `d_notes > 5%` | **先查病因，不许直接重导** |
| D | `end=cap` | 改 pass 判据后重导 |
| E | 无独立参照 | 标 `no-ref`，不参与判定 |

## 三、密度问题的调查（C 类专用）

OPENING 的对策，也是 C 类的通用流程：

```
1. 把参照和我们各按"每 60 秒"切桶，逐桶比音符数 → 输出对照表
2. 判读：
   每桶都 ~47%       → 全局漏音（tick 喂法 / 记录展开）
   某点之后骤降      → 某轨中途停了 / 提前循环
   只有某几桶异常    → 数据里有特殊段落（变轨）
3. 若怀疑"变轨"：记录每轨 (seg, loop, cur, en) 序列，统计 seg 变化
   （如果 [bx+0] 会变，说明一条轨会跨数据段，所有"走完一遍"的判据都要按段算）
```

**TLOVE_08 是变轨的试金石**：WIN 版 198.2 s / 19090 音，最后 15 秒只有 294 音。
如果我们的导出没有这个稀疏收尾，就是吞了 coda。

## 四、执行顺序与止损

```
0. 甄别假参照          （半天）
1. 出全库台账 + 静态体检（一天）
2. 统计各类占比 → 决定投入
3. 修 B 类（tempo）     ← 改动最小，先验证判据有效
4. 修 D 类（pass 判据）
5. 查 C 类（密度）      ← 最难，可能牵出变轨
```

**止损规则**：

- 每步单独验证，**不许合并改**；
- 哪一步的统计结果与预期不符，停下汇报，不要"顺手再改一处"；
- C 类调查若两轮内定位不到病因，先冻结，把 A/B/D 类交付完。

## 七、验收口径（2026-11-25 用户确认）

`no-ref` 不是最终失败，也不要求每首单独找 HOOT。顺序是：

1. 先解决审计已发现的问题（OPENING 密度、11 首 `cap`、FMD5 密度、
   `VENUS_03` tempo、TLOVE_02/08/16 等）；
2. 修完后重新导出；
3. 对**未使用相关驱动特性**的曲子，做新旧导出对比：
   - 优先逐字节 SHA256 相同；
   - 若只差容器/元数据，比较音符、时间、tempo、通道事件流，必须无差别；
   - 无差别 → 这些 `no-ref` 按「回归通过」验收，不再逐首找参照。
4. 已知问题涉及的曲子仍按参照/专项判据；
5. 用户会另做 HOOT 抽查。
