# MSDRV4（黒パッケージ）—— `.MS` 格式

《殻の中の小鳥》（Black Package / 1996）用的 MIDI 驱动。

## 结论先说

**`.MS` 用的是 MMD 的命令系统**，只换了容器。
MMD 是 KAJA 的 PC-98 MIDI 驱动，两者指令编码一致 —— 这大概率不是巧合，
MSDRV4 要么直接用了 MMD，要么是照着它写的。

## 容器

```
+0x00  40 × u32 偏移表
         前 36 项是轨道指针，第 39 项指向文件末尾
         轨道号 = MIDI 通道号（0–15），16 以上为空轨
```

空轨是 `fe 9e 9e 9e`（结束符 + 填充）。

## 命令

与 MMD 相同的部分：

| 字节 | 含义 | 例 |
|---|---|---|
| `< 0x80` | 音符（音高 / 延迟 / 长度 / 力度） | `3c 64 00 40` |
| `0x80–0x8F` | 位掩码形式（bit3→buf0, bit2→buf1, bit1→buf2, bit0→buf3） | `8a 78` |
| `0xE6` | **选轨**：`e6 00 NN` | |
| `0xE7` | 变速：`e7 00 XX 00` | |
| `0xD8–0xDF` / `0xE8–0xEF` | MIDI 消息（类型 = 低 4 位） | `eb 00 5b 4b` = CC 91 = 75 |
| `0xFE` | 结束 | |

**与 MMD 不同的部分**：

1. **`0x9E` 是单字节命令**（等待 / 同步）。MMD 里没有这个，
   但它夹在命令之间频繁出现（`8a 78 9e 9e e6 00 00 9e …`）。
   不这样处理的话，`e7` 变速会被吞掉。

2. 没有 16 轨头部，也没有曲名。

## 已验证

`MD_01_GS.MS`（Heels Beat on the Stone Paving）解析出 **57.5 秒**，
VGM 包记录的官方时长是 **0:57** —— 吻合。

### 与参考 MIDI 对照

手上有 VGMrips 附带的 `風は無くとも鳥は飛ぶ`（第 4 首）SC-55 / SC-88 两份 MIDI。
按「官方时长 ÷ tick 数」给每首算一个整体速度后：

| 我们 | 参考 | 时长 | 音符 | 音程相似 |
|---|---|---|---|---|
| 04 [SC-55] | SC-55 | 231 / 235 秒 | 1979 / 1856 | **1.00** |
| 04 [SC-88] | SC-88 | 231 / 236 秒 | 2215 / 2056 | **1.00** |

**音程序列完全一致**（前 16 个音逐个吻合），说明音符、时值的解析是对的。
音符数多约 7%，可能是同音连打或装饰音的差异。

## 变速与通道（已解）

### `8A XX` = 设 BPM

**tempo 不在 `e7` 里，而在 `8A` 里。**

```
8a 41    ← MD_04：0x41 = 65 BPM
8a 78    ← MD_01：0x78 = 120 BPM
```

`tempo_us = 60000000 / XX`

用「官方时长 ÷ tick 数」独立算出的 BPM 对照：

| 文件 | `8A` 值 | 反推 BPM | 差 |
|---|---|---|---|
| MD_01 | 120 | 121.0 | 1.0 |
| MD_03 | 82 | 84.8 | 2.8 |
| MD_04 | 65 | 66.2 | 1.2 |
| MD_07 | 110 | 113.1 | 3.1 |
| MD_08 | 74 | 76.1 | 2.1 |
| MD_09 | 125 | 130.5 | 5.5 |

六个独立样本全部吻合（差 1–5 BPM，来自 tick 数取整）。
**这也解释了为什么 MD_04 一个 `e7` 都没有却有 231 秒。**

所以 `e7` 在这个驱动里**不是**变速——语义待定，先跳过。

### `E6 00 NN` = 设通道

**通道号不等于轨道号。** 实测 `MD_04_GS.MS`：

| 轨 | 开头 | 实际通道 |
|---|---|---|
| 0–9 | `e6 00 00` … `e6 00 09` | 0–9 |
| 10 | `e6 00 0a` 然后 `e6 00 09` | **9** |
| 11 | `e6 00 0b` 然后 `e6 00 09` | **9** |
| 12–15 | `e6 00 0c` 后紧跟 `fe` | 空 |

所以**轨 10、11 是通道 9（打击乐）的追加声部**。
按轨道号分配会多出 ch10/ch11，而鼓轨的音符被拆散——这正是和参考 MIDI 对不上的原因。

### 其它命令

| 命令 | 长度 | 说明 |
|---|---|---|
| `9E` | 1 字节 | 等待/同步 |
| `9C` | 3 字节参数 | 用途未明，跳过 |

## 静态反汇编的结论：此路不通

反汇编了 `MSDRV4.EXE` 之后，得到一个**明确的否定结论**——这本身比继续试参数有价值。

### 已确认的

`[0050h]` **不是命令字节，是 MIDI 端口选择器**（0/1/2）：

```asm
; 选端口
mov al, [0052h]
mov [0050h], al      ; 当前端口类型
mov ax, [0058h]
mov [0054h], ax      ; 数据口
mov ax, [005Ah]
mov [0056h], ax      ; 状态口

; 输出
cmp byte ptr [0050h], 2
jae  short
in   al, dx          ; 等状态 bit6
test al, 40h
jne  ...
out  dx, al          ; 发数据
```

之前把 `mov al,[0050h]` / `sub al,80h` 当成命令分派，是**误读**。

### 否定的部分

整个 83 KB 里**没有任何一条命令比较指令**：

| 指令 | 出现次数 |
|---|---|
| `cmp al, 8Ah`（设 BPM） | **0** |
| `cmp al, 9Ch` | **0** |
| `cmp al, 9Eh` | **0** |
| `cmp al, E6h` | **0** |
| `cmp al, E7h` | **0** |
| `cmp al, 0FEh` | 2（均无关） |

13 处 `sub al, 80h` 全部是缓冲区地址计算：

```asm
add di, 1000h
shl ax, 2
add di, ax
sub al, 80h        ; 这里的 80h 是数据偏移
```

所以**分派不是比较链**。

### 可能的解释

1. **跳转表分派**——`sub al,80h` 之后 `jmp [table+bx*2]`。没找到该模式。
2. **指令流被预处理过**——加载时先"编译"成内部表示，解释器只处理编译后的形式。

**② 更可能**：`lodsb` 密集出现在 0x30E–0x324 这一小段（169 处里有相当一部分挤在这里），
那种密度更像解码/展开例程；而且 EXE 里有大量 `J J J J`、`$S$S$S$S` 这样的重复字节，
像是压缩数据。

结构上和 MMDR 完全不是一类东西：

| | MMDR | MSDRV4 |
|---|---|---|
| 大小 | 3218 B | 83290 B |
| 格式 | 裸 COM | MZ + 疑似压缩 |
| 可读性 | 一望即知 | 有编码层 |

## 这件事说明了什么

**文件格式不等于音乐的完整定义。**

`.MS` 里没有"这条命令等几拍"的说明——它只有操作码和操作数。
真正的语义（一个延迟单位是多少 tick、`9C` 的三个字节干什么、`E7` 是什么）
**只存在于驱动的运行时行为里**。

所以：

- 能静态解出来的，是**结构**（表、命令、参数）
- 解不出来的，是**时间语义**
- 而后者恰恰是音乐能不能听的关键

这也解释了为什么 MMDR 当初只能靠跑：**这类格式本来就不是自描述的**。
写驱动的人只需要它自己认得，不需要别人认得。

**必须转仿真。** 让驱动自己跑、抓 `out` 端口的时间戳——这也是 HOOT 的做法。

## 仿真方案

```
1. Unicorn 加载 MSDRV4.EXE（MZ，CS=0x1E，IP=0）
2. hook 所有 out（MIDI 数据口 + 8253 的 out 0x77/0x71）
3. 喂入 MD_04_GS.MS
4. 对比参考 MIDI 的事件时间，反推每条命令的 tick 数
```

MMDR 的仿真代码（`companies/leaf/src/mmdr_emu.py`）可以直接改。

## 仿真的尝试（已跑通，能出音）

写了 `src/exe_load.py`（MZ 装载器），结论如下。

### 能做到的

```
MZ 解析         ✅ 重定位 167 项，全部应用
装载            ✅ PSP(0x1000) 与 load module(0x1010) 分开，差 0x10 段
执行            ✅ 跑起来了
DOS 调用        ✅ AH=09 打印 / AH=35 取向量 / AH=25 设向量 / 48/49/4A 假分配器
常驻            ✅ 打印完整配置后 INT 21 AH=31 TSR
INT 61 派发     ✅ 按 IVT（push FLAGS/CS/IP）后 API 可用
板子探测        ✅ 按探测序列应答，选中标准 MPU 分支
播放            ✅ AH=21 AL=0 后 INT 0Bh 出节拍，0xE0D0 出 MIDI
导出            ✅ 5 包 81 个 MIDI（GS/88 双版本，时长按 Timer B 校准）
```

### 旧结论作废：不是 DOS 内存，是 INT 61 没派发

当初以为它崩在 `22A1:0335`、“跳进数据区”、依赖内存控制块/低内存数据。实际是：

- 它在这条指令上停住：`22A1:0333  mov ah,1 / int 61h`；
- **驱动的常驻 API 就是 `INT 61h`**，而当时的 hook 只认 `CD 21/08/7F/20/16`，
  `CD 61` 被当成无效指令 → 看起来像“跳进数据区”；
- `AH=48/49/4A` 给个假分配器就够，**不需要 MCB**；
- `pusha` 这类 386 指令 Unicorn 本来就能跑，**不是问题**。

补上 IVT 派发后，驱动打印 `以下の設定で常駐します。`（含端口、缓冲区大小等配置），
然后正常 `INT 21 AH=31` 常驻。

### 后端检测：按探测序列建模后，选中 super-MPU

驱动是「核 + 后端」结构，常驻数据段 `0x177C`。装的时候会跑两段探测：

1. `0x53E7`：先试三组 FM 端口（`0x88`、`0x188`、`0x288`），取分数最高的；
2. `0x52E0` 那条链里 `0x55CC` 探 super-MPU：读 `0xE0DA`、写 `0x0A` 再读回，
   `>>9` 后等于 `0x0A` 就认。

我们的 `in` 原先一律返回 `0xFF`，探测全超时。按下面这张表应答之后：

| 端口 | 应答 |
|---|---|
| `0x1480` / `0x1481` / `0xA460` | 非 `0xFF`（探测循环等的是“不是 FF”） |
| `0x88/0x8A/0x8C/0x8E`、`0x188…`、`0x288…` | `0x00`（bit7 清零 = 就绪） |
| `0xE0DA` | 写什么、读回 `(v << 9)`（super-MPU 的回显） |
| `0xA0` | `0x20`/`0x00` 交替（等 bit5 翻转的握手） |
| `0xE0D0` / `0xE0D2` | `0xFE` / 就绪时 bit6=0 |

结果：`[0x63]=06`（MIDI 板）、`[0x52]=0x80`、`[0x53]=0x81`（super-MPU），
打印 `...initilize super-mpu...` 后正常 TSR。

### MSP_HOOT.COM：HOOT 自己的壳把协议写好了

包里那 207 字节的 `MSP_HOOT.COM` 就是 HOOT 给这个驱动的壳，反汇编直接给出调用序列：

```asm
AH=10  INT 61               ; 初始化
AL=00  AH=20 INT 61         ; 返回 ES:DI = 歌曲缓冲（实测 22A1:0000，32 KB）
AL=20  AH=20 INT 61         ; 另一块缓冲（实测 177C:3A50）
AL=30  AH=20 INT 61         ; 再一块（实测 177C:5650）
AH=3F  INT 21               ; 把文件读进上面拿到的缓冲（句柄 0x10 / 0x11）
AH=21 AL=00 INT 61          ; 播放（读 AH=20 拿到的缓冲）
AH=22 AL=00 INT 61          ; 停止/复位
AH=22 AL=01 DX=0x00B4       ; 设参数（速度）
```

启动时它还挂 `INT 7F`，从端口 `0x7E0` 取命令：`0` = 重读文件并 `AH=21 AL=0` 播放，
`2` = 停止。

### INT 61 的 API 表

入口 `1010:0005`，`jmp 0x18` → 按 AH 查表（表基址 `cs:0x46`，AH 0–0xD0；
64 个真实入口，其余 146 项是 `ret` 桩）。

| AH | 行为 |
|---|---|
| `00` | 版本，返回 `AX=0x0404` |
| `01` / `02` | 初始化 / 停止 |
| `03` | 轨道表 `DS:0x47D`（16 槽 × 4 字节 far 指针）：`AL=0` 注册 `ES:BX`、`AL=1` 清、`AL=2` 数空槽、`AL=3` 取 |
| `08` | 每通道音量（`DL = 0x7F - [ch+0x48]`） |
| `10/11/12/14/15/18` | 读配置（`[0x2A]`/`[0x63]`/`[0x38]`/`[0x52]`/`[0x58]`/`[0x5A]`…） |
| `20` | `AL=0/0x20/0x30` → 分别返回三块缓冲的 `ES:DI` |
| `21` | `AL=0` 从头播放、`AL=1` 续播、`AL=5/6` 读写 `[0x40C]`、`AL=7` 设 `ES:DI` 指针 |
| `22` | `AL=0` 停止、`AL=1` 带 `DX` 设参数（HOOT 用 `DX=0xB4`） |
| `30–32` | 板级查询 |
| `40/41` | 走后端表（`0x597D`/`0x59DD`） |
| `47` | 遍历 `DS:0x68`（步长 `0x21`）逐轨推进 |
| `D0` | 写配置 |

### 出音了：`0xE0DA` 不回显 → 走标准 MPU 分支

关键一步：让 `0xE0DA` **不回显**（读回 0），驱动就不选 super-MPU，改走 `0x5614`
那条标准 MPU 分支，`[0x52]=0x01`、`[0x53]=0x03`，数据口回到 **`0xE0D0`**。

这样 `AH=21 AL=0` 之后，`0xE0D0` 上就是真正的 MIDI 流：

```
F0 41 10 42 12 40 00 7F 00 41 F7      ; GS reset
F0 41 10 42 12 40 01 30 04 0B F7      ; GS DT1（逐个参数）
E0 00 40 E1 00 40 … EF 00 40          ; 16 通道 pitch bend 回中
9x nn vv …                            ; 音符
```

抓 3000 拍就有 974 个 note-on + 18 条 SysEx，通道/音色都对。

### 节拍：`(256 − TimerB) × 0.2911 ms`

驱动把 OPNA 的 **Timer B** 当音乐时钟（`0x188=0x26` → `0x18A=value`），并且**每首曲子的值不同**：

| 曲 | TimerB | tick |
|---|---|---|
| MD_01 | 220 | 10.48 ms |
| MD_02 / MD_06 | 208 | 13.97 ms |
| MD_03 | 204 | 15.14 ms |
| **MD_04** | **190** | **19.21 ms** |
| MD_05 | 211 | 13.10 ms |
| MD_07 | 217 | 11.35 ms |
| MD_08 | 198 | 16.88 ms |
| MD_09 | 222 | 9.90 ms |

系数用 **MD_04 ↔ `風は無くとも鳥は飛ぶ_SC-55.mid`** 拟合：1847 个音全部对齐，
斜率 19.213 ms / 66 计数 = **0.2911 ms/计数**，残差中位 9.4 ms。

> 参考只用 **SC-55 MIDI**（和 `.MS` 自己的速度数据）。同目录的 `.vgz` 是**芯片音乐**
> （FM/YM2608 录音），不是 MIDI 编曲，时长/音符/速度都不能用来校准。

### 还差什么

1. **还剩两个包的容器没解**：`stjan2_98` 是 `.BM0/1/2`（三份一套曲，疑似分 bank），
   `rekiai_98` 是 `.MF`（`MF01` 头，另一种容器）。`get_98`/`merrygr_98` 的 `.MSF`
   已确认同 `.MS` 格式并导出；
2. 曲名已按 HOOT `<titlelist>` 全部换成日文（见上表）；
3. `0xE0D4`/`0xE0D8`（super-MPU 路径）不需要了——标准 MPU 分支已经能出音；
4. 缓冲区上限 32KB（`0x22A1`）；
5. 乐器/通道已对，但 `E7`/`C1–C4`/`9C` 的语义仍是静态解析那边的老问题。

探针与导出器：`build/_msdrv_probe*.py`、`build/msdrv_export*.py`、`build/msdrv_all.py`。

## 未解决

- `e7` 的语义（**不是变速**，已确认；速度走 `8A`）
- `C1–C4` 那几个未知命令
- **通道分配**：`E6` 能读出来，但按它分配后每首的通道数仍不一致
- **开场静默短 3.8 拍**（参考 5.35 拍，我们 1.58 拍）——总时长却对得上
- **MD_05 / MD_06 时长偏短**（72.6 vs 125、57.9 vs 92）

### 已修的坑

1. **`vlq()` 收到负数会死循环**——`v >>= 7` 对负数永远是 -1。
   合并 tempo 和音符事件时必须用同一个有序流，`last` 不能再单独推进。
2. **`E7` 曾被当作 tempo 输出**，把 136 当成 136 微秒，导致整曲速度失控（57 秒压成 1 秒）。
3. **`9C` 是 3 字节参数**（不是单字节）。试过单字节，时长立刻变成 96 秒 / 432 秒，明显变差。
4. **轨道开头的假音符**：轨道在第一条 `e6` 之前不算开始，
   且力度为 0 的 note_on 一律丢弃。这两条消掉了开头那个莫名其妙的鼓声。

## 驱动侧线索

`MSDRV4.EXE`（83290 字节，MZ，CS=0x1E，入口文件偏移 0x4A0）。

在文件 0x1B00 附近找到了 MIDI 输出层：

```asm
mov al, [0050h]     ; 当前命令字节
sub al, 80h
jnc +24             ; < 0x80 → 音符
mov al, [si+39h]
and al, 0Fh         ; 低 4 位 = 消息类型
```

但**没有** `cmp al,0E7h` 或 `and al,0F8h` 这类比较，
说明命令分派可能是跳转表，或者 `e7` 走的是和 `eb` 同一条通用路径。
tempo 的换算代码还没定位。
