# MSDRV4（黒パッケージ）—— `.MS` 格式

《殻の中の小鳥》（Black Package / 1996）用的 MIDI 驱动。

## 结论先说

**`.MS` 用的是 MMD 的命令系统**，只换了容器。
MMD 是 KAJA 的 PC-98 MIDI 驱动，两者指令编码一致 —— 这大概率不是巧合，
MSDRV4 要么直接用了 MMD，要么是照着它写的。

## 容器

```
+0x00  40 × u32 偏移表
         前 36 项是轨道指针，第 39 项指向文件末尾
         轨道号 = MIDI 通道号（0–15），16 以上为空轨
```

空轨是 `fe 9e 9e 9e`（结束符 + 填充）。

## 命令

与 MMD 相同的部分：

| 字节 | 含义 | 例 |
|---|---|---|
| `< 0x80` | 音符（音高 / 延迟 / 长度 / 力度） | `3c 64 00 40` |
| `0x80–0x8F` | 位掩码形式（bit3→buf0, bit2→buf1, bit1→buf2, bit0→buf3） | `8a 78` |
| `0xE6` | **选轨**：`e6 00 NN` | |
| `0xE7` | 变速：`e7 00 XX 00` | |
| `0xD8–0xDF` / `0xE8–0xEF` | MIDI 消息（类型 = 低 4 位） | `eb 00 5b 4b` = CC 91 = 75 |
| `0xFE` | 结束 | |

**与 MMD 不同的部分**：

1. **`0x9E` 是单字节命令**（等待 / 同步）。MMD 里没有这个，
   但它夹在命令之间频繁出现（`8a 78 9e 9e e6 00 00 9e …`）。
   不这样处理的话，`e7` 变速会被吞掉。

2. 没有 16 轨头部，也没有曲名。

## 已验证

`MD_01_GS.MS`（Heels Beat on the Stone Paving）解析出 **57.5 秒**，
VGM 包记录的官方时长是 **0:57** —— 吻合。

### 与参考 MIDI 对照

手上有 VGMrips 附带的 `風は無くとも鳥は飛ぶ`（第 4 首）SC-55 / SC-88 两份 MIDI。
按「官方时长 ÷ tick 数」给每首算一个整体速度后：

| 我们 | 参考 | 时长 | 音符 | 音程相似 |
|---|---|---|---|---|
| 04 [SC-55] | SC-55 | 231 / 235 秒 | 1979 / 1856 | **1.00** |
| 04 [SC-88] | SC-88 | 231 / 236 秒 | 2215 / 2056 | **1.00** |

**音程序列完全一致**（前 16 个音逐个吻合），说明音符、时值的解析是对的。
音符数多约 7%，可能是同音连打或装饰音的差异。

## 变速与通道（已解）

### `8A XX` = 设 BPM

**tempo 不在 `e7` 里，而在 `8A` 里。**

```
8a 41    ← MD_04：0x41 = 65 BPM
8a 78    ← MD_01：0x78 = 120 BPM
```

`tempo_us = 60000000 / XX`

用「官方时长 ÷ tick 数」独立算出的 BPM 对照：

| 文件 | `8A` 值 | 反推 BPM | 差 |
|---|---|---|---|
| MD_01 | 120 | 121.0 | 1.0 |
| MD_03 | 82 | 84.8 | 2.8 |
| MD_04 | 65 | 66.2 | 1.2 |
| MD_07 | 110 | 113.1 | 3.1 |
| MD_08 | 74 | 76.1 | 2.1 |
| MD_09 | 125 | 130.5 | 5.5 |

六个独立样本全部吻合（差 1–5 BPM，来自 tick 数取整）。
**这也解释了为什么 MD_04 一个 `e7` 都没有却有 231 秒。**

所以 `e7` 在这个驱动里**不是**变速——语义待定，先跳过。

### `E6 00 NN` = 设通道

**通道号不等于轨道号。** 实测 `MD_04_GS.MS`：

| 轨 | 开头 | 实际通道 |
|---|---|---|
| 0–9 | `e6 00 00` … `e6 00 09` | 0–9 |
| 10 | `e6 00 0a` 然后 `e6 00 09` | **9** |
| 11 | `e6 00 0b` 然后 `e6 00 09` | **9** |
| 12–15 | `e6 00 0c` 后紧跟 `fe` | 空 |

所以**轨 10、11 是通道 9（打击乐）的追加声部**。
按轨道号分配会多出 ch10/ch11，而鼓轨的音符被拆散——这正是和参考 MIDI 对不上的原因。

### 其它命令

| 命令 | 长度 | 说明 |
|---|---|---|
| `9E` | 1 字节 | 等待/同步 |
| `9C` | 3 字节参数 | 用途未明，跳过 |

## 静态反汇编的结论：此路不通

反汇编了 `MSDRV4.EXE` 之后，得到一个**明确的否定结论**——这本身比继续试参数有价值。

### 已确认的

`[0050h]` **不是命令字节，是 MIDI 端口选择器**（0/1/2）：

```asm
; 选端口
mov al, [0052h]
mov [0050h], al      ; 当前端口类型
mov ax, [0058h]
mov [0054h], ax      ; 数据口
mov ax, [005Ah]
mov [0056h], ax      ; 状态口

; 输出
cmp byte ptr [0050h], 2
jae  short
in   al, dx          ; 等状态 bit6
test al, 40h
jne  ...
out  dx, al          ; 发数据
```

之前把 `mov al,[0050h]` / `sub al,80h` 当成命令分派，是**误读**。

### 否定的部分

整个 83 KB 里**没有任何一条命令比较指令**：

| 指令 | 出现次数 |
|---|---|
| `cmp al, 8Ah`（设 BPM） | **0** |
| `cmp al, 9Ch` | **0** |
| `cmp al, 9Eh` | **0** |
| `cmp al, E6h` | **0** |
| `cmp al, E7h` | **0** |
| `cmp al, 0FEh` | 2（均无关） |

13 处 `sub al, 80h` 全部是缓冲区地址计算：

```asm
add di, 1000h
shl ax, 2
add di, ax
sub al, 80h        ; 这里的 80h 是数据偏移
```

所以**分派不是比较链**。

### 可能的解释

1. **跳转表分派**——`sub al,80h` 之后 `jmp [table+bx*2]`。没找到该模式。
2. **指令流被预处理过**——加载时先"编译"成内部表示，解释器只处理编译后的形式。

**② 更可能**：`lodsb` 密集出现在 0x30E–0x324 这一小段（169 处里有相当一部分挤在这里），
那种密度更像解码/展开例程；而且 EXE 里有大量 `J J J J`、`$S$S$S$S` 这样的重复字节，
像是压缩数据。

结构上和 MMDR 完全不是一类东西：

| | MMDR | MSDRV4 |
|---|---|---|
| 大小 | 3218 B | 83290 B |
| 格式 | 裸 COM | MZ + 疑似压缩 |
| 可读性 | 一望即知 | 有编码层 |

## 这件事说明了什么

**文件格式不等于音乐的完整定义。**

`.MS` 里没有"这条命令等几拍"的说明——它只有操作码和操作数。
真正的语义（一个延迟单位是多少 tick、`9C` 的三个字节干什么、`E7` 是什么）
**只存在于驱动的运行时行为里**。

所以：

- 能静态解出来的，是**结构**（表、命令、参数）
- 解不出来的，是**时间语义**
- 而后者恰恰是音乐能不能听的关键

这也解释了为什么 MMDR 当初只能靠跑：**这类格式本来就不是自描述的**。
写驱动的人只需要它自己认得，不需要别人认得。

**必须转仿真。** 让驱动自己跑、抓 `out` 端口的时间戳——这也是 HOOT 的做法。

## 仿真方案

```
1. Unicorn 加载 MSDRV4.EXE（MZ，CS=0x1E，IP=0）
2. hook 所有 out（MIDI 数据口 + 8253 的 out 0x77/0x71）
3. 喂入 MD_04_GS.MS
4. 对比参考 MIDI 的事件时间，反推每条命令的 tick 数
```

MMDR 的仿真代码（`companies/leaf/src/mmdr_emu.py`）可以直接改。

## 仿真的尝试（已试，未完成）

写了 `src/exe_load.py`（MZ 装载器），结论如下。

### 能做到的

```
MZ 解析         ✅ 重定位 167 项，全部应用
装载            ✅ PSP(0x1000) 与 load module(0x1010) 分开，差 0x10 段
执行            ✅ 跑起来了
DOS 调用        ✅ AH=09 打印 / AH=35 取向量 / AH=25 设向量
```

调用顺序是 `09 → 35 → 35 → 25 → 09` 然后崩——
**这就是标准的 TSR 安装流程**，可以确认它是个常驻驱动（不是播放器）。

### 卡在哪

崩在 `22A1:0335`，跳进了数据区。反汇编看到它在做 TSR 重入检测：

```asm
mov bx, 0
mov es, bx
test byte ptr es:[76F9], 1    ; 检查低内存标志
jne  已安装
```

**它依赖一个真实的 DOS 环境**（低内存数据、内存控制块链），
我们给的是全零内存。

而且它用了 **386 指令**（`pusha`），比 MMDR / MS.COM 那套 8086 代码复杂一个档次。

### 和已跑通的两个对比

| | MMDR | MS.COM | MSDRV4 |
|---|---|---|---|
| 大小 | 3.2 KB | 6.5 KB | **83 KB** |
| 装载 | 裸 COM | 裸 COM | **MZ + 167 项重定位** |
| 指令集 | 8086 | 8086 | **含 386 指令** |
| 首次尝试 | 通 | 通 | **崩** |

### 要继续的话

1. 内存控制块链（`AH=48/49/4A` 真实工作）
2. 低内存区的 DOS 数据（它检查的那几个标志）
3. 386 指令的支持

**估计还要 2–3 小时反复试。** 收益是 9 首曲子，所以先搁置。

## 未解决

- `e7` 的语义（**不是变速**，已确认；速度走 `8A`）
- `C1–C4` 那几个未知命令
- **通道分配**：`E6` 能读出来，但按它分配后每首的通道数仍不一致
- **开场静默短 3.8 拍**（参考 5.35 拍，我们 1.58 拍）——总时长却对得上
- **MD_05 / MD_06 时长偏短**（72.6 vs 125、57.9 vs 92）

### 已修的坑

1. **`vlq()` 收到负数会死循环**——`v >>= 7` 对负数永远是 -1。
   合并 tempo 和音符事件时必须用同一个有序流，`last` 不能再单独推进。
2. **`E7` 曾被当作 tempo 输出**，把 136 当成 136 微秒，导致整曲速度失控（57 秒压成 1 秒）。
3. **`9C` 是 3 字节参数**（不是单字节）。试过单字节，时长立刻变成 96 秒 / 432 秒，明显变差。
4. **轨道开头的假音符**：轨道在第一条 `e6` 之前不算开始，
   且力度为 0 的 note_on 一律丢弃。这两条消掉了开头那个莫名其妙的鼓声。

## 验证状态

### 对上的

- **program change 完全一致**：参考 `{0:49, 1:47, 2:0, 3:[32,48], 4:75, 5:46, 6:57, 7:60, 8:68, 9:48}`，
  我们一模一样
- **时长 9 首里 7 首对上**（见下表）
- **通道数**：MD_01 现在出 10 个通道，和参考一致

### 还没对上的

**开场延迟短了约 3.8 拍。** 参考第一个音在 2.68 秒（5.35 拍），
我们在 1.46 秒（1.58 拍）。总时长却能对上——说明丢的是**开头那一段等待**，
不是速度算错。

嫌疑仍在 `9C` 附近的字节对齐，但换成单字节会全盘崩，所以不是简单长度问题。

**MD_05 / MD_06 偏短**（72.6 vs 125、57.9 vs 92），疑似中途还有别的速度命令。

`e7` 抓到了，但**它不是 tempo 的唯一来源**。

| 文件 | 官方秒 | tick 数 | 反推 BPM | `e7` 值 |
|---|---|---|---|---|
| MD_01 | 57 | 5516 | 121.0 | 136 |
| MD_03 | 53 | 3597 | 84.8 | 199 |
| MD_04 | 231 | 12236 | 66.2 | **（无）** |

两个关键反证：

## 驱动侧线索

`MSDRV4.EXE`（83290 字节，MZ，CS=0x1E，入口文件偏移 0x4A0）。

在文件 0x1B00 附近找到了 MIDI 输出层：

```asm
mov al, [0050h]     ; 当前命令字节
sub al, 80h
jnc +24             ; < 0x80 → 音符
mov al, [si+39h]
and al, 0Fh         ; 低 4 位 = 消息类型
```

但**没有** `cmp al,0E7h` 或 `and al,0F8h` 这类比较，
说明命令分派可能是跳转表，或者 `e7` 走的是和 `eb` 同一条通用路径。
tempo 的换算代码还没定位。
