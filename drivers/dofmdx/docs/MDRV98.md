# MDRV98 / DOFMDX98（D.O. 的 MIDI 驱动）

驱动清单里 `DOFMDX98.COM` 有 **79 条记录**（do / foster / zyx 三家），是本地样本第三多的驱动。
但同一个驱动家族有**三种打包方式**，本文能跑通的只有"独立驱动"那一条：
**6 个包、117 首不同曲目**。四条路线的边界见下面的「覆盖边界」。
数据是 `.FMD` / `.MSC`（签名 `68V2`，明文）。

> **2026-11 这一轮的新结论**：驱动**是装中断的**，时序来自 **YM2608 Timer A**，
> 不是"由调用者传时间"。旧文档里"不装中断 / 纯可调用库"的说法作废，见下。

## 装载模型（已按代码确认）

| 文件 | 大小 | 装载位置 |
|---|---|---|
| `DOFMD_98.BIN` | **206** 字节 | 线性 `0x0600` = 段 `0x0060:0000`（`bootcs=0x0060 bootip=0`） |
| `MDRV98` | **11519** 字节 | 线性 `0x0FA0` = 段 `0x00FA:0000`（XML 里 `offset="0xfa0"`） |
| `CRxxx?.FMD` | — | 音乐数据（`F`=OPN / `C`=MT-32 / `G`=GS） |

**段基址是 `0x00FA`，不是 0。** 驱动内部用到的偏移（跳转表 `0x0029` 等）
都是相对 `CS=0x00FA` 的，所以"装在偏移 0"这个说法只对了一半：段内起点是 0。

证据是 BIN 开头直接写中断向量表：

```asm
000E  xor ax,ax
0010  mov ds,ax
0012  mov [0x114],ax        ; IVT[0x45].offset = 0
0015  mov [0x116],0x00FA    ; IVT[0x45].segment = 0xFA
```

`0x114 = 0x45*4`。**INT 45h 就是驱动入口**（`iret` 结尾，必须按中断方式调用）。

按这个布局在 unicorn 里跑 BIN，向量表结果：

```
INT 45 -> 00FA:0000     ← 驱动
INT 7F -> 0060:0039     ← BIN 自己的前端
```

### 踩过的坑（旧的装载位置是错的）

第一版把 `MDRV98` 接在 BIN 后面（偏移 `0xCE`，因为 206 = 0xCE 看着合理）。
错在两点：BIN 不在 0，驱动也不紧跟 BIN。实际是 `0x600` / `0xFA0`，
两者之间隔着 0x9A0 字节。用错布局时跳转表读到的是 BIN 的字节，
`call ax` 会跳到延时循环里。

## 启动流程（BIN，206 字节）

```asm
        cli
        mov dx,0x7E8 ; mov al,0x80 ; out dx,al   ; 声卡控制
        mov ax,cs    ; mov ss,ax
        mov sp,0x4CE
        mov ds,0 ; IVT[0x45] = 0x00FA:0000
        int 45h                                  ; AX=0 → AH=0 AL=0
                                                 ;   = 表 A 功能 0：硬件检测 + 装中断
        int 14h                                  ; BIOS
        IVT[0x7F] = CS:0x0039
        mov dx,0x7E8 ; mov al,0x81 ; out dx,al
        sti
        hlt / jmp $
```

BIN 自己的 INT 7F 处理器（`CS:0x39`）只做转发，见下节。

## API 派发（`CS:0x0000`）

```asm
pusha ; push ds ; push es
cmp ah, 0Ch
jae 退出
mov si, 0x29          ; 跳转表 A
or al, al
je  +3
mov si, 0x17D4        ; 跳转表 B（AL != 0）
xor al, al
xchg al, ah           ; AX = 功能号
add ax, ax
add si, ax
mov ax, cs ; mov ds, ax ; mov es, ax
lodsw                 ; ax = 表[功能号]
pop si
call ax
...
iret
```

**`AH` 是功能号（0–11），`AL` 选表。** 表 A 是 FM/声卡那套，表 B 是 MIDI 那套。

### BIN 实际怎么调（重要）

BIN 的 `AX` 是 `0x0100|state` / `0x0200|state` / `0x0400|state`，`state` 装好曲子后是 1：

| BIN 的 INT 7F `AL` | BIN 做的事 | 实际落到驱动的调用 |
|---|---|---|
| `0` | 看 state，调 `int 45h` | `AH=2 AL=state`（表 B 功能 2） |
| `1` | 从 `0x7D4` 读偏移、`0x7D6` 读段；校验 `[段:偏移]` 处的 `68V2`；调 `int 45h` | 先 `AH=0 AL=1`（表 B 功能 0，MIDI 板探测），再 `AH=1 AL=1 BX=段 DX=偏移`（表 B 功能 1，打开），最后 `AH=4 AL=1`（表 B 功能 4） |
| `2` | 跳回 `AL=0` 那条路 | 同上 |

关键：**BIN 只走表 B（`AL=1`）**。表 A 在这条链路里只用了一次——启动时
`int 45h` 的 `AX=0`（`AH=0 AL=0`），干硬件检测和装中断。

## 中断：驱动自己装 IRQ 处理器（推翻旧结论）

旧文档说"MDRV98 不装任何中断、IVT 写入 0 处"。**错。** 它写 IVT 用的是
`mov ds,0` 后的绝对地址，不是 `INT 21h/25h`，所以之前的搜索没搜到。

表 A 功能 0（`0x41`）做完声卡检测后，在 `0xDD`–`0xF0` 装处理器：

```asm
00DD  mov [0x185],si      ; 记下向量偏移（还原时用）
00E1  push ds / xor ax,ax / mov ds,ax
00E6  mov di,0x187
00E9  movsw / movsw       ; 把原 IVT[si] 存到驱动 0x187（注意 movsw 会让 si+4）
00EB  mov word [si-4],0x5BF
00F0  mov word [si-2],cs  ; 装新处理器（si 已后移 4，等价于写回原 si）
```

按板型选 `(si 向量偏移, cl PIC 屏蔽位)` 四选一：

| 板型（`in 0x18A` 读回 `&0xC0`） | si | 向量 | cl |
|---|---|---|---|
| `0xC0` | `0x50` | INT 14h | `0x10` |
| `0x40` | `0x54` | INT 15h | `0x20` |
| `0x80` | `0x48` | **INT 12h** | `0x04` |
| 其它 | `0x2C` | INT 0Bh | `0x08` |

实测（模拟器 `in 0x18A` 回读 `0xBF` → `&0xC0 = 0x80` 分支）：

```
INT 12 -> 00FA:05BF      ; si=0x48, cl=0x04（已用寄存器断点核对）
```

随后把 `cl` 存到 `[0x18B]`，`[0x18B]` 就是 PIC 屏蔽位；`0x162` 置屏蔽位（关中断）、
`0x13F` 清屏蔽位（开中断），都写 `0x08`/`0x0A`（从机 8259）。

### 处理器 `0x5BF` 干什么

```asm
05BF  cs:[0x15CE]=ss ; cs:[0x15D0]=sp ; cs:[0x15D2]=ax   ; 换栈到 0x17D4
05DA  pusha / push ds / push es
05E2  call 0x162          ; 关中断
05E5  call 0x6F1          ; EOI
05E8  inc byte [cs:0x5BE] ; 重入计数
05FC  call 0x5B0          ; 读 0x188，test bit0（Timer A）
05FF  jne 0x608           ;   bit0 → call 0x633（音乐推进）
0601  call 0x5BB          ; 读 0x188，test bit1（Timer B）
0604  jne 0x60D           ;   bit1 → call 0x19AE（MIDI 输出）
0613  call 0x13F          ; 开中断
...   恢复 SS:SP，iret
```

`0x633` 里读 `[0x120A]`（数据段），按通道结构推进；`0x71B` 处理 3 组通道。

**所以音乐是靠 YM2608 的定时器中断推进的，不是游戏每帧调用。**
这也解释了为什么之前"AL=0/1 × AH=各种 × 初始化顺序"全都 0 字节输出——
没有定时器中断，序列器一步都不走。

## 时序：YM2608 Timer A

初始化时写出去的端口序列（实测）：

```
0x7E8<-0x80
0x188<-0x07  0x18A<-0xBF      ; 写 0xBF 再读回 = 声卡存在检测
0x188<-0x07  0x188<-0x0E
0x188<-0x27  0x18A<-0x30      ; 定时器复位
0x0A <-0x00                    ; 开放 PIC 屏蔽位
0x7E8<-0x81
```

打开曲子（`CR001C.FMD`）时：

```
0x188<-0x24  0x18A<-0xDD      ; Timer A 高 8 位
0x188<-0x25  0x18A<-0x01      ; Timer A 低 2 位
0x188<-0x27  0x18A<-0x15      ; 载入 + 允许 IRQ + 复位
```

`0x27` 的位：bit0/1 = Timer A/B 载入，bit2/3 = Timer A/B 允许中断，bit4 = 复位。
`0x24 = 0xDD` + `0x25 = 0x01` 拼出 Timer A 计数值 `221*4 + 1 = 885`。
换成赫兹还没算，但**节拍来源就是这个定时器**，不用再找"哪个 API 是 tick"。

## MIDI 输出

| 端口 | 方向 | 用途 |
|---|---|---|
| `0xE0D0` | out/in | MIDI 数据（`0x2131` 直接写这里） |
| `0xE0D2` | in | 状态：bit7=有数据，bit6=忙 |
| `0xE0D2` | out | 数据（`0x2109`/`0x20F1` 走这条，带 ACK） |

- `0x2131`：等 `0xE0D2` bit6=0 → 写 `0xE0D0`，不等 ACK。
- `0x2109` / `0x20F1`：等 bit6=0 → 写 `0xE0D2` → `0x214B` 等 bit7=0 →
  从 `0xE0D0` 读回，期望 `0xFE`（ACK）。
- `0x214B` 超时置 `BX=0xFFFF`；`0x2109` 结尾 `mov ax,bx`，用 AX 返回这个状态。
- 表 B 发的是**标准 MIDI**：`0xB0|ch` + `0x07` + 值（音量）、
  `0xC0|ch` + 音色号（`0x1ED3`）、`0xB0|ch` + `0x7B` + `0x00`（All Notes Off）。

MIDI 板探测（表 B 功能 0 → `0x18A2`）：

```asm
18A2  mov dx,0xE0D2
18A5  in  al,dx
18A6  cwde
18A7  cmp ax,0xFFFF
18AA  je  0x18BE      ; 读回 0xFF = 板子不在（浮空）→ [0x18C2]=AL
      ... 有板子：发 0xFF/0x3F、初始化、[0x18C2]=0
```

**反了**：`0xFF` 走的是"板子不在"分支（`[0x18C2]=0xFF` 只是把 readback 存进去）。
旧文档写的"读到 0xFF 才置位 MIDI 通路"要按这条重新理解——
`0x18C2` 存的是 `in` 的返回值，不是"存在标志"。

## 打开曲子的参数（修正）

`AH=1` 的入参是 `BX=段`、`DX=偏移`，但**两张表的偏移含义不一样**：

| 表 | DX 指向 | 证据 |
|---|---|---|
| 表 A（`0x22B`） | 4 字节偏移表（要**跳过** `68V2`，即 `DX=+4`） | `mov ax,es:[di] ; add ax,di` |
| 表 B（`0x1807`） | `68V2` 魔数本身；函数内部自己 `add di,4` | `0x1910: add di,4` |

表 B 的实际入参是 `ES:DI`（`0x1807` 先 `push bx / push dx`，后面 `pop di / pop es`），
BIN 用 `BX=段 DX=偏移` 传进来正好对上。

表 A 实测（`BX=0x4000 DX=4`，`CR001C.FMD`）：

```
[0x1200] = 00FF
[0x120A] = 4000    ← 数据段
[0x1210] = 0004    ← 偏移
[0x1216] = 00C3    ← 4 + 表[0] = 4 + 0xBF，正确
```

功能 3 / 4 只是写播放标志，实测：

```
AH=3 → [0x1204] = [0x1205] = 1
AH=4 → 0
```

## 抓包导出（已完成）

`src/mdrvcap/` 就是成品（模块说明见 [src/mdrvcap/README.md](../src/mdrvcap/README.md)）。
只跑 MIDI 那条腿，不需要音频、不需要屏幕、不需要 FM 合成：

```
DOFMD_98.BIN（INT 7F 前端；板命令走 0x7E0，数据指针走 0x7D4/0x7D6）
        │ INT 45h
        ▼
   MDRV98 表 B（0x17D4）
        │ Timer B 中断 → INT 12h → 0x5BF
        ▼
   0xE0D0 数据 / 0xE0D2 状态（ACK 0xFE） → 字节流 → SMF
```

模型里必须做对的四条：

1. `in` 要回读上次 `out` 的值（功能 0 靠写 `0xBF` 再读回判断声卡）；
2. `0x188` 是状态寄存器：bit0 Timer A、bit1 Timer B、bit7 busy，**读不清**，
   写 `0x27` 才清标志。（处理器会连读两次分别测 bit0/bit1，实现成"读后清"的话
   第二次读就是 0，MIDI 永远不会被处理。）
3. 板命令走 `0x7E0`：`0`=设置、`1`=加载+播放；`INT 7F` 驱动 BIN 的前端；
4. `0xE0D0` 读回 `0xFE` 当 ACK。

### 时间校准

一次 Timer B 中断 = **4.908 ms**。用两份 Win95 GM 版参考做 DP 对齐 + 最小二乘：

| 参考 | 比值（ref tick / our tick） | 反解 tick |
|---|---|---|
| 水晶迷宫（cl_98） | 2.7479 | 4.9070 ms |
| 雑音領域（zatuon_98） | 3.9206 | 4.9008 ms |

## 覆盖边界（重要，别把三条路线混成一条）

同一个 `MDRV98` 家族在 HOOT 里其实有**三种打包方式**，能跑通的只有第一种。

| 路线 | 形态 | 覆盖 | 状态 |
|---|---|---|---|
| **A 独立驱动** | `DOFMD_98.BIN` + `MDRV98` / `ZYXMD`（11519 字节） | **6 个包**：cl_98(46) / you4_98(46，同曲目) / zatuon_98(17) / gbakuten_98(15) / kyouiku_98(24) / laidi1_98(15) | ✅ 抓包器只支持这一条 |
| **B `DOFMDX98.COM`** | 774 字节 DOS 装载器 + 游戏 EXE（驱动打包在 EXE 里） | 32 部 / 124 个条目；**11 包 766 个文件（678 首）已导出**，FM 4 包跳过、MMD 8 包另走、7 包缺失 | ✅ 已解 |
| **C `MDRV98.COM` / `BGMDRV.COM`** | 8–12 KB 的 DOS 常驻驱动 + 95 / 193 字节的小壳，数据是 `.MUS` / `.MDT` | 28 个包 | 🔶 `.MUS` 已能导出（libido7 / faladia / narumj）；shinc 部分、l7impact/shikumi/blue 等按构建待处理；`.MDT` 链已对上、运行卡循环 |
| **D `MV2x`** | 同一个 `DOFMD_98.BIN` 前端 + `MV21` / `MV22` 驱动 | 23 部（DOR 系列等） | ⛔ 纯 FM：只写 OPN `0x188/0x18A`，没有 MIDI 输出 |

补充事实：

- A 路线里 6 个包的驱动**内容完全相同**（sha1 `e8177a9bf8a3`），只是名字叫
  `MDRV98` 或 `ZYXMD`。按 32 字节签名扫全部 1777 个 pc98 包，命中就是这 6 个。
- `herceq_98` 也挂 `dofmd_98.bin` + `ZYXMD`，但它的 `ZYXMD` 只有 **5801 字节**，
  是另一个构建（跳转表位置不同），没跑过，不要当同一个驱动。
- 旧文档里的"79 部"是驱动清单口径，不是可导出数量；A 路线实际可导出 **117 首**（去重后）。
- **清点是基于 HOOT 库的，天然会漏。** 已知漏网：`TORIKO2`（虜2，D.O.）不在 HOOT 里，
  但存在 Win95 版 MIDI（36 首，`TK201`–`TK236`）。DOR 系列则在库里，走 D 路线
  （`MV21`/`MV22`/`MV23`），不属于本文的 MDRV98。

### brm2_98（Branmarker2）试跑记录

- 包里没有 `MDRV98`：只有 `DOFMDX98.COM`（774）+ `BR2_98.EXE`（139 KB）+ 67 个 `.CM/.GS/.FM`。
- 直接喂给 `mdrvcap`（用 cl_98 的驱动）**能出 MIDI**：`BM201.GS` 起头就是 `68V2`，
  驱动照常解析，430 秒里 12019 个音。
- 但这是**串驱动**：`BR2_98.EXE` 里搜不到 MDRV98 的 32 字节签名、跳转表、
  `Mdrv2System` 字符串，说明 B 路线的驱动是打包在 EXE 里的另一个构建，
  由 `DOFMDX98.COM` 在运行时解出来（它从 stdin 读 EXE，`INT 21h` 读数据，
  校验 `68V2` 后走 `INT 45h`）。
- 所以：**数据格式兼容，驱动不一定同版**。brm2 的输出目前只能算"格式上跑得通"，
  不能当原版结果用。要真解 B 路线，得复刻 `DOFMDX98.COM` 的装载流程（DOS 环境）。

### B 路线：DOFMDX98.COM 的装载流程（已跑到驱动初始化）

`DOFMDX98.COM`（774 字节）不是普通装载器，它做四件事：

1. `INT 21h AH=3F` 从 stdin 读游戏 EXE 的**文件名**（HOOT 的 `conin` 喂的就是这个名字）；
2. `INT 21h AH=4B03` 把 EXE 当**覆盖层**加载（brm2：136,603 字节 + 537 个重定位）；
3. 在加载后的 EXE 里按指令字节模式搜驱动入口——
   `BE 54 01`（`mov si,0x154`）… `BF xx xx` … `A5 A5` … `C7 44 xx FC` …
   找到后把远指针写回，`INT 21h AH=25 / AL=45` 把 **INT 45h 指到驱动入口**；
4. 装 `INT 7F`（自己的 handler），之后由它从 stdin 读曲子、校验 `68V2`、走 `INT 45h`。

**驱动是编译在游戏 EXE 里的另一个构建**（brm2 样本）：

| 项 | 值（段内偏移） |
|---|---|
| 驱动入口 | `INT 45h = 4E05:0007`（EXE 镜像装在段 `4010`） |
| 派发器 | `cmp ah,0x0E`；表 A 在 `0x49`，表 B 在 `0x227A` |
| 功能 0（检测 / 装中断） | `0x2304` |
| 功能 1（打开曲子） | `0x230D` → `0x234B` 设置 → `0x2C42`/`0x2C2A` 发 `FF 3F` → `0x2425` 解析 → `0x22F1` 开定时器 |
| 时序处理器 | `INT 12h = 4E05:093F`（驱动自己装的） |
| 声卡检测 | 文件偏移 `0xE9B5`（`mov cx,0x188; in al,0x60`） |
| MIDI 探测 | 文件偏移 `0x10D2C` 起，共 7 处 `mov dx,0xE0D2` |

**已经跑通**（自建的 DOS 环境，脚本在 `build/hootcap/dosrun.py` + `broute.py`，
实现了 `INT 21h` 的 `48/49/3D/3F/3E/4B03/25`）：

```
shell 初始化完成：INT45=4E05:0007  INT7F=0A00:0178  INT12=4E05:093F
触发 INT 7F：读入 BM201.GS(2715B) → 校验 68V2 → 探测 → 发出 FF 3F
```

**板子握手（已解）**。这个构建的 `0xE0D2` bit7 语义是「发送就绪」：

| 事件 | bit7 | `0xE0D0` 读回 |
|---|---|---|
| 平时 | 1 | — |
| 往 `0xE0D2` 写一个命令 | → 0 | — |
| 读 `0xE0D0`（应答） | → 1 | `0xFE` |

- 命令走 `0xE0D2`，真正的 MIDI 数据走 `0xE0D0`；
- `0x2C84` 等 bit7 **清零**再读应答，`0x2C6A` 等 bit7 **置位**再写数据；
- 之前把 bit7 当成"有数据可读"，方向正好反了，所以死在 `0x2C84`。

这个驱动开定时器的写法与 A 路线相同（`0x26=0xEF`、`0x27=0x2A`），
所以 tick 仍是 **4.9082 ms**，时间轴不用重新标定。

**结果**：B 路线 11 个包全部导出（7 分钟/首，共 766 个文件；去重后 678 首）：

| 包 | 曲目 | 包 | 曲目 |
|---|---|---|---|
| brm2 | 134（GS+MT-32） | rouge_d | 136 |
| yojus2 | 116 | laidi2 | 72 |
| thotel | 58 | heart_r | 56 |
| you6 | 56（= heart_r） | hsuna3 | 52 |
| cybalpha | 32 | you8 | 32（= cybalpha） |
| ringout | 22 | | |

交叉验证：`brm2` 的 430 秒导出是 12015 个音，而用 A 路线驱动"串"同一份数据是 12019 个，
差 4 个（截断边界）——说明跑的是游戏内真驱动。

**覆盖盘点（32 个包）**：

| 类别 | 包 | 处置 |
|---|---|---|
| 已导出 | 11（上表） | ✅ |

| MMD / `.PAI` 作品 | h_kioku1/2、k_chojin、rakuen1/2、rinkan_g、sayonara、timestrm | ➡ 走 `mmd_parser`，不是这条驱动 |

### C 路线：常驻驱动 + 小壳（已收口，2026-11-22）

28 个包实际上是**两种数据、三套壳**：

| 数据 | 驱动 | 壳 | 包 |
|---|---|---|---|
| `.MUS` | `BGMDRV.COM`（约 9 KB） | `BGMDRV98.COM`（193 B） | libido7、faladia、narumj、shinc（GS/GM，已导）；l7impact、shikumi（HOOT 只有 `opn`，PASS） |
| `.MUS` | `BGM.COM`（5–6 KB） | `BGMDRV98.COM` | blue、freew、providen（**纯 FM**，只写 OPNA `0x188/0x18A`） |
| `.MDT` | `MDRV98.COM`（8–12 KB） | `MDRV98P.COM`（95 B）/ `mlp_hoot.com` | ee、ee2、kyoko、mjm、tobakka、yougen、pocky2、ponkan、ponyon、tensen、pt_anth2、yumeut、tohoreii、twins98、mrkdia98、oz98、bktb98、cz98 |

**壳 `BGMDRV98.COM`（`.MUS`）**

1. 扫 INT 64h / INT 68h 的处理程序，比对其段内 `0x103` 处的 7 字节 `"KIN_BGM"`
   定位驱动（驱动入口在 `0x10B`，前面故意留了签名）；
2. 把 `INT 7F` 挂到自己的处理程序；
3. 命令 0：`INT 64h AH=3` 复位 → 从端口 `0x7E2` 取一个 16 位值
   （高字节是命令、低字节是文件句柄）→ 把 `.MUS` 读进 64 KB 缓冲 →
   再调一次 `INT 64h`，此时 **DS:DX = 缓冲**。

**驱动 `BGMDRV.COM`**

- TSR 驻留；INT 64h 是 API，跳转表在 `0x113A`（AH 0–2 → `0x142`，3 → `0x30F`，
  4 → `0x37B`，5 → `0x38B`，6 → `0x40C`，7 → `0x42A`）；
- INT 08h 是时钟（`0xDDC`）；MIDI 走 `0xE0D0` / `0xE0D2`；
- 板子探测在 `0x1E7`：写 `0x3F` 到 `0xE0D2`，读 `0xE0D0` 等 `0xFE`，
  结果写进 **`[0x21EB]` 通道掩码**。

**`.MUS` 格式**：14 条 4 字节记录（轨号、`0xFF`、偏移 16 位），数据从 `0x38` 开始。

**已经跑通**：驱动驻留（`INT 64h = 1000:010B`）、壳靠签名找到它、`INT 7F` 触发后
发出 147 字节通道初始化（`B1 40 00` / `B1 7B 00` / `B1 01 00` …）。

**`.MUS` 的正确播放姿势（实测）**：

1. 驱动驻留后，把 **`[0x21EB]` 板子能力掩码设成 `0xFF`**（正常是 `0x1E7` 的探针
   写它：写 `0x3F` 到 `0xE0D2`、读 `0xE0D0` 等 `0xFE`，默认 0 会导致所有轨道被禁用）；
2. 壳的 `INT 7F`（命令 0）把 `.MUS` 读进 64 KB 缓冲；
3. 手动调驱动 **`INT 64h AH=0`**（轨道 0–5）和 **`AH=1`**（轨道 6–13），
   `DS:DX = 缓冲段:0`——这两条才是解析轨道的；
4. 按驱动设的 8253 计数器（`[0x21F8]=0x1333`，2.4576 MHz / 4915）**每 2 ms 敲一次 INT 08h**。

**踩过的坑**：

- 端口 `0x7E2` 返回 `0x03xx` 只复位、`0x05xx` 才走 AH=5——但 AH=5（`0x3A7`）
  写的是 `0x1AEE+bx` 数组，真正让时钟出声的是 AH=0/1 写 `0x1AE0+bx`；
- **解析之后再调 AH=3 会把播放打回复位**（实测：只调 0+1 有音符，加一个 3 就变成
  每 tick 重发 16 通道初始化、零音符）；
- `BGMDRV.COM` 有 9035 和 9066 两种构建。9066（shinc/l7impact/shikumi）**不是另一套逻辑**：
  AH 分派表内容与 9035 逐项相同（表在 `0x1150` vs `0x113A`），只是数据偏移整体
  **+0x16**（`0x21EB`→`0x2201`、`0x1AE0`→`0x1AF6`），并且 API 向量从 **INT 64 换成 INT 68**；
- `BGM.COM`（blue/freew/providen）是第三种东西：`"KIN_BGM"` 不在 `0x103`
  （blue `0xD4F`、freew `0xD95`、providen 根本没有），壳的固定偏移比对会失败；
  而且它**没有 MIDI 口**，是纯 FM 驱动。

**结果（`.MUS`，2026-11-22 收口）**：只导 HOOT 挂 MIDI 标识（GS/GM）的作品，
FM（OPN/OPNA）一律 PASS。

| 作品 | 包 | HOOT | 导出 |
|---|---|---|---|
| ファルアディア | faladia_98 | GS | 25 首 |
| Libido7 | libido7_98 | GS | 14 首（LB19 坏，剔除） |
| なる麻雀 | narumj_98 | GM | 14 首（与 Libido7 **同一批 `.MUS`**，导出的 MIDI 逐字节相同） |
| Shinc | shinc_98 | GS | 11 首（SHINC_01 不导、SHINC_03 坏） |

合计 **64 个文件 / 50 首不重复**（`build/hootcap/cmidi7/`，7 分钟截断）。
复现：`python build/croute_export.py shinc_98 --skip SHINC_01.MUS --out build/hootcap/cmidi7/Shinc`

**判定为 FM、不再追的包**：

- `blue`/`freew`/`providen`：`BGM.COM` 里**没有** `0xE0D0`/`0xE0D2`，只写 OPNA
  `0x188`/`0x18A`（`0xD68` 处是标准「写地址口 → 忙等 → 写数据口」）；HOOT 也只挂 `opn`；
- `l7impact`/`shikumi`：`BGMDRV.COM` 9066 有 MIDI 路径，但 HOOT 没有 GS 变体
  （只有 `opn`），按 FM 处理。

**9066 构建本身没问题**——交叉实验：9066 驱动 + libido7 的 `.MUS`，输出和 9035 完全一致；
换回 shinc 的个别曲目才刷屏。所以刷屏是**数据/曲目语义**，不是构建、不是 DOS 环境。

**已知缺陷（未解，已剔除）**：`LB19`、`SHINC_03`、`SHINC_01` 会「复位刷屏」——
驱动每 tick 重发 16 通道初始化（`CC1`/`CC123` 各 7 万～160 万次），产出几百万事件。
导出后按「事件数 > 20 万或音符≈0」剔除。根因不在 MIDI 主线，未继续查。

**`.MDT` 路线（`MDRV98.COM` + `MDRV98P.COM`）**：这两个文件不是游戏里的驱动，
而是 **HOOT 自己的一套"宿主侧播放器"**：

- `MDRV98.COM` 驻留后挂 `INT F2h`（`1000:206E`）和 `INT 12h`（`1000:18E7`）；
- `INT F2` 的分派表按 AH 走（AH=3/4/0 → `0x21F9`，AH=6 → `0x219D` 拷贝，
  AH=8 → `0x21E2` 拷贝到 `CS:0x2800`，AH=9/0xA/0xB/0xC 是读写小工具……），
  整体更像一组**宿主服务原语**（拷缓冲、读写字节），而不是完整的播放 API；
- 壳 `MDRV98P.COM` 的顺序：`F2 AH=3` → 读 `.MDT` 到自己段 `0x15F` →
  `F2 AH=6`（把数据拷到驱动 `CS:0x4000`）→ `F2 AH=0`（清 0x500 字节状态区）；
- 驱动里的播放器状态：`[0x1C5]` 有效通道数、`[0x138]` 播放标志、
  `[0x123]` 解析指针；解析函数在 `0x767`（读 `[0x123]` 指向的数据）。

**卡点**：数据确实拷进了 `CS:0x4000`（`02 03 0D 00 …` 与 `.MDT` 一致），但
`[0x1C5]`/`[0x138]` 始终是 0——把所有 `INT F2` 的 AH（0–0x14）逐个试过，
没有一个能把解析指针 `[0x123]` 或有效通道数设起来。

结论：`.MDT` 这条路的播放逻辑**不在模拟器内的代码里**，而在 HOOT 宿主侧
（`INT F2` 只是两者之间的协议）。所以改走**静态解析**。

**静态解析（已完成）**：解析器在 [`drivers/dofmdx/src/mdt/`](../src/mdt/)，
用法 `python -m mdt <pack>`。

`.MDT` 格式（以 `ee_98/ALLY_S1.MDT` 为例，2326 字节）：

```
00: 02 03          ; 版本/格式
02: 0D             ; 曲号（索引，选中表里第 13 项）
03: 00             ; 标志（bit7 有效）
04: 01 00          ; ？
06: 表项…          ; 每项 4 字节：(u16 起点, u16 终点)
```

- `MDRV98.COM` 的解析入口 `0x767` 就是读这套头：`bx = 表 + 曲号*4`，
  取出两个 u16 加上基址得到 `[0x1A6]`/`[0x1A8]` 两个指针（曲子的起止）；
- 数据区是事件流：`0xE0` 循环开始、`0xE1` 出口、`0xE2` 跳回、`0xE9` BPM、
  `0xEA` 时值倍率、`0xEB` 音色、`0xEC` 音量、`0xF2` 绝对时值音符、`0xF9`/`0xFA` 跳转……；
  音高 = 高 nibble × 12 + 低 nibble；时间网格 48 tick/四分音符；
- 鼓轨（`0x8B0` 起）是另一套操作码（`00 C8 14 7A DC 41 …`）；
- 文件尾是 `FF FF FF FF 03 03`（结束标记）。

**产出**：19 个包、**507 首**（`build/mdt/out/`，不进仓库），合计 412,180 个音；
8 个 0 音符文件是静音/初始化占位（`MUON`×4、`CZ00`、`MKD00`、`INIT`、`TW00`）。

**两道必须保留的保险**（`parser.py`）：

1. `parse_track` 的迭代上限——`tohoreii_98/ST0.MDT` 的 `0xFF`+跳转路径会自循环，
   曾把 DSH 渲染进程拖到 OOM；
2. 音符读取前的 `ptr >= len(data)` 边界检查——`pocky2_98/A1_SB1.MDT` 会越界。

**限制**：这是 FM/SSG 数据，转出来是**音符级转录**（旋律、和声、节奏、循环长度保真），
音色用 GM 近似，LFO/包络等细节丢弃。想往“更像 FM 原曲”方向推（力度、CC、鼓映射、
音色表），改进项按性价比列在 [`src/mdt/README.md`](../src/mdt/README.md)。

### D 路线：FM，不是 MIDI（关闭）

`MV21` / `MV22` 里**一次都没有** `0xE0D0` / `0xE0D2`（MIDI 口），只写 OPN 的
`0x188` / `0x18A`。实测 200 个 INT 12 tick：`0x188`/`0x18A` 各写 4814 次，MIDI 字节 0 个。

`DOFMD_98.BIN` 前端 + MV2x 能正常跑（`INT 45 = 00FA:0000`，
`INT 12 = 00FA:041D`/`00FA:059B`），但产出的是 FM 寄存器流。

**结论：PC-98 版 DOR 系列是纯 FM，MIDI 版在 Win95。** D 路线没有 MIDI 可挖。

### 导出时长的约定（默认 7 分钟）

没有参考 MIDI 的包（B 路线全部、C 路线全部）按固定长度截断，默认 **7 分钟（420 秒）**：

- 依据：以已有的 **Win 版 MIDI** 为参照，7 分钟足以覆盖绝大多数曲子的完整长度与一次以上循环；
  再长只是在循环里重复，收益低；
- 代价：B 路线 678 首 × 7 分钟，并行 9 个进程约 20 分钟；C 路线 40 首 × 7 分钟，并行 3 个进程约 30 分钟；
- 有参考 MIDI 的包（A 路线）仍然**优先用参考长度**，不套这个默认值；
- 截断处会补 note-off，不会留挂音；但听起来是硬切，不是自然收尾。

**例外：`ringout_98` 有 Win 版参考**（`D:\music\90S Galgame music\RINGOUT\RIN01.MID`–`RIN11.MID`，
300–311 秒），已按参考长度重导（22 个文件），并顺带做了校验：

| 曲子 | 参考 | 我们 |
|---|---|---|
| RIN01 | 300.3s / 9235 音 | 300.3s / 9244 音 |
| RIN03 | 309.5s / 7955 音 | 309.5s / 7994 音 |
| RIN04 | 310.0s / 3825 音 | 310.0s / 3834 音 |
| RIN10 | 308.3s / 2016 音 | 308.3s / 2016 音 |

时长完全一致，音符数差在 0.5% 以内（边界音），说明 B 路线的抓包在音符层面也是对的。

**tick 时长的独立验证**：拿 `RIN01` 的 9235 个音逐音对齐（按音符序号对时间），
最小二乘拟合得到 **4.9087 ms/tick**，与假设的 4.9082 只差 0.01%——B 路线的
时间轴不是猜的，是量出来的。拟合还给出一个约 198 ms 的常数偏移（参考 MIDI 开头
比驱动输出晚一点），属于起播延迟，不影响比例。

### 踩过的坑：覆盖加载的重定位因子

实现 `4B03` 时把参数块里的 load segment 当成了"加载段 + 重定位因子"加了两遍，
驱动指针从 `4E05` 变成 `8E15`，`INT 45h` 一跳就飞到未初始化内存。
**重定位只加 load segment 一次。**

## 数据格式

`.MSC` 和 `.FMD` 是**同一种格式**（都以 `68V2` 开头），只是扩展名不同——
ZyX 的三个包用 `.MSC`，D.O. 的包用 `.FMD`，抓包器不用区分。

`68V2` + 4 字节一组偏移表 + 紧凑命令流。
抓包跑通之后，静态解只用于**理解数据本身**；事件与时间以驱动输出为准。
