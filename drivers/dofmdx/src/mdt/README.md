# `mdt` —— `.MDT`（MDRV2 的 FM/SSG 演奏数据）静态解析

`.MDT` 是 D.O. 那批「常驻驱动 + 小壳」作品的数据格式（ee、kyoko、tobakka、ponkan…）。
它们的播放逻辑在 HOOT 宿主侧（见 `MDRV98.md` 的 C 路线小节），模拟器里抓不到 MIDI，
所以这里走**纯静态解析**：直接读数据，输出音符事件。

原始数据是 FM/SSG 演奏指令，转出来的是**音符级转录**——旋律、和声、节奏、循环长度
都保留，音色用 GM 近似（FM 音色和 LFO 细节无法映射）。

## 用法

```bash
cd drivers/dofmdx/src
python -m mdt ee_98                 # 整包 → ./mdt_out/ee_98/*.mid
python -m mdt ee_98 D:\out\ee       # 指定输出目录
python -m mdt --file ALLY_S1.MDT    # 单文件
```

HOOT 素材路径默认 `D:\GamedataUnpack\hoot20251231\pc98`，可用 `HOOT_PC98` 覆盖。

## 格式

```
00: 02 03        ; 版本
02: 0D           ; 曲号（表索引）
03: 00           ; 标志（bit7）
04: 01 00
06: 表项…        ; 每项 4 字节：(u16 起点, u16 终点)
```

事件流（操作码表见 `parser.py` 的 docstring）：`0xE0` 循环开始、`0xE1` 出口、
`0xE2` 跳回、`0xE9` BPM、`0xEA` 时值倍率、`0xEB` 音色、`0xEC` 音量、
`0xF2` 绝对时值音符、`0xF9`/`0xFA` 跳转…… 音高 = 高 nibble × 12 + 低 nibble。

时间网格 48 tick/四分音符；`0xE9` 的值就是 BPM；门限 = 时值 × `0xEA` 倍率 / 8。

## 如果想更接近 FM 原曲

先说清楚：**原曲不是 MIDI**，是 FM/SSG 的寄存器演奏。这里做的是“音符级转录”——
旋律、和声、节奏、循环长度保真，但音色天然无法映射。所以它适合当**骨架**，
不适合追求“原声还原”。

如果要往“更像原曲”方向推，按性价比排序：

| 改进 | 成本 | 效果 |
|---|---|---|
| 力度：把 `0xEC` 音量、轨道音量映射到 velocity/CC7 | 小 | 动态层次回来，不再一条直线 |
| 淡入淡出 `0xF0` → CC11 | 小 | 段落过渡自然 |
| 鼓映射细化（位掩码 → GM 打击乐逐个核对） | 小 | 节奏更像原曲 |
| 颤音 `0xE6`/`0xED` → pitch bend | 中 | 长音不再死板 |
| 音色表：按每个包的 FM 音色号对到更接近的 GM patch | 中 | 听感提升最明显，但要人工试听 |

真正“原声还原”需要的是 **FM 合成**（按音色参数渲染 OPN/SSG），那是另一条路，
和 MIDI 转录是两个目标。

## 已知限制

- 19 个包、**507 首**（`build/mdt/out/`，不进仓库）；
- 8 个 0 音符文件（`MUON`×4、`CZ00`、`MKD00`、`INIT`、`TW00`）大概率是静音/初始化占位；
- **必须保留 `parser.py` 里的两道保险**：
  - `parse_track` 的迭代上限（40 万次）——`tohoreii_98/ST0.MDT` 的 `0xFF`+跳转路径
    会在不加计数的情况下自循环，曾把 DSH 渲染进程拖到 OOM；
  - 音符读取前的 `ptr >= len(data)` 边界检查——`pocky2_98/A1_SB1.MDT` 会越界。
